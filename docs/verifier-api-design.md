# Верификатор предъявлений для внешнего потребителя — предпроектное проектирование API и форматов

Статус: **предпроектная работа (бумажное проектирование), до блока 8-live**.
Код верификатора в этом документе НЕ создаётся и не описывается как готовый;
документ фиксирует проектные решения до их реализации.

Основа — **решение владельца 11.11.2026 (stage-decisions)**:

- язык — **Go**, с переиспользованием пакетов ядра (подписи, аттестация,
  Merkle, canonical-хеши) **как go-модульная зависимость**; вторая
  реализация протокола не создаётся;
- тесты — на **те же golden-векторы** (`vectors/`), что у ядра;
- API — **«verify в один вызов»** (предъявление + чекпоинт + доказательство);
- **без P2P-стека** в зависимостях;
- сборки JVM — через **gomobile bind**, JS — через **GOOS=js**.

Спецификация предъявлений — раздел 6.1 спецификации (KNOWLEDGE.md,
v9.16); форматы чекпоинтов — spec/07; каноническое кодирование — spec/01.

> **ПОМЕТКА О НЕСТАБИЛЬНОСТИ.** Параметры проверки и API, описанные ниже,
> **могут измениться после блока 8-live**: аттестация на реальном железе
> и замеры ресурсов (размер WASM/AAR, время проверки, память на живых
> устройствах) могут потребовать пересмотра состава полей, кодов ошибок
> и сигнатур. До завершения 8-live этот документ — проект, а не контракт.

## 1. Что проектируется

Внешний потребитель (стороннее приложение: сервис, партнёр, фонд —
профили 2, 4, 6, 7) проверяет предъявление участника сети, **не будучи
узлом** (6.1). Ему нужны:

1. проверка предъявления «в один вызов»: предъявление + чекпоинт +
   Merkle-доказательство + ожидаемые параметры сети на входе;
2. лёгкая синхронизация цепочки чекпоинтов с любого узла (6.1: «серверы
   проекта не нужны») — уже реализована в ядре (`core/present.LightSync`);
3. производные данные для решения (H(address ‖ app_id), статус, возраст,
   глубина, уровень гарантий) — **вердикт выносит проверяющий, протокол
   вердиктов не выносит** (6.1).

Всё это уже существует в ядре (`core/present.Verify`, `LightSync`,
`AppIdentity`). Проектируемый верификатор — **не новая реализация
проверки, а фасад над пакетами ядра**, упакованный для внешнего
потребителя: отдельный экспортируемый API-пакет поверх `core/present`,
`cons`, `core/crypto`, `core/wire`, `core/smt`, `core/threshold`,
`core/attest` — с устойчивыми форматами входа/выхода, типизированными
ошибками и сборками JVM/JS.

## 2. Переиспользование пакетов ядра (go-модульная зависимость)

Верификатор импортирует пакеты ядра из этого же модуля
(`github.com/rumatakira74/equality-trust-networks/...`). Для внешнего
потребителя ядро публикуется как обычная go-модульная зависимость
(репозиторий уже является Go-модулем); потребитель, в свою очередь,
импортирует пакет верификатора. Никакого копирования кода протокола.

| Пакет ядра | Что переиспользуется | Зависимости (внешние) |
| --- | --- | --- |
| `core/crypto` | ECDSA P-256 DER (`SignDER`/`VerifyDER`/`ParsePubKey`/`MarshalPubKey`), fingerprint, деривация адреса `DeriveAddress(fp, network_id)` | только stdlib |
| `core/wire` | канонический кодек (spec/01), `AttestStatement` (+`Hash`), `Checkpoint` (+`CheckpointHash`), `StateLeaf` | только stdlib |
| `core/smt` | `VerifyProof` — sparse Merkle-доказательство против корня состояния | только stdlib |
| `core/threshold` | `Verify` — N-из-M набор подписей ECDSA P-256 (spec/07 7.2, решение этапа 0) | только stdlib |
| `cons` | `Verify` чекпоинта (цепочка, возраст эпох, окно времени, пороговая подпись) | `golang.org/x/crypto` (Argon2id) |
| `core/present` | `Verify` (полная проверка предъявления), `LightSync`, `PubSource`, `AppIdentity` | `golang.org/x/crypto`, `core/*`, `cons` |
| `core/attest` | X.509-цепочки аппаратной аттестации (проверка корней, уровни, свежесть патчей) — для потребителя, которому нужен собственный порог устройства | только stdlib |

**Ключевое свойство (проверено пробой GOOS=js, см.
`reports/verifier-wasm-probe/`):** ни один из этих пакетов не тянет
P2P-стек. Внешние зависимости verify-контура — только
`golang.org/x/crypto` (argon2, blake2b, cryptobyte) и `golang.org/x/sys`.
Пакеты `net/`, `libp2p`, WebRTC-транспорт (`wlynxg/anet`) в граф
верификатора **не входят** — ни для JVM, ни для JS-сборки.

## 3. API: verify в один вызов

### 3.1. Сигнатура (Go)

Проектная сигнатура фасадного пакета (имя пакета — рабочее, `verifier`;
окончательное — при реализации):

```go
// VerifyAttestation — проверка предъявления «в один вызов» (решение 11.11):
// предъявление + чекпоинт + доказательство уже внутри attestation;
// ожидания сети и контекст вызова — в req.
func VerifyAttestation(attestation []byte, req VerifyRequest) (*VerifyResult, error)

// VerifyRequest — ожидания проверяющего (НЕ политика: протокол вердиктов
// не выносит, 6.1; пороги возраста/глубины проверяющий применяет сам
// к полям результата).
type VerifyRequest struct {
    NetworkID    []byte   // ожидаемая сеть (6.1: «из какой сети приходит человек»)
    ManifestHash []byte   // ожидаемый хеш манифеста (3.3, уровень гарантий)
    Challenge    []byte   // challenge, выданный проверяющим этому предъявлению
    NowSec       uint64   // текущее время (срок годности предъявления)
    PubOf        PubSource // открытые ключи подписантов чекпоинтов
}

// VerifyResult — производные данные для решения проверяющего.
type VerifyResult struct {
    AppIdentity [32]byte   // H(address ‖ app_id) — «один человек — одно действие» (6.1)
    Statement   *wire.AttestStatement // статус, возраст, глубина, flagged, эпоха
    Leaf        *wire.StateLeaf       // доказанный лист состояния
    AgeBound    uint64   // верхняя оценка возраста из листа (VerifyAgeBound)
}
```

Соответствие существующему ядру: `VerifyAttestation` — обёртка над
`present.Decode` + `present.Verify` (+ `VerifyAgeBound`), разворачивающая
ошибки в типизированные коды (раздел 5). Отдельным вызовом остаются:

- `NewLightSync(networkID, genesisTime, epochSeconds, maxShift, pubOf)` —
  лёгкий клиент цепочки чекпоинтов; `Adopt(cp)` принимает чекпоинты от
  любого узла (порядок поставки любой, приём строго последовательный);
- `AppIdentity(addr, appID)` — тот же идентификатор без предъявления;
- `ParseHardwareAttestation(chain, roots, minLevel, maxPatchAgeMonths, now)`
  — фасад над `core/attest` для потребителя с собственным порогом
  устройства (projected; параметры — см. пометку о нестабильности).

### 3.2. Сигнатуры для JVM (gomobile bind)

Ограничение gomobile: в экспортируемом API только `int64/[]byte/string/
bool/error`; `uint64` ядра конвертируется в `int64` (значения сети далеки
от 2^63 — тот же приём, что в `mobile/mobile.go`). Проектная поверхность:

```
VerifyAttestation(attestation []byte, networkID, manifestHash, challenge []byte,
                   nowSec int64, pubkeys [][]byte) (result *VerifyResult, err error)
```

`pubkeys` — открытые ключи подписантов (DER, [][]byte вместо callback
`PubSource`: gomobile не экспортирует произвольные функции-параметры;
внутри разворачивается в `PubSource` по списку). Результат —
экспортируемый тип с методами-геттерами (`AppIdentity() []byte`,
`Status() string`, `AgeDays() int64`, `VouchDepth() int64`,
`Flagged() bool`, `Epoch() int64`).

Прецедент по среде (stage-decisions 01.11): gomobile bind на Go 1.27
требует `-ldflags "-checklinkname=0"` — зависимость `wlynxg/anet`
(WebRTC-транспорт libp2p, только Android) использует `go:linkname` на
`net.zoneCache` (Go 1.23+ запрещает такие ссылки без флага). **У
верификатора `net/` в графе нет**, поэтому ожидание — флаг не потребуется;
проверяется при реализации (проба WASM этого не покрывает: gomobile
в сферу пробы не входил).

### 3.3. Сигнатуры для JS (GOOS=js GOARCH=wasm)

Тот же фасадный пакет экспортируется в WASM. Проектная граница —
минимальный набор из двух-трёх функций над `[]byte`-аргументами
(`VerifyAttestation`, `AdoptCheckpoint`, опционально `LatestCheckpoint`),
вызываемых из JS через `syscall/js`; JSON-кодирование результата —
на стороне JS-обёртки. Никаких P2P-зависимостей: проба
`reports/verifier-wasm-probe/` подтверждает, что verify-контур ядра
собирается под GOOS=js GOARCH=wasm как есть.

## 4. Форматы входа/выхода

### 4.1. Предъявление

Состав — раздел 6.1 (подпись кошелька над утверждением: `network_id`,
адрес, статус, возраст, глубина графа поручительств, метка `flagged`,
хеш манифеста, эпоха чекпоинта, `challenge` проверяющего, срок годности,
`app_id`) + открытый ключ кошелька + Merkle-доказательство состояния
кошелька из финализированного чекпоинта.

Два представления, оба уже определены ядром (верификатор новых форматов
не изобретает):

1. **Каноническое (подписываемое)** — `wire.AttestStatement`:
   protobuf-подобная каноническая кодировка spec/01 (поля 1–11),
   `Hash() = SHA-256(canonical(...))`; подпись — ECDSA P-256 DER над
   этим хешем (в headless-ядре; на живом устройстве — по `signing_auth`
   сети, ключ в Android Keystore наружу не выходит — этап 6).
2. **Транспортное** — JSON (`present.Presentation`: `statement`,
   `public_key`, `signature`, `leaf`, `siblings`) для передачи
   «кошелёк → проверяющий» напрямую; эталонное сообщение
   `proto/attest.proto Attestation` (statement + signature + proof +
   checkpoint одним сообщением) — для межплатформенного обмена.

Проектное решение для фасада: **вход `VerifyAttestation` — байты
транспортного кодирования** (JSON `present.Encode` либо canonical
`Attestation`; при реализации фиксируется один формат, второй —
опциональным приёмником). Чекпоинт передаётся внутри сообщения
(`Attestation.checkpoint`, поле 13) или отдельным аргументом — при
реализации фиксируется одно; в JSON-представлении чекпоинт передаётся
отдельно (проверяющий обычно держит уже принятый через LightSync).

### 4.2. Чекпоинт

`wire.Checkpoint` (spec/07 7.1): `network_id`, `epoch`, `state_root`,
`prev_checkpoint_hash`, `network_time`, `protocol_version`,
`active_wallets`, `total_supply`, `participants`, `threshold`,
`threshold_sig` (N-из-M ECDSA P-256), `finalized_tx_ids`.
`checkpoint_hash = SHA-256(canonical(Checkpoint без threshold_sig))`.
Проверяется: принадлежность сети, соответствие эпохе утверждения,
пороговая подпись (`threshold.Verify` против `PubSource`), при
использовании LightSync — ещё цепочка `prev_hash`, возраст эпох и окно
времени (`cons.Verify`).

### 4.3. Merkle-доказательство

Sparse Merkle-дерево состояния (`core/smt`): индекс листа — адрес
кошелька (32 байта), лист — `wire.StateLeaf` (9 полей, решение D7,
spec/07 7.1.1: seq, balance, status, flags, registered/activated epoch,
last_claimed_period, delayed_threshold, threshold_change_epoch),
соседи пути — по 32 байта. Проверка: `smt.VerifyProof(idx, leafHash,
siblings, root)` против `checkpoint.state_root`; затем сверка полей
утверждения с листом (статус, `flagged`), `VerifyAgeBound` — верхняя
оценка возраста (возраст не может превышать время от регистрации
до эпохи чекпоинта).

### 4.4. Выход

`VerifyResult` (раздел 3.1): `app_identity` (32 байта, вычисляется
проверяющей стороной — не передаётся), проверенные `statement` и `leaf`,
верхняя оценка возраста. Проверяющий **сам** применяет пороги (возраст,
глубина, уровень гарантий по хешу манифеста, статус) — протокол вердиктов
не выносит (6.1).

## 5. Модель ошибок

Существующий `present.Verify` возвращает нетипизированные ошибки
(строки). Для внешнего потребителя фасад разворачивает их в
**типизированные коды** — по образцу стабильных кодов `E_*` ядра
(spec/00), но в отдельном пространстве имён верификатора (проект —
`V_*`, чтобы не пересекаться с кодами транзакций):

| Код | Условие |
| --- | --- |
| `V_DECODE` | предъявление не разбирается (неполное/битое) |
| `V_NET` | `network_id` предъявления или чекпоинта ≠ ожидаемого |
| `V_MANIFEST` | хеш манифеста не сходится (3.3) |
| `V_CHALLENGE` | `challenge` пуст или не совпадает (повторное использование, 6.1) |
| `V_EXPIRED` | срок годности истёк (`now ≥ expires_at`) |
| `V_KEY` | ключ кошелька не разбирается / адрес не соответствует ключу |
| `V_SIG` | подпись кошелька неверна |
| `V_NO_CHECKPOINT` | чекпоинт отсутствует / без пороговой подписи / чужая эпоха |
| `V_THRESHOLD` | пороговая подпись чекпоинта не достигнута |
| `V_PROOF` | Merkle-доказательство не сходится с корнем чекпоинта |
| `V_LEAF` | утверждение не соответствует листу (статус, flagged) |

Модель: `type VerifyError struct { Code string; Detail string }`,
реализует `error`; все коды стабильны и попадают в golden-векторы
(раздел 6). `Detail` — человекочитаемый, нестабильный. Порядок проверок:
дешёвые и однозначные раньше дорогих (decode → сеть/манифест/challenge/
срок → ключ/подпись кошелька → чекпоинт/порог → Merkle) — чтобы
мусорный ввод отсекался до криптографии (тот же принцип, что net-DoS A3
для транзакций).

## 6. Тестирование: те же golden-векторы, что у ядра

Решение 11.11: тесты верификатора — на **те же golden-векторы**
(`vectors/`), что у ядра. Каталог `vectors/` (формат `tnp-vector-1`,
spec/03, spec/05) сейчас покрывает транзакции; предъявления — сообщения
вне реестра (`proto/attest.proto`), поэтому проект — **расширение того
же каталога и формата** векторами attest, без второго формата:

- `valid_attest.json` — полный счастливый путь: сеть genesis → транзакции
  до активации → чекпоинт (пороговая подпись) → предъявление → ожидаемый
  `accept` + производные (`app_identity`, `age_bound`);
- негативные `bad_attest_*.json` — по одному на каждый код `V_*`
  (чужая сеть, чужой манифест, повторный challenge, истёкший срок,
  подменённый ключ/адрес, неверная подпись кошелька, чекпоинт без
  порога, порванный Merkle-путь, расхождение листа);
- материализация криптополей — той же эталонной реализацией ядра
  (плейсхолдеры `SIG_PLACEHOLDER` / `txid:WALLET:seq` — по правилам
  `vectors/README.md`), поэтому векторы **одни и те же** для ядра
  (сборка предъявления) и верификатора (проверка): oracle-тест гоняет
  вектор через `present.Build` и через `VerifyAttestation` и требует
  зеркального совпадения.

Такой векторный файл — кандидат в `vectors/` при реализации; сейчас
(бумажная стадия) он только спроектирован.

## 7. Сборки

| Цель | Инструмент | Заметки |
| --- | --- | --- |
| JVM/Android (AAR) | `gomobile bind` | тот же конвейер, что `mobile/` (этап 6); ожидание — без `-checklinkname=0` (нет `net/` в графе; прецедент 01.11 — флаг нужен из-за `wlynxg/anet`, в верификатор не входит); проверяется при реализации |
| JS/WASM | `GOOS=js GOARCH=wasm go build` | проба `reports/verifier-wasm-probe/`: verify-контур ядра собирается под js/wasm как есть; P2P-пакеты в сферу пробы не входят (по мандату) |
| Нативный Go | импорт go-модуля | основной путь для серверных потребителей |

Размерные ориентиры: AAR ядра с P2P — ~103,6 МБ (reports/stage6);
верификатор без P2P ожидается кратно меньше — замеры и решение по
размеру — после 8-live (см. пометку о нестабильности).

## 8. Вне области проектирования

- P2P-синхронизация и полный узел (LightSync работает с любым узлом,
  серверы проекта не нужны — 6.1);
- вердикты и политика проверяющего (пороги возраста/глубины/гарантий) —
  решает потребитель (6.1);
- ZK-доказательства членства (тайные голосования — позже, 6.1);
- отзыв аттестации (CRL/OCSP) — отложен для v1 (№43, stage9-decisions);
- изменение текстов лицензий и спеки (не входит в мандат).
