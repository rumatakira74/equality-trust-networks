# Дизайн слияния сетей (network merge) — предложение Vibe для аудита

Дата: 1 ноября 2026 г. Статус: 🆕 дизайн, не принят; передан на аудит. Автор: Vibe (по заказу владельца). Основание: пункт «Этап 13. Совместимость сетей и слияние» плана разработки. Спека-эталон: docs/KNOWLEDGE v9.11. Документ — материал для аудита и решения владельца, не часть спеки.

## 0. Сценарий и требования владельца

Два подразделения одного облачного оператора независимо развернули сети платформы, затем решили объединиться. На платформе два вида сетей по семантике остатка: **с переходящим остатком** (единицы живут между периодами) и **без него** (право/единица сгорает на границе периода). Требования: сети одного типа должны быть объединяемы; сети разных типов не должны пересекаться.

Что уже даёт протокол v9.11: `network_id = H(manifest ‖ genesis)` (само-сертификация, нельзя застолбить/подделать); `address = SHA-256(fingerprint ‖ network_id)` — единая точка деривации адреса, fingerprint — стабильная межсетевая идентичность устройства; финализированные чекпоинты с корнями состояния (state roots) — готовый якорь для снапшотов; signal-механика изменения параметров (раздел 13) — прецедент ратификации без администратора; закрытый перечень типов транзакций уже расширялся прецедентом (`update_guardians`).

## 1. Тип сети для слияния

`type(network) = (семантика остатка; вид единицы; привязка ресурса)`:

- **семантика остатка:** `persistent` (периодическое право накапливается: `periodic_equal` + `accrual_window`, остаток переносится, демередж/комиссия не «сгорание» — профили 1/2/5/6/7) | `reset` (право сгорает на границе периода: `quota_reset`, `voucher`, recurring профиля №8 — сгорание E_BURNED на границе P+1 или сбросом в конце периода);
- **вид единицы:** `currency | hours | quota(resource_id) | points | voucher(program_id) | heartbeat`;
- **привязка ресурса:** конкретный `resource_id`/`program_id` для квот и ваучеров.

Тип — инвариант слияния: результат слияния имеет тот же тип, что источники; цепочка merge'ей сохраняет тип, поэтому разные типы не пересекаются **транзитивно и навсегда**. Мостов между сетями нет по определению (раздел 3.1 спеки: мосты вне v1), обмен между разными типами не появляется и через слияние.

## 2. Ключевой принцип: слияние = новая сеть, а не правка старых

Из `network_id = H(manifest ‖ genesis)` и неизменности манифеста следует: изменить A или B «на месте» нельзя. **Слияние — запуск сети C с merge-genesis.** Философски это продолжение раздела 13: «если правила перестали подходить — запускается новая сеть, участники переходят добровольно». Никаких ролей и администраторов не появляется: валидность слияния проверяют узлы, согласие выражают участники.

`network_id` C = `H(manifest_C ‖ genesis_C)` как у всех сетей; `manifest_C` включает поле `merged_from` — список `(network_id_A, terminal_checkpoint_A)`, `(network_id_B, terminal_checkpoint_B)`.

## 3. Протокол слияния по шагам

1. **Подготовка манифеста C.** Любой участник (или конфигуратор) собирает манифест C: тип = тип A = тип B; параметры — предложение к ратификации; защитные параметры (`device_policy`, `signing_auth`, `checkpoint_mode`, K, D, `transfer_mode`, размер и режим эмиссии) — **не слабее любой из сетей-источников** (протокольная проверка, не конвенция); остальное (ставки демереджа/комиссии в границах допустимого) — на ратификацию. Посевной круг в C не задаётся: все импортированные `active`; `seed_sunset` не нужен.
2. **Ратификация.** Участники A публикуют signal-транзакции `merge_signal{H(manifest_C), target_epoch}`, подписанные по правилам сети; участники B — симметрично. Порог в каждой сети ≥ 2/3 `active` (по образцу `members_quorum`), окно сбора — параметр (предложение ~30 дней). Сигналы публичны, считаются из реестра, узлы включают их в журнал как обычные tx закрытого перечня (новый тип — расширение перечня явным решением, прецедент `update_guardians`). Ратификация не собралась в любой из сетей → слияние отменяется, сети живут дальше.
3. **Снапшот.** Целевая эпоха E выбирается так, чтобы терминальный чекпоинт попадал на границу периода (для `reset`-сетей — обязательно; для `persistent` — желательно). Последний финализированный чекпоинт A эпохи E становится **терминальным**: он несёт обычное state root плюс merge-поле `(H(manifest_C), network_id_C после вывода)`. Собор подписей — по действующему `checkpoint_mode` сети A. Терминальный чекпоинт не собрался (офлайн-подписанты, атака) → слияние отменяется по таймауту, сети продолжают жить.
4. **Halt-правило.** Узел A, увидев валидный терминальный чекпоинт, переходит в терминальное состояние: не принимает и не публикует новые tx, продолжает раздавать журнал и терминальный чекпоинт, предлагает миграцию в C. Это «самоубийство по консенсусу» — правило проверяют сами узлы, внешнего принуждения нет.
5. **Импорт.** Genesis C содержит `(network_id_A, terminal_checkpoint_A)` и `(network_id_B, terminal_checkpoint_B)`. Таблица импорта `(fingerprint, старый адрес, состояние)` **не хранится в genesis** — она выводима детерминированным replay журналов A и B любым узлом (терминальные чекпоинты — якоря: импорт обязан дать в точности их state roots; расхождение = невалидный genesis C). В C адрес = `SHA-256(fingerprint ‖ network_id_C)`; кошелёк, состоявший в обеих сетях, получает один адрес (дедупликация по fingerprint).
6. **Старт C.** Своя эпоха и календарь периодов от genesis C; чекпоинт-кворум — объединённое множество `active`; демередж/комиссия C действуют с момента genesis C (неретроактивно). Приложение участника переключается: та же ключевая пара Keystore, новый адрес вычисляется локально (`fingerprint ‖ network_id_C`), приватный ключ не покидает устройство, повторная регистрация и повторная аттестация не нужны — членство уже в genesis C.

## 4. Импорт состояния

| Что | persistent | reset |
| --- | --- |
| Балансы | суммируются по fingerprint на снапшоте | не переносятся (квоты сгорели на границе; право даётся правилами C с нуля) |
| Статус `active` | сохраняется | сохраняется |
| Возраст | от более ранней `register` при двойном членстве | то же |
| Граф поручительств | объединение рёбер; слоты пересчитываются по календарю C от импортированных дат | то же |
| `flagged` | переносится (постоянная, доказательная метка) | то же |
| Цепочка кошелька | `seq` продолжается (последний seq + 1), `prev` = txid последней tx по терминальному чекпоинту — защита от эквивокации не сбрасывается | то же |
| Незавершённые отложенные переводы (D=48 ч) | отменяются с возвратом отправителю до снапшота (детерминированно, replay-безопасно) | не применяются (квоты не подпадают под отложенные переводы) |
| Пулы (`pool`), незакрытые сборы | возвращаются донатам (refund) до снапшота; перенос пулов между сетями вне v1 | то же |

## 5. Офлайн-узлы и терминальный чекпоинт

Halt — не флаг, а **терминальный чекпоинт**: вернувшийся онлайн узел A досинхронизирует журнал, видит терминальный чекпоинт, переходит в терминальное состояние (история + предложение миграции в C). Двойной траты у офлайн-узла нет: его tx после терминального чекпоинта никто не подтвердит (нет кворума), чужую tx за границей он сам не примет (правило halt). История A остаётся верифицируемой навсегда через state root терминального чекпоинта, записанный в genesis C.

## 6. Предъявления `attest` после слияния

Действующие предъявления из A остаются криптографически валидны до своего срока годности (подпись кошелька + Merkle-доказательство из финализированного чекпоинта A), но сеть A мертва: лёгкий клиент не найдёт пиров для сверки, а уровень гарантий привязан к манифесту A. Правило: верификатор обязан показывать «сеть A (слита в C, эпоха E)»; новые предъявления выдаёт только C. Протокол ничего не обещает после смерти сети — «решает проверяющий» (раздел 6.1 спеки) сохраняется.

## 7. Ограничение v1: попарные слияния

Слияние ровно двух сетей за раз. Объединение N сетей — цепочкой попарных merge'ей (A+B → AB, затем AB+C). Основание: координация целевых эпох и комбинаторика ратификации для N≥3 не дают операционной выгоды, а стоимость реализации и тестирования заметна; тип сохраняется транзитивно, так что попарные слияния покрывают сценарий целиком.

## 8. Атаки и защиты

1. **Двойная трата через «воскрешение» A.** Атакующий держит узел A живым и тратит остаток там и в C. Защита: halt по терминальному чекпоинту; tx после него не подтверждает ни один узел A; в C балансы уже зафиксированы снапшотом.
2. **Merge-инфляция (сибилла через слияние).** Ферма растит сеть B (10k «активных») и сливает её с честной A. Защиты: (а) ратификация в **каждой** сети — ферма не контролирует честную A, её участники видят публичную статистику B перед сигналом (размер, распределение возрастов, плотность графа поручительств — «репутация без вердиктов»); (б) протокольный запрет ослабления защитных параметров в C; (в) возраст и граф импортируются честно — слияние не «отмывает» молодость.
3. **Гонка слияний** (A+B и A+D одновременно). Побеждает merge, чей терминальный чекпоинт финализирован в A первым; A останавливается один раз; проигравший commitment никогда не станет терминальным (его `target_epoch` уже занята).
4. **Подделка ратификации.** Сигналы подписаны `active`-кошельками и включены в журнал; подсчёт — детерминированный replay. Дублирующиеся сигналы (один кошелёк — много сигналов) считаются один раз по адресу; эквивокация сигналов ловится общими правилами (один `seq`).
5. **Replay merge-commitment между сетями.** Все подписи несут `network_id` (спека v9.11); терминальный чекпоинт валиден только внутри A; genesis C уникален своей парой источников.
6. **DoS через отмену слияния.** Умышленный отказ подписантов от терминального чекпоинта — слияние просто отменяется (таймаут), сети живут; стоимость — время участников, не состояние сети.

## 9. Что НЕ входит

Мосты и обмен между сетями; слияние сетей разных типов (протокольно невалидно); слияние N≥3 за один merge; перенос пулов; «мокрые» слияния с правкой живых сетей; глобальная сеть `global` как участник слияния (она зарезервирована и единственна по определению).

## 10. Зависимости и порядок

- **Детерминизм replay — предусловие.** Импорт выводится replay'ем журналов; текущая находка live/replay у границы периода (FINDING-replay-live-divergence, фикс времени txNow) должна быть закрыта **до** реализации слияния — иначе таблица импорта недетерминирована. Слияние ставится в плане после этапа фикса времени.
- Реализация = расширение закрытого перечня tx (`merge_signal`), merge-поле чекпоинта, валидация merge-genesis, halt в слое net, UI миграции; `protocolVersion` +1. Оценка объёма — после аудита и решения владельца.

## 11. Открытые решения за владельцем

1. Порог и окно ратификации (предложение: ≥2/3 `active`, окно ~30 дней, таймаут-отмена).
2. Судьба незавершённых отложенных переводов (предложение: refund до снапшота).
3. Разрешить ли разные значения не-защищённых параметров у источников (эмиссия 1000 vs 1200) при равном типе (предложение: да, через ратификацию манифеста C; альтернатива: только идентичные профили).
4. Счётчик выпусков для награды поручителям R (предложение: обнуляется в C — все начинают с первого выпуска; альтернатива: перенос счётчика при двойном членстве).

## 12. Вопросы для аудита

1. Soundness halt-правила: существует ли путь, при котором tx после терминального чекпоинта подтверждается (сговор подписантов, форк чекпоинт-цепочки, ре-орг финальности)?
2. Терминальный чекпоинт: достаточна ли защита существующих режимов (`decentralized` N-из-M, `members_quorum` 2/3) против «нарисованного» чекпоинта с merge-полем?
3. Ратификация: корректен ли подсчёт порога из журнала; возможен ли двойной счёт, устаревшие сигналы (сигнал отозван/кошелёк `flagged` после сигнала), race между сигналом и `target_epoch`?
4. Импорт: полнота и детерминизм вывода таблицы импорта из журналов; поведение при расхождении с state root терминального чекпоинта; продолжение `seq`/`prev` — есть ли крайние случаи (кошелёк с незафиксированной в чекпоинте tx)?
5. Типы: достаточно ли определения типа (остаток + единица + ресурс), чтобы исключить слияния с разной экономикой (демередж vs нет, `free` vs `restricted`)? Нужно ли включать `transfer_mode` в тип?
6. `flagged` и `evidence`: перенос метки корректен; переносится ли приостановка выпуска (№12) и её таймер?
7. Merge-инфляция: оцените протокольную часть защиты (запрет ослабления) — какие параметры упущены в списке «не слабее»?
8. Предъявления после слияния: риски «мёртвой» сети для внешних потребителей; нужно ли ограничить срок годности предъявлений при терминальном чекпоинте?
9. `reset`-слияния: корректно ли «право не переносится» при переносе статуса `active` и графа; создаёт ли это арбитраж (активироваться в B перед слиянием)?
10. Гонки слияний и два конкурирующих манифеста C: достаточно ли «первый финализированный побеждает»?
