## 0. Контекст и задача

Исходные положения спеки v9.11:

- сети-инстансы изолированы, обмен между сетями отсутствует, мосты вне v1 (раздел 3.1);
- `network_id = H(manifest ‖ genesis)` — само-сертифицирующийся, манифест неизменен после запуска (3.3, 13);
- `address = SHA-256(fingerprint ‖ network_id)` (7.2) — адрес выводится от финального network_id;
- финальность: чекпоинты эпох, подписанные пороговой подписью, state root — sparse Merkle (9.1, 12.5);
- изменяемые параметры — только через сигнализацию участников в границах genesis (13).

Сценарий: два подразделения одного облачного оператора независимо развернули сети одного профиля и решили объединить. Требования владельца: (1) сети одного типа должны быть объединяемы; (2) сети разных типов не должны пересекаться. Два вида сетей: **с переходящим остатком** (баланс/право живёт между периодами) и **без него** (право сгорает в конце периода).

## 1. Ключевой принцип: слияние = новая сеть, а не правка старых

Из неизменности манифеста и само-сертификации `network_id` следует: объединить A и B «на месте» нельзя. **Слияние — запуск сети C с merge-genesis**, который содержит манифест C, манифесты A и B, терминальные чекпоинты A и B (state roots + merge-commitment) и таблицу импорта. A и B после слияния терминальны (раздел 3). Это прямое продолжение принципа спеки: «если правила перестали подходить — запускается новая сеть, участники переходят добровольно» (13). Право форка сохраняется: любой участник может продолжить A на прежних правилах — но это форк мёртвой сети, C его не признаёт (3.2).

## 2. Механика по шагам

### Шаг 1. Ратификация без администратора

Участники A и B публикуют в своих цепочках signal-транзакции `merge_signal{хеш манифеста C, целевая эпоха}` — механика как сигнализация изменяемых параметров (13). Черновые параметры: порог **≥2/3 `active`** в каждой сети, окно 30 дней; сигналы публичны и входят в state root. Оба порога достигнуты → слияние назначается на согласованную целевую эпоху; хотя бы один нет → слияние не происходит, сигналы истекают с окном, сети живут дальше.

### Шаг 2. Терминальный чекпоинт (halt) — вместо «флага остановки»

Последний финализированный чекпоинт A на целевой эпохе дополняется **merge-полем**: `{network_id_C, genesis_hash_C, подтверждение порога ратификации}`. Это и есть остановка сети: следующий чекпоинт никогда не соберёт кворум подписантов, потому что валидные узлы перешли в терминальное состояние. Преимущества перед отдельным «правилом остановки»:

- **офлайн-узлы безопасны**: узел A, вернувшийся после слияния, синхронизирует журнал, видит терминальный чекпоинт и переходит в режим «только чтение + предложить миграцию в C»; транзакции после терминального чекпоинта он не публикует и не принимает;
- **двойной траты нет даже у офлайн-узла**: его tx после границы никто не подтвердит (нет quorum), а чужую tx он не примет — граница детерминирована номером эпохи, не локальными часами;
- переиспользуется существующая финальность чекпоинтов — новый механизм консенсуса не вводится.

Genesis C встаёт на терминальные чекпоинты A и B. Полная история A и B остаётся верифицируемой: старая транзакция проверяется через state root её терминального чекпоинта; журналы A и B целиком в C не копируются.

### Шаг 3. Импорт идентичности по fingerprint

В C адреса пересчитываются от `network_id` C. Таблица импорта `(fingerprint, адрес в A/B, состояние)` выводима из публичных журналов A и B и включается в genesis C (в виде commitments; полный список верифицируется replay-ом журналов). Человек, состоявший в обеих сетях, получает **один** кошелёк в C: межсетевая идентичность — это fingerprint (7.2), а не адрес. Дедупликация сибиллы бесплатна: N членств = 1 кошелёк.

### Шаг 4. Импорт состояния

| Объект | Перенос в C | Правило |
| --- | --- | --- |
| Балансы (persistent) | да | сумма по fingerprint |
| Право периода (reset) | членство | одна квота на человека в первом периоде C, не суммируется |
| Статус | да | `active` побеждает `registered`; `expired` не переносится (нужна новая регистрация) |
| Возраст | да | от более ранней `register` при двойном членстве |
| Граф поручительств | да | объединение рёбер, слоты пересчитываются по правилам C |
| Метка `flagged` | да | постоянная доказательная метка, публичная история сохраняется |
| Отложенные переводы (D = 48 ч) | нет | отмена с возвратом отправителю — детерминированно и replay-безопасно (предложение; альтернатива — не принимать новые за 48 ч до целевой эпохи) |
| История A и B | внешне | проверяется через терминальные чекпоинты, в C не копируется |
| Посевные круги A и B | нет | все импортированные уже `active`; quorum чекпоинтов C = импортированное активное множество, `seed_sunset` не нужен |
| Демередж/комиссия C | с genesis C | на импортированные балансы действует с момента genesis C — неретроактивно (3.2) |
| Счётчик выпусков для награды R | обнуление | в C все начинают с первого выпуска (предложение) |
| Мораторий/возрастные пороги | да | сохраняются по исходным датам |

### Шаг 5. Старт C

Своя эпоха и календарь периодов от genesis C; манифест C ратифицирован обеими сетями (шаг 1); PoW, чекпоинты, комиссии — по манифесту C.

## 3. Правило типов — протокольное, не конвенциальное

Тип сети для слияния = **семантика остатка** + привязка единицы:

- `persistent` — периодическое право накапливается, остаток живёт между периодами (`periodic_equal` + `accrual_window`; профили 1/2/5/6/7);
- `reset` — право сгорает в конце периода (`quota_reset`, ваучеры с дедлайном, профиль №8 recurring);
- плюс `unit` и привязка `resource_id`/`program_id` (две квотные сети разных ресурсов — разные типы).

Узел проверяет типы при валидации merge-genesis: **merge валиден ⇔ типы равны**. `sandbox` никогда не сливается ни с чем. Следствия: разные типы не пересекаются транзитивно и навсегда (тип — инвариант слияния, цепочка merge'ей его сохраняет); мостов между типами нет по определению. Право должно быть записано в спеке как проверка каждым узлом — иначе «не должны пересекаться» остаётся пожеланием.

Для **reset-сетей** слияние проще и безопаснее: переносится только членство, двойной траты накопленного нет; терминальный чекпоинт всё равно нужен (иначе сгоревшие права можно «продлить» продолжением A). Для **persistent** он критичен.

## 4. Защиты от злоупотреблений

- **Двойная трата** — терминальный чекпоинт (раздел 2, шаг 2): tx после границы A не получает подтверждения ни в A (нет quorum), ни в C (незнакомая сеть — E_NET, replay-изоляция подтверждена мини-тестнетом 6/6 направлений).
- **Merge-инфляция** (ферма растит сеть B из 10k «активных» и сливает её с честной A). Протокольный запрет: **манифест C не может иметь защитные параметры слабее любой из сетей-источников** (`device_policy`, `signing_auth`, `checkpoint_mode`, K, D, правила поручительств). Социальный слой: перед ратификацией UI показывает статистику второй сети — размер, распределение возрастов, плотность графа поручительств; «репутация без вердиктов», каждый решает сигналом. Дополнительно к обсуждению: минимальный возраст сети-источника (например, 3 периода) как барьер «свежих ферм под слияние».
- **Гонка слияний** (A+B и A+D одновременно): побеждает тот merge, чей merge-commitment попал в терминальный чекпоинт A первым; A останавливается один раз; проигравший commitment не валидируется (его целевая эпоха уже прошла).
- **Несимметричная ратификация**: quorum в A достигнут, в B нет — терминального чекпоинта нет ни у одной, сети живут.

## 5. Предъявления `attest` после слияния

У сторонних потребителей могут быть действующие предъявления из A/B (срок годности, `challenge`). После слияния: подпись и Merkle-доказательство остаются криптографически валидны (терминальный чекпоинт финализирован навсегда), но сеть мертва — лёгкий клиент не найдёт пиров для живой сверки. Предложение: предъявления A/B действуют до своего срока годности, но верификатор обязан показывать «сеть A (слита в C, эпоха N)». Для свежих проверок потребитель миграцию не нужен — адрес в C выводится из fingerprint, предъявление из C несёт манифест C. Протокол после смерти сети ничего не гарантирует — и не должен.

## 6. Слияние более двух сетей

v1 — **только попарно**. Слияние N сетей за раз упирается в координацию целевых эпох и комбинаторику ратификации, а операционно эквивалентно цепочке попарных слияний (A+B → AB, затем AB+C). Цепочка уже даёт «объединение N сетей», тип сохраняется транзитивно, каждая пара проходит полный цикл защит. Если попарное ограничение закрепить в спеке, рекурсивные слияния специфицировать отдельно не нужно.

## 8. Вопросы для аудита

1. **Звучность halt (терминального чекпоинта):** возможна ли двойная трата или «продление» сгоревших прав при сговоре доли подписантов A, продолжающих сеть после целевой эпохи? Поведение при split-brain A ровно на целевой эпохе (две финальные ветки, обе «последние»)?
2. **Dedup по fingerprint:** конфликтные случаи двойного членства (active в A + registered в B; разные возрасты; `flagged` в одной); fingerprint, попавший в чёрный список миграции кошелька.
3. **Порог ратификации:** 2/3 против 1/2; атаки через покупные сигналы; что именно защищает порог в reset-сетях (балансов нет — защищать только состав).
4. **Merge-инфляция:** достаточен ли запрет ослабления защитных параметров + ратификация; нужен ли минимальный возраст сети-источника; экономика «ферма под слияние» с учётом того, что B должна пройти ратификацию в A.
5. **Детерминизм сеттлемента C:** взаимодействие с фиксом txNow (этап фикса времени) — сеттлемент C от genesis C, порядок AcceptedTxs при импорте сумм балансов, демередж первого периода.
6. **Отложенные переводы:** отмена с возвратом против «не принимать новые за 48 ч до целевой эпохи»; что видит получатель, чей перевод отменён.
7. **`attest` после смерти сети:** корректность срока годности без живых пиров; что должна показывать верифицирующая библиотека.
8. **N-way vs попарно:** подтверждение, что попарного ограничения достаточно и не создаёт невыгодных паттернов (например, «спираль слияний» оператора из k сетей).
9. **Quorum чекпоинтов C = импортированное активное множество:** риски сразу после старта (первая эпоха C, когда часть участников офлайн); уместен ли переходный режим подписантов по образцу посевного круга и его закат.
10. **Гонки и отказа среды:** конкурирующие манифесты C (два несовместимых предложения с разными параметрами) при равном типе — правила выбора; частичная ратификация и истечение окна.

## 9. Открытые решения за владельцем (черновые предложения — в скобках)

1. Порог и окно ратификации (≥2/3 `active`, 30 дней).
2. Судьба незавершённых отложенных переводов (отмена с возвратом).
3. Разрешение разных не-защищённых параметров при равном типе (да, через ратификацию манифеста C обеими сетями; альтернатива v1 — только идентичные профили).
4. Счётчик выпусков для награды R (обнуляется).
5. Минимальный возраст сети-источника (обсуждение после аудита).
6. Участие `global`-сети в слияниях (v1 — не участвует: глобальная сеть одна по определению).
