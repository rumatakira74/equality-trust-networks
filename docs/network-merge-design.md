## 1. Сценарий и требования

Требования владельца (01.11.2026):

1. Два подразделения одной организации (пример: облачный оператор) развернули независимые сети; затем решили объединить.
2. Платформа различает два вида сетей: **с переходящим остатком** и **без него**.
3. Сети одного вида должны быть объединяемы.
4. Сети разных видов не должны пересекаться — не объединяются и не обмениваются, транзитивно и навсегда.

Опора: спека 3.1 («между сетями нет обмена, мосты вне v1»), 13 (без администратора, неизменность манифеста, право форка, сигнализация параметров), 9.1 (цепочки, голосование, чекпоинты, финальность), 7.2 (fingerprint, деривация адреса v9.11), 7.5 (flagged), 8.3 (отложенные переводы), 6.1 (attest/verifier).

**Отличие от моста.** Мост — постоянный обмен между живыми сетями; слияние — **однократный переход с остановкой сетей-источников**. Мосты остаются вне v1 без изменений.

## 2. Определения

- **Persistent-сеть** — периодическое право накапливается, остаток живёт между периодами (`periodic_equal`, `accrual_window` > 0; профили 1/2/5/6/7 по разделу 5).
- **Reset-сеть** — право сгорает на границе периода (`quota_reset`, ваучеры с дедлайном, профиль №8 «Абонентский ресурс» recurring).
- **Тип сети** T = {остаток: `persistent`|`reset`; `unit`; привязка `resource_id`/`program_id`; `sandbox`} — вычислим из манифеста детерминированно.
- **Терминальный чекпоинт** сети A — финализированный чекпоинт A, расширенный merge-полем (§6.3); после него A не принимает транзакции.
- **Merge-genesis** — genesis сети C: манифест C + список родителей (для каждой сети-источника: `network_id`, манифест, хеш терминального чекпоинта) + корень таблицы импорта.
- **Merge-commitment** — содержимое merge-поля терминального чекпоинта: {`network_id_C`, `genesis_hash_C`, `signal_root`, `merge_epoch`}.

## 3. Инвариант: слияние = новая сеть, а не правка старых

`network_id = H(manifest ‖ genesis)` (3.1) и неизменность манифеста после запуска (13) означают: объединить A и B «на месте» нельзя без подмены идентичности. Поэтому **слияние — запуск сети C**, а A и B останавливаются по собственным правилам узлов, без внешнего принуждения. Это продолжение философии 13: «если правила перестали подходить — запускается новая сеть, участники переходят добровольно». Право форка сохраняется: несогласное меньшинство может продолжить A на прежних правилах — но после терминального чекпоинта не соберёт quorum для новых финализаций (обычная механика консенсуса 9.1, ничего нового).

## 4. Правило типов — протокольное

**Merge валиден ⇔ T(A) = T(B) = T(C).** Проверка каждым узлом при валидации merge-genesis и merge-signal. Следствия:

- разные виды не пересекаются **транзитивно**: тип — инвариант цепочки слияний (C наследует тип родителей, дальнейшие слияния C — только с тем же типом);
- `sandbox` никогда не сливается с не-`sandbox` (учебный уровень гарантий не смешивается с рабочими сетями — 3.3);
- мосты между видами исключены по построению (вне v1 + тип запрещает и будущий обмен между persistent и reset).

Дополнительное протокольное ограничение: **защитные параметры C** (`device_policy`, `signing_auth`, `checkpoint_mode`, K, D = 48 ч, `transfer_mode`, размер и режим эмиссии — перечень 13) **не слабее, чем у каждой из сетей-источников**. Не-защищённые параметры могут отличаться от A и B: манифест C ратифицируется участниками обеих сетей до слияния (§6.1) — гарантии ни одного участника не ослабляются молча.

## 5. Переносимое состояние (по видам сетей)

| Что переносится | persistent | reset |
| --- | --- | --- |
| Баланс / квота | суммируется по fingerprint при двойном членстве | одна квота на человека (не суммируется) |
| Статус `active`/`registered` | переносится | переносится |
| Возраст кошелька | от более ранней `register` при двойном членстве | так же |
| Граф поручительств | объединение рёбер; слоты пересчитываются | так же |
| Метка `flagged` | переносится (постоянная, доказательная — 7.5) | так же |
| История A и B | остаётся в A и B; проверяема через корень терминального чекпоинта в genesis C | так же |
| Незавершённые отложенные переводы (8.3) | предложение: отменяются с возвратом отправителя в терминальном чекпоинте (детерминированно, replay-безопасно) | не применяются |
| Счётчик выпусков для награды R (7.4) | предложение: обнуляется — открытое решение §11 | не применяются |
| PoW-история, посевной круг | не переносятся; в C посевного круга нет | так же |

**Импорт не создаёт новых регистраций.** В C нет ни одной новой `register`: таблица импорта выводится replay'ем журналов A и B любым узлом — значит, не требует новой аппаратной аттестации и не расширяет поверхность атаки на 7.2.

## 6. Механика

### 6.1 Ратификация (без администратора)

- Новый тип транзакции `merge_signal` {`network_id_C`, `genesis_hash_C`, `target_epoch`}: публикуется кошельками A и B; подпись по `signing_auth` сети; дедупликация — одна signal от кошелька.
- Порог: ≥2/3 `active`-кошельков каждой сети (по образцу `members_quorum` 2/3, раздел 13); окно сигнализации — открытое решение §11.
- UI перед подписью показывает статистику второй сети: размер, распределение возрастов, плотность графа поручительств, уровень гарантий манифеста (3.3), diff манифеста C от родного. «Репутация без вердиктов» — решение за участником.
- Оба порога должны быть достигнуты к `target_epoch`; иначе сигналы сгорают, сети живут дальше.

### 6.2 Снапшот

На `target_epoch` (или первой эпохе после достижения обоих порогов) в каждой сети строится терминальный чекпоинт обычным порядком.

### 6.3 Терминальный чекпоинт и остановка сети-источника

- Чекпоинт эпохи слияния расширяется merge-полем (merge-commitment, §2).
- Финализация — обычная (quorum подписантов сети, 9.1). После финализации узел сети A:
  1. не принимает и не публикует новые транзакции (детерминированный отказ из закрытого перечня E_*);
  2. продолжает раздавать журнал и историю (light-сервис);
  3. анонсирует `network_id_C` желающим перейти.
- **Офлайн-узел** на момент слияния: при возврате синхронизирует журнал, валидирует терминальный чекпоинт, переходит в то же состояние. Tx, подписанные офлайн после границы, не подтверждает никто (нет quorum выше терминальной высоты) — двойной траты нет.

### 6.4 Genesis C и его валидация каждым узлом

Узел, валидирующий C, проверяет:

1. типы равны (§4); защитные параметры C не слабее родителей;
2. терминальные чекпоинты родителей финализированы и подписаны их quorum;
3. signal-пороги достигнуты: signals проверяются по журналам родителей против `signal_root`;
4. таблица импорта выводится replay'ем журналов родителей до их терминальных чекпоинтов и совпадает с корнем в genesis C;
5. `network_id_C = H(manifest_C ‖ genesis_C)` — само-сертификация v9.11 без изменений.

### 6.5 Импорт идентичности

- `address_C = SHA-256(fingerprint ‖ network_id_C)` (7.2 v9.11): fingerprint переносим, адреса в C новые.
- Таблица импорта: (`network_id` родителя, старый адрес) → `address_C` с полным состоянием (балансы/квоты, статусы, возраст, рёбра поручительств, `flagged`).
- Двойное членство (один fingerprint в A и B) → **один** кошелёк в C; persistent — балансы суммируются; reset — квота одна. Дедупликация сибиллы при слиянии бесплатна.
- Fingerprint внутри каждой сети уникален по построению (7.2: один fingerprint = один адрес, повторная `register` с тем же fingerprint отвергается).

### 6.6 Старт C

- Эпохи/периоды C — от genesis C (новый календарь; якорь слота челленджа №39 — от genesis-времени C).
- Посевного круга нет: кворум чекпоинтов C = объединённое множество импортированных `active`.
- Демередж/комиссия C действуют на импортированные балансы с момента genesis C (неретроактивность — 3.2).

## 7. Предъявления attest после слияния (6.1)

- Подписи и Merkle-доказательства из A остаются криптографически проверяемыми навсегда: терминальный чекпоинт финализирован, история не переписывается.
- Свежих эпох у A больше нет: verifier показывает статус «сеть слита в C (терминальная эпоха N)» из merge-поля терминального чекпоинта.
- Протокол не гарантирует «живой реестр» остановленной сети — и не должен: достаточность предъявления решает проверяющий (6.1). Отдельных предписаний сторонним системам не вводится.

## 8. Ограничение v1: слияние ровно двух сетей

Merge-genesis допускает N ≥ 2 родителей, но v1 фиксирует **N = 2**: координация эпох и ратификация для N > 2 комбинаторно дороже, а цепочка попарных слияний (A+B → C, затем C+D → E) даёт тот же результат при том же типе (транзитивность §4). Рекурсивные слияния отдельно не специфицируются.

## 9. Атаки и защиты

| Атака | Защита |
| --- | --- |
| Двойная трата: потратить в A после снапшота и в C | терминальный чекпоинт: после финализации нет quorum для новых tx A; в C средства только из состояния на терминальном чекпоинте |
| Merge-инфляция: ферма растит сеть B из 10k «активных» и сливает её с честной A | (1) ратификация ≥2/3 в A со статистикой B в UI; (2) защитные параметры C не слабее; (3) правила A не меняются ретроактивно. Остаточный риск = обычный риск фермы (7.6) в большем масштабе — открытый вопрос аудита |
| Поддельный merge-commitment | подписывается quorum чекпоинтов A/B — стойкость равна стойкости чекпоинтов (9.1) |
| Гонка слияний A+B против A+D | терминальный чекпоинт один: первая финализация выигрывает; для второй не собрать quorum после остановки |
| Replay merge-механики на потомках | commitment ссылается на точный терминальный чекпоинт и `network_id_C`; другая ссылка = другой genesis = другая сеть |
| Sybil через импорт | новых `register` нет; таблица импорта = replay журналов; дедуп fingerprint; двойное членство → один кошелёк |
| Принуждение несогласного меньшинства | право форка (13): продолжение A возможно, но без quorum чекпоинтов не финализируется — та же механика, что при любом разделе сети (9.1) |
| Остановка честной сети злоумышленником | терминальный чекпоинт требует тот же quorum (2/3), что любой чекпоинт; сам merge-signal ничего не останавливает |

## 10. Изменения протокола (после утверждения)

1. Тип tx `merge_signal` — расширение закрытого перечня явным решением (прецедент `update_guardians`).
2. Merge-поле чекпоинта (checkpoint.proto + валидация).
3. Genesis-поля C: родители + корень таблицы импорта.
4. Валидация merge-genesis: типы, параметры, терминальные чекпоинты, signal-пороги, вывод таблицы импорта.
5. Правило остановки узла после терминального чекпоинта.
6. `protocolVersion` +1 — изменение валидации; живых сетей нет, миграцию не пишем (тестнеты пересоздаются genesis'ом).
7. Спека: новый раздел «Совместимость и слияние» + правки 13 (сигнализация), 6.1 (verifier), титул/changelog; RU+ENG.

## 12. Вопросы для аудита

1. Полнота перечня атак §9 — особенно: атаки на саму ратификацию (закупка signals, манипуляция весами голосующих), экономические атаки на persistent-слияние (инфляция предложения в момент слияния), атаки через выбор параметров манифеста C.
2. Достаточна ли связка «терминальный чекпоинт + genesis C» против всех форм replay и подмены (включая форк сети-родителя до слияния и повторное «оживление» журнала A)?
3. Согласованность с предстоящим фиксом времени (txNow = tx.TimestampClaim): вся merge-механика должна определяться от txNow/эпохи, а не от часов узла — где это может сломаться?
4. Конфликты с существующим кодом: genesis.proto, checkpoint.proto, cons/, core/ledger — какие инварианты и валидации затронет?
5. Импорт состояния: неучтённые зависимости возраста/графа/`flagged` (награды R, слоты поручителей, демередж на импортированных балансах, граница members_quorum при удвоении числа участников)?
6. attest/verifier: достаточно ли показывать статус «слита в C», или нужен формальный признак для сторонних систем?
7. Жизнеспособность ограничения «ровно две сети за раз» (§8) и достаточность дедупликации по fingerprint при слиянии сетей, где могла произойти миграция кошельков (раздел 11 спеки — старый ключ Terminal, fingerprint в чёрном списке).
