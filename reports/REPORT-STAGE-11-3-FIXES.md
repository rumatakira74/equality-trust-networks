## 1. PENDING №2 — settle отложенных операций после рестарта узла

**Было:** отложенная операция применялась только при живом
apply-триггере: replay из БД пинирует часы на timestamp_claim
(cons.Replay, №40), поэтому после рестарта зрелые переводы/смены
гардианов «зависали» до ближайшей транзакции (блокер 3 прогона 11.2 —
триггером была техническая register).

**Стало:**
- `Ledger.SettleNow()` (core/ledger/ledger.go) — публичное доведение
  сеттлемента до текущего времени источника: зрелые отложенные
  операции (переводы D, миграции, смены гардианов, порог P) применяются
  без транзакции-триггера; повторный вызов без эффекта
  (Executed/Effective).
- Узел (net/node.go): после завершения первичной сверки (syncLoop,
  полный узел) — `settleNow()` и далее периодический `settleLoop`
  каждые 30 с. До завершения первичной сверки settle НЕ запускается:
  пинированное применение истории должно оседать по историческим
  границам (демередж, №40) — settle «впереди» сверки ломал бы
  исторический демередж (поймано тестом
  TestStoreReplayConvergesWithColdSync, см. ниже).

**Тесты:**
- core/ledger/settle_now_test.go: TestSettleNowGuardianUpdateWithoutTrigger
  (незрелая смена ждёт, зрелая вступает по SettleNow без транзакции,
  повтор — без эффекта), TestSettleNowPendingTransferWithoutTrigger
  (то же для отложенного перевода).
- net/settle_restart_test.go: TestSettleAfterRestartMatured (рестарт
  узла из БД после зрелости — перевод применяется сам; повторный flush
  и повторный рестарт из той же БД баланс не меняют),
  TestSettleAfterRestartImmature (незрелая остаётся в ожидании).
- net/replay_restart_test.go (TestStoreReplayConvergesWithColdSync)
  сведён к сравнению после settle на всех трёх путях (store-replay /
  пинированное применение / холодная сверка): до правки settle-на-старте
  ломал исторический демередж холодной синхронизации (A=B≠C), после
  переноса settle за первичную сверку — все пути сходятся.

**Прогон (скриншоты 24–29):** публикация смены гардианов [V2] (PIN +
биометрия, хеш и подпись согласия — хелпер вне репо, ключом посевного
V2), сдвиг часов гостя на +49 ч (rootable-образ google_apis, adb root
date -s — способ прогона 11.2, вне кода), перезапуск узлов и
приложения: смена вступила в силу БЕЗ внешнего триггера — «использовано
1 из 150», текущий гардиан только V2, в истории «Took effect»
(29-guardians-settle-effect.png). В 11.2 этот шаг требовал живой
транзакции-триггера.

## 2. PENDING №3 — таймаут биометрии не вешает UI

отмена диалога биометрии — «Подпись не подтверждена», кнопка снова
активна. Widget-тесты: таймаут (мок платформы не отвечает —
_HangingSignFake) и отмена. Прогон: промпт биометрии → «Отмена» →
экран рабочий (30–31).

Замечание: таймаут BiometricPrompt — платформенный слой (BiometricGate,
отчёт 11.2); фикс на стороне экрана: UI не висит и восстанавливается.
Воспроизвести сам платформенный таймаут на эмуляторе детерминированно
нельзя — покрыто widget-тестом с моком.

## 3. PENDING №4 — History после рестарта

**Было:** WalletScreen запрашивал историю один раз в initState — до
завершения сверки узла после рестарта показывал «Nothing yet» и не
обновлялся.

**Стало:** экран подписан на AppState и перезапрашивает историю на
каждое уведомление (подъём/остановка узла, новый снапшот кошелька,
операция), с защитой от параллельных запросов. Тест
test/wallet_history_test.dart: пустая история → рестарт узла (снапшот
обновился) → записи появляются без перезахода на экран. Прогон:
после рестарта приложения/узла History показывает UPDATE_GUARDIANS и
регистрацию (26, 28).

## 4. PENDING №6 — IME портит длинный hex

**HexChunkField** (lib/widgets/hex_chunk_field.dart): ввод чанками по
20 символов, отдельные поля с авто-переходом фокуса; вставка полной
строки в первый чанк распределяется по полям; контроль символов
(inputFormatters + второй контур sanitize) и длины (счётчик
«Введено N из 64», ошибка при избытке; для подписей — чётность).
Применён на экранах: согласие гардиана (адрес подопечного, хеш),
перевыбор (адрес гардиана, подпись), запуск миграции (старый адрес,
гардиан, подпись), approve миграции (старый/новый адрес) — ввод
данных карточки восстановления на стороне гардиана/нового
устройства. Тесты: test/hex_chunk_field_test.dart (распределение
вставки, фильтрация, счётчик/ошибки, авто-переход).

**Находка прогона:** IME-нестабильность воспроизведена на обоих
полюсах — вставка полной строки теряла символы («Введено 61 из 64»,
счётчик поймал), а в поле списка «новые гардианы» (обычный TextField)
IME дважды дописал « to» и один раз съел 2 символа: битый список
пересчитал хеш смены, публикация упала E_GUARDIAN_UPDATE (повтор
находки 11.2). Поэтому контроль длины/символов добавлен и в поле
списка: ошибка «Ожидается ровно 64 hex-символов» + блокировка
публикации (тест «битый адрес в списке блокирует публикацию»).
Чанковый ввод по 20 с проверкой полей прошёл без потерь (адрес 64/64,
подпись 140–142 симв.).

- IME эмуляторов нестабилен и к чанкам при длинной вставке (теряет

- Поле «новые гардианы» — многострочный список, чанки неприменимы;
  контроль — валидация длины/символов каждой строки (ошибка +
  блокировка публикации). Повторная порча после валидации маловероятна,
  но не исключена (IME); при E_GUARDIAN_UPDATE — исправить поле и
  повторить (отклонённая транзакция цепочку не двигает).
- Таймаут BiometricPrompt (платформенный слой) на эмуляторе
  недетерминирован — №3 покрыт widget-тестом с моком; на живом
  телефоне — чек-лист.
- Способ сдвига часов для прогонов (PENDING №5) — по-прежнему решение
