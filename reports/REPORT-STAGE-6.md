## 1. Связка ядра: gomobile bind (AAR) — выбор и обоснование

**Выбор: `gomobile bind` → AAR** (пакет `mobile/`, Java-класс `tnp.Tnp`).

Сравнение вариантов (замеры — `reports/stage6/aar-contents.md`):

| Критерий | gomobile bind (AAR) | c-shared + JNI/FFI вручную |
| --- | --- | --- |
| Размер | 103,6 МБ AAR (4 ABI; arm64 — 51,1 МБ .so) | тот же .so + свой JNI-слой |
| Накные расходы вызова | 5–10 мкс (сборка tx + protobuf-кодирование + разбор; хост) | сопоставимо (тот же JNI-переход), но пишется вручную |
| protobuf-обмен | []byte напрямую (Go-кодирование внутри AAR), без копий в Kotlin | нужен свой маршалинг через JNI-границу |
| Код связки | генерируется (18 КБ classes.jar) | ~1–2 тыс. строк ручного JNI на каждую функцию |
| Сборка/CI | одна команда, работает в CI | отдельная инструментальная цепочка |

gomobile даёт тот же размер (вся тяжесть — libp2p в .so, не в связке),
генерирует типизированный JNI-слой и убирает ручной FFI; накладные
расходы вызова (микросекунды) пренебрежимы на фоне PoW (секунды) и
сетевых операций. c-shared + JNI не даёт преимуществ ни по одному
критерию.

Сборка: `gomobile bind -target=android -androidapi 26 -ldflags "-checklinkname=0" -o android/libs/tnp.aar ./mobile`.
Флаг `-checklinkname=0` обязателен (Go 1.23+): зависимость `wlynxg/anet`
(WebRTC-транспорт libp2p, только Android) использует go:linkname на
`net.zoneCache`.

**Доработки ядра для связки — один коммит cbcd9a4 (минимальные, с пометкой):**
- `core/attest`: разбор реальных цепочек KeyMint/Keymaster (п.2 ниже);
- `core/ledger` applyRegister: R4b — challenge внутри цепочки аттестации
  обязан совпадать с challenge регистрации (анти-replay цепочки);
- `net`: экспорт `ConnectedPeers` и `BalanceWithProof` (баланс по
  Merkle-доказательству против финализированного чекпоинта, 12.5);
- `mobile/`: сам мост (код ядра не менялся).

Ключевой принцип связки: **ключ кошелька не покидает Android Keystore**.
Мост отдаёт хеш на подпись (`Tx.SigningHash`), Kotlin подписывает через
Keystore (`SHA256withECDSA`, DER) и возвращает подпись (`SetSignature`).

## 2. Keystore и аттестация (вопрос №7 → №37)

**KeystoreWallet** (`android/.../keystore/KeystoreWallet.kt`):
- ECDSA P-256 (`secp256r1`), `setAttestationChallenge(challenge)`;
- `setUserAuthenticationRequired(true)` + `AUTH_BIOMETRIC_STRONG`,
  таймаут 30 с — каждая операция подписи требует биометрии;
- `setInvalidatedByBiometricEnrollment(true)` — новый отпечаток
  инвалидирует ключ (повторная регистрация обязательна);
- цепочка аттестации → формат ядра (лист первым, 4-байтовый BE-префикс
  длины; корни не передаются — зашиты в APK, 7.2).

**Разбор цепочки в `core/attest`** (новый keymint.go, коммит cbcd9a4):
- реальный формат KeyMint/Keymaster: OID 1.3.6.1.4.1.11129.2.1.17,
  KeyDescription (attestationSecurityLevel, attestationChallenge,
  AuthorizationList с длинными тегами [704] RootOfTrust → deviceLocked,
  verifiedBootState; [706] osPatchLevel → YYYYMM);
- синтетический формат этапа 3 сохранён (песочница/эмулятор): Verify
  сначала пробует его, затем реальный;
- `Chain.Challenge` — challenge из расширения; applyRegister проверяет
  его совпадение с challenge регистрации (R4b): переиспользованная
  цепочка → E_ATTEST. Тест: TestRegisterChallengeBinding.

**Challenge задаёт узел** (R4, №23): SHA-256(pub ‖ protocol_id ‖
network_id) — `tnp.Tnp.attestationChallengeFor(pub, networkID)`.

**Эмулятор**: синтетические корни из `core/attest` (SandboxGenesis.
trustedRootsDER — детерминированы от network_id, одинаковы у всех
узлов песочницы). Instrumented-тест генерирует ключ с challenge,
проверяет цепочку и расширение в листе.

**Живое устройство**: instrumented-тест `KeystoreAttestationInstrumentedTest`
генерирует ключ и сохраняет цепочку в файл приложения (без приватных
данных); проверка против корней Google — чек-лист (см. раздел 8).

## 3. Экран биометрии

`BiometricGate`: `canUseStrongBiometrics` (BIOMETRIC_STRONG через
BiometricManager). **Отказ в регистрации без настроенной биометрии**:
MainActivity.setup() при недоступности биометрии показывает сообщение и
открывает системный экран добавления отпечатка
(`ACTION_BIOMETRIC_ENROLL` + `EXTRA_BIOMETRIC_AUTHENTICATORS_ALLOWED =
BIOMETRIC_STRONG`). Подпись — только через `BiometricPrompt` с
`CryptoObject(Signature)` (ключ с setUserAuthenticationRequired без
биометрии не подписывает).

## 4. PIN (8.2): обычный и тревожный

`PinManager` + `DuressState` (`android/.../pin/`):

- **Неразличимость**: один экран ввода, один ритм — функция `gate()`
  проверяет ОБА хеша одним кодом (сравнение за постоянное время),
  интерфейс не показывает, какой PIN сработал; настройка тревожного —
  тот же диалог с кнопкой «Пропустить» (по файлу нельзя узнать,
  задан ли тревожный PIN: оба хеша в одной записи, одно шифрование).
- **Тревожный вход → режим-приманка** (уровень приложения, не ядра):
  DuressState хранит «легенду» (правдоподобный остаток + история),
  показывается вместо баланса; реальное состояние реестра не искажается,
  сеть не опрашивается. **Ключ подписи при приманке не используется**:
  send() в приманке возвращает «перевод недоступен», Keystore не
  вызывается.
- **Отпечаток при тревожном отключён**: `DuressState.biometricAllowed()`
  = false в приманке; вход по отпечатку не предлагается, пока активен
  тревожный режим. Выход из приманки — обычный PIN (duress.exit()).
- Хранилище: файл PIN-состояния, AES-256-GCM ключом Keystore
  (tnp-pin-master); хеши PBKDF2-HMAC-SHA256, 120k итераций.
  allowBackup=false — в бэкап не попадает.

## 5. Сеть на устройстве

- **allowBackup=false** + dataExtractionRules/backupRules (ничего не
  бэкапится и не переносится) — AndroidManifest.xml.
- **seq от нескольких пиров перед подписью**: `Node.TipFromPeers(wallet,
  minAgree)` — опрос подключённых пиров (GetTip), требуется согласие
  minAgree (дефолт 2) одинаковых (seq, prev) — eclipse-защита 12.3/12.4.
  WalletFlow.buildTransferTx строит транзакцию с seq+1/prev=tip.
- **NSD/mDNS**: Go-узел анонсирует и находит пиров libp2p mDNS (служба
  `tnp-<первые 8 hex network_id>`, домен `_p2p._udp`) — тот же протокол
  mDNS, что NSD; `NsdDiscovery` отображает найденные службы на экране
  приложения. Разрешение CHANGE_WIFI_MULTICAST_STATE в манифесте.
- **Bluetooth SideChannel (12.4)**: `BluetoothSideChannel` — RFCOMM
  (SDP-имя tnp-sidechannel, фиксированный UUID), кадр = 4 байта BE
  длины + wire-кодирование транзакции. Приём: `tnp.Tnp.decodeTx` →
  `Node.onOfflineTx` — статус «ожидает публикации»; публикация
  `publishAwaiting()` при появлении сети — полный apply проверяет
  seq/prev (быстрая находка эквивокации). Статусы: awaiting_publication
  / published / finalized («получено по Bluetooth» ≠ оплата).
- **Лёгкий режим узла (12.2)**: `NodeController` — уровень full при
  «зарядка И Wi-Fi» (BatteryManager + ConnectivityManager), иначе light;
  смена условий — перезапуск узла (foreground service держит процесс).
  Лёгкий узел: DHT client, заголовки чекпоинтов, Merkle-доказательства
  баланса против ФИНАЛИЗИРОВАННОГО чекпоинта (`balanceWithProof`),
  свои входящие (`lightSync`). Foreground service — dataSync-тип,
  уведомление, START_STICKY.

## 8. Чек-лист «что проверить на живом телефоне»

1. Установить APK, настроить отпечаток; убедиться, что без биометрии
   регистрация отказывает и открывается экран добавления отпечатка.
2. Зарегистрировать кошелёк: замерить время register-PoW (таргет 2^24)
   — записать; замерить выпуск (mint-PoW, Argon2id 32 МиБ, таргет 2^56)
   — записать; по замерам утвердить таргеты №9.
3. Аттестация: убедиться, что цепочка доходит до корня Google
   (уровень TEE/StrongBox в расширении), приложить captured-сертификаты
   (без приватных данных) в reports/stage6/; проверить разбор
   tnp.ParseAttestation с корнями Google, зашитыми в APK.
4. Проверить инвалидацию ключа: добавить новый отпечаток → подпись
   должна отказать (setInvalidatedByBiometricEnrollment).
5. PIN: задать обычный и тревожный; войти по тревожному — убедиться,
   что показывается легенда, перевод недоступен, отпечаток не
   предлагается; войти по обычному — приманка снята.
6. Bluetooth: два телефона, сопряжение; передать подписанную транзакцию
   офлайн; на получателе — статус «ожидает публикации»; при появлении
   Wi-Fi — публикация и проверка seq/prev.
7. NSD: в одной Wi-Fi-сети узлы находят друг друга (mDNS) без ручного
   ввода адресов.
8. Замеры 12.1: память узла (full vs light), энергия за час
  (foreground service), размер APK/AAB после подписания.
9. Уровни: зарядка+Wi-Fi → полный узел (DHT server); отключить
   зарядку → перезапуск в лёгкий (DHT client).

## 10. Ограничения этапа

- Эмулятор x86_64 ≠ телефон ARM: замеры PoW на эмуляторе — ориентир;
  финальные таргеты №9 — по живому телефону (чек-лист п. 2).
- Корни аттестации Google не зашиты в APK (нужен выбор: полный набор
  корней Google + ротация — отдельное решение; сейчас песочница
  использует синтетические корни).
- Переключение уровня узла — перезапуск (не live-switch); состояние
  полного узла — SQLite в filesDir (allowBackup=false).
- Bluetooth: приём/передача реализованы; выбор устройства — по имени
  из сопряжённых; UI-экран выбора пары — упрощён (чек-лист п. 6).
