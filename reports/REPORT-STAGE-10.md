## 1. Адаптивная комиссия (10.2, долг 8.0)

Заглушка `Fee = RateMin` удалена. Пересчёт ставки — на границе эпохи из
данных финализированных чекпоинтов: рост `total_supply` за последние
`fee_adjust_epochs` (K) эпох выше целевого — ставка растёт на шаг, иначе
снижается; границы `[rate_min, rate_max]`. Источник — чекпоинты
(пороговая подпись): значения консенсусны, поэтому все узлы сходятся к
одному значению без координации; выбор источника решает и проблему
дивергенции живых узлов при позднем прибытии транзакций (клинический
случай, из-за которого claim-time схемы отвергнуты).

- Поля genesis 57–59: `fee_adjust_epochs`, `fee_target_growth_micros`,
  `fee_step_micros`; 0 — пересчёт выключен (векторы этапа 0 не затронуты).
- Ряд предложения персистентен (SQLite `checkpoint_supply`), рестарт из
  БД восстанавливает цепочку пересчётов — свёртка идентична работавшему
  без остановки узлу (тест `TestAdaptiveFeeRestart`).
- Рост считается 128-битным умножением — без переполнения uint64
  (найдено тестом верхней границы).
- `fee_mode = POOL`: комиссия идёт в общий фонд сети
  (`State.CommonFund`); INV-8 расширен на балансы пулов и общий фонд.

Тесты (`core/ledger/fee_test.go`): эквивалентность двух узлов, снижение
до нижней границы, верхняя граница, разогрев окна (до K+1 чекпоинтов
ставка не меняется), нулевая база, регрессия/дубль эпохи, выключенный
режим, round-trip полей genesis. Дефолты (K=6, цель 6%, шаг 0,05 п.п.) —
предположение, №44.

## 2. attest + проверяющая библиотека (6.1)

`core/present`: предъявление = подписанное кошельком утверждение
`wire.AttestStatement` (network_id, адрес, статус, возраст, глубина
графа поручительств, flagged, хеш манифеста, эпоха чекпоинта, challenge
проверяющего, срок годности, app_id) + Merkle-доказательство листа
состояния из чекпоинта (`cons.StateProof`, sparse Merkle по адресам) +
открытый ключ кошелька (проверяющий не имеет реестра; адрес проверяется
деривацией из ключа).

- `Verify` — без полного узла: подпись кошелька, привязка ключа к
  адресу, challenge (защита от повторного использования), срок
  годности, хеш манифеста (3.3), пороговая подпись чекпоинта,
  Merkle-доказательство против корня, соответствие утверждения листу
  (статус/flagged). Вердикт выносит проверяющий (6.1) — протокол
  вердиктов не выносит; `VerifyAgeBound` даёт производную оценку
  возраста из листа.
- `H(address ‖ app_id)` (`AppIdentity`) — «один человек — одно действие»
  в стороннем приложении; публично связан с адресом.
- `LightSync` — лёгкий клиент-синхронизатор: принимает чекпоинты с
  любого узла, проверяет цепочку (prev_hash, окно времени) и пороговую
  подпись; `net.CheckpointChain` — транспорт из полного узла.
- Тесты: полный цикл (лёгкий клиент → Verify → app-identity),
  подлоги (чужой challenge/манифест/сеть, просрочка, порог не достигнут,
  подмена утверждения и листа), глубина графа, цепочка LightSync.
- Сборки JVM/JS — №45 (PENDING); приоритет — языки сообществ пилотов.

## 3. redeem (6.2) и quota_reset

Payload-теги 17–24 в wire (закрытый перечень типов уже содержал
REDEEM/RECEIPT с этапа 0). Валидация spec/03 3.11: D1 поставщик из
`providers`, D2 `resource_id` сети, D3 правила списания как у transfer
(мораторий, остаток, комиссия по fee_mode), D4 слот в будущем/настоящем.
`receipt` (D5): подписан поставщиком, сверяется с состоявшейся REDEEM
(сумма/ресурс/слот), запись без изменения балансов; повторы отклоняются.

`quota_reset`: квота заявляется ровно за один завершённый период
(накопления нет, `E_ACCRUAL_WINDOW`), неиспользованные когорты сжигаются
на границе периода (settlePeriod).

## 4. pool (6.3)

`pool_create/donate/close/claim` (spec/03 3.9): получатель — кошелёк из
`providers`, режимы выпуска `release_on_deadline` (дедлайн — граница
эпохи, доля фиксируется по числу active), `release_on_goal`,
`release_continuous`; `refund_if_unmet` — возврат донатам при закрытии
невыполненного пула (P5); равные доли `active`-кошелькам, повторный
claim — `E_POOL_CLAIMED`. Право закрытия — создатель (№26, предположение);
незаявленные доли остаются в пуле (№19, предположение). Прогресс публичен
(состояние пересчитывается каждым узлом; экспорт — п.6).

## 5. contribution (6.4)

`contribution_claim/confirm` (spec/03 3.12): K1 окно периодов
(текущий/предыдущий — предположение), K2 подтверждающий active,
K3 не связан поручительствами с заявителем (реальные vouch-рёбра в
тесте), K4 лимит подтверждений на человека в период, K5 без дублей,
K6 N=2 подтверждений принимают заявку. Выплата — из пула программы
(рекомендуется) либо эмиссия `on_contribution` с потолками на человека
и на период (предположения, №46). Числа — константы
`core/ledger/modules.go` с пометками PENDING.

Гейтинг модулей: операции выключенного модуля — `E_MODULE` (поле
`modules` профиля, раздел 4).

## 6. sandbox (6.5)

Синтетические кошельки: флаг `-synthetic` в `register` (R5: только
песочница; метка в чекпоинте). Headless-режим — существующие флот/ sim.
Экспорт реестра для анализа — режим `export` в `tnp-testnet` (6.5:
«оборудование, предложение, неравенство считаются из публичного реестра
любым клиентом»): json — кошельки, пулы, метрики (оборот по типам
transfer/redeem/pool_donate, предложение minted/burned/net, Gini
балансов, счётчики synthetic/active); csv — таблица кошельков для
анализа. Проверено на живом узле (закрытая тестовая сеть, артефакты
вне репо).

## 7–8. Конфигуратор + шаблоны семи профилей (раздел 5, 3.3)

`core/profiles`: семь шаблонов раздела 5 (лаборатория, человечность,
квоты, ваучеры, банк времени, вклад, касса взаимопомощи) на базе
дефолтов «Валюта» (1.1/1.2, №9/№15–17). Валидация раздела 4: запрет
`relaxed` при высоких ставках (при выключенной комиссии ставки не
действуют — учебные сети проходят), `quota_reset` без накопления и с
заданным resource_id, heartbeat без стоимости и soulbound, демередж
обязателен для передаваемых hours/currency вне песочницы (10.3/10.4),
модули соответствуют единице и режиму выпуска, invite_only-доступ при
invite_only-входе, sandbox без params_mutable.

Уровень гарантий вычисляется из манифеста (3.3), не заявляется:
высокий — strict+decentralized+open_vouch; средний — relaxed или
members_quorum; учебный — sandbox; вход по приглашению — «средний»
(интерпретация этапа 10: закрытый круг ниже высокого).

`tnp-testnet configure`: `-list` (шаблоны с уровнями гарантий) или
`-template 1..7 -network-id ИМЯ` + оверрайды (issuance, K, эпоха,
resource_id, имя) → валидация → genesis.bin + manifest.json +
`guarantees.json` (уровень + обоснование + manifest_hash) + invite.txt.
Проверено: все семь шаблонов генерируют валидные genesis-пакеты, ядро
их читает (`slots -genesis`).

## 10. Карточка восстановления (решение владельца 20.10.2026)

Экран «сохраните эти данные» — шаг онбординга после успешной
регистрации: адрес кошелька, адреса назначенных гардианов

v9.7 (раздел 11). Тесты: корректные данные после регистрации (адрес,
гардианы, объяснения, QR), честное предупреждение без гардианов, доступ
из настроек, payload QR.

## Отклонения и предположения

- Адаптивная комиссия: параметры пересчёта (K, цель, шаг) — черновые
  дефолты, №44; подбор симуляцией — этап 11. Источник — minted-объём
  чекпоинта (`total_supply`), т.е. рост только от эмиссии; демередж и
  сжигание комиссий в рост не входят (поле чекпоинта единственное).
- contribution/pool: N=2, лимит 5/период, потолки 1×/10× issuance,
  право закрытия — создатель, незаявленные доли — в пуле, окно заявки —
  текущий/предыдущий период (№46, = №13/№19/№26).
- Уровень гарантий: invite_only-вход — «средний» (интерпретация).
- `contribution_claim` несёт необязательный `pool_id` — пул программы
  для выплаты; в payload-составе spec/03 3.12 не определён (модульные
  payload этапа 10 кодируются впервые).
- Гонка `cpTick`/`rebuildToFinality` (чтение `n.Ledger` без лока)
  существует с начального релиза, найдена `-race` в прогонах этапа —
  закрыта (`applyMu.RLock`). Флаки `TestSyncAnchorContinuation`,
  `TestLightNodeCheckpointProof`, `TestSideChannelPublishPropagates`
  под `-race` воспроизведены на main (timing-чувствительность
  детектора гонок; без `-race` зелёные) — не регресс этапа.
