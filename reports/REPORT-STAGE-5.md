### 1. Эпохи и сетевое время (9.2) — `cons/time.go`

- Источник правды — эпохи чекпоинтов: `cons.Clock` ограничивает сетевое
  время узла интервалом `[cp.time, cp.time + epoch_seconds + сдвиг]`.
- **№16, предложение v1: `epoch_seconds` = 24 ч** — чекпоинт раз в
  сутки: финальность «на следующий день», трафик подписей пренебрежим
  (21 подпись × ~72 байта), время для сети (9.1). Песочница —
  `time_scale`; в тестах переопределяется (`ConsensusEpochSeconds`).
- **Предел сдвига сетевого времени: `epoch_seconds/4` (6 ч при 24 ч)** —
  четверть эпохи: достаточный запас против спешащих/отстающих часов,
  при этом атаки на «растягивание» эпохи ограничены; проверяется в
  `cons.Verify` (spec/07 7.2.1).
- Календарь UTC (9.2): «1-е число месяца» = первая эпоха, начавшаяся
  после 00:00 UTC 1-го (`PeriodOfEpoch`); период выпуска меняется
  только на границе эпохи.
- Допуск timestamp ±30 мин — уже в ядре (C9); при replay часы
  пинируются на `timestamp_claim` (C9 — на момент публикации).

### 2. Выборочное голосование (9.1) — `cons/vote.go`

Snowball-подобное: повторяющийся опрос случайной выборки пиров, кворум
по суммарному весу, β последовательных раундов — локальная финальность.
Вердиктов о «вине» нет (7.5): голосование только выбирает ветку; метка
`flagged` — только через `evidence` любым узлом.

- **Веса** (возраст + аттестация): `1 + min(age/365, 2) + 1` (сеть с
  `device_policy STRICT` — все кошельки с TEE-аттестацией, R2 на
  register; посевной круг — genesis-ключи). Диапазон 1–4.
  Дифференциация по уровню аттестации отдельных устройств — этап 6
  (нужны данные об устройствах).
- **Параметры (предложение, обосновано симуляцией)**: k = 10 пиров в
  выборке, **α = 0,7** кворума веса, **β = 4** последовательных раунда.
  Обоснование α: живость гарантируется при доле злонамеренных ≤ 30%
  (вес честных 0,7 ≥ α); победа атакующего требует ≥ 70% веса в
  выборке — при f = 50% вероятность серии из β раундов пренебрежима
  (эмпирически: исход при 50% не гарантирован ни для одной из сторон —
  это граница устойчивости). β = 4 — финальность за 4 раунда опроса
  (симуляция: `RoundsToFinality = [4]` во всех сценариях).
- Судей нет: проигравшая ветка остаётся в журнале (INV-1c) и служит
  материалом `evidence` (7.5).

### 3. Чекпоинты (spec/07) — `cons/checkpoint.go`, `cons/modes.go`

- Header: `StateRoot` (core/smt, лист `StateLeaf` из 9 полей — D7),
  `finalized_txid_list` (поле 12), пороговая подпись N-из-M
  (`core/threshold`); `checkpoint_hash` = SHA-256(canonical без
  подписей); цепочка: `epoch = prev+1`, `prev_hash`, предел сдвига
  времени (7.2.1).
- Сбор подписей по сети: тема `checkpoint/<network_id>` (заготовка
  этапа 4 ожила) — предложение + доли; подписи композициональны,
  агрегирует любой узел; дедуп по подписанту.
- **Режимы**:
  - `decentralized` — детерминированная выборка `ValidatorsM`
    active-кошельков (сортировка по SHA256(prev_hash ‖ адрес) —
    предсказуема только после финализации предыдущего чекпоинта),
    **N ≥ 2/3 M** (№17, рабочая гипотеза spec/07);
  - `members_quorum` — все active, N = ceil(2/3 M);
  - переходный (холодный старт) — посевной круг из genesis, N = 2 из 3,
    до `seed_sunset`.
- **№15, предложение дефолтов**: `seed_sunset` = 100 `active`-кошельков
  ИЛИ 24 эпохи (24 суток при epoch 24 ч); genesis может задать свои
  значения (`SeedSunset`). После — режим манифеста.
- Узел не подписывает чекпоинт при незавершённом голосовании: чекпоинт
  фиксирует сходимость (документировано).

### 4. Симуляция (9.1, «проверить до реализации») — `sim/`

Детерминированная (seed), headless, поверх тех же core+cons; сотни
виртуальных узлов, раундовая виртуальная сеть (разбиение/офлайн),
pre-state кошельков (готовый социальный граф — механика активации
тестируется ядром этапа 3). Сценарии и результаты (n — узлы):

| Сценарий | Результат |
| --- | --- |
| Конфликт веток (n=100, 70/30) | финальность за **4 раунда** (β); победила ветка большинства; 30 узлов перестроились (30 откаченных валидных tx); чекпоинты финализируются |
| Эквивокация + evidence (n=100) | ветка выбрана голосованием; кошелёк помечен `flagged` через evidence (подал узел 9; вердиктов нет) |
| Двойной выпуск (n=20, 2 календарных месяца) | конфликт обнаружен, разрешён голосованием; чекпоинты на всём горизонте |
| Расщепление 70/30 + слияние (n=60, members_quorum) | во время расщепления большинство (≥ 2/3) продолжает финализировать чекпоинты; меньшинство — нет; после слияния меньшинство синхронизирует цепочку и перестраивается (18 откатов); все сходятся |
| Злонамеренное меньшинство (n=100) | f=10/20/30% — **честная ветка побеждает**; f=50% — исход не гарантирован (граница устойчивости α=0,7); при 20% чекпоинты в одном прогоне не собрались (выборка валидаторов — варьируется) — см. «Риски» |
| Холодный старт (10 узлов) | переходный режим: чекпоинты подписывает посевной круг (3, N=2); голосование сходится и в малой сети |
| members_quorum при офлайне (n=30) | офлайн 10/20/30% — чекпоинты финализируются; **40% — нет** (онлайн < 2/3) — граница 1/3 |
| Переход seed_sunset (эпоха 3) | подписанты: переходный = 3 (круг), после = 20 (все active) |

Метрики по прогонам: трафик голосования ~4 000–4 800 сообщений на
разрешение конфликта (100 узлов × 4 раунда × k=10); перестройки
(откаты) = числу узлов, державших проигравшую ветку; replay-ошибок 0.

### 5. Интеграция (net, cmd)

- `net/cons.go`: голосование по сети (протокол
  `/tnp/<hex>/vote/1.0.0`: запрос предпочтения → ветка + вес),
  чекпоинты в полном узле (закрытие эпохи, подпись участником, сбор
  долей по теме, финализация, store), перестройка состояния под
  финализацию, лёгкий узел проверяет доказательство баланса против
  корня финализированного чекпоинта (`VerifyProofAgainstCheckpoint`).
- Конфликтные ветки сохраняются в store и воспроизводятся replay
  (INV-1c/INV-3).
- `cmd/tnp-node`: флаг `-wallet` (кошелёк узла — подписант чекпоинтов);
  статус-файл: число чекпоинтов.
- Сетевые тесты: `TestCheckpointTransitionalNetwork` (переходный режим,
  2 из 3, финализация на всех узлах), `TestVoteFinalityNetwork`
  (голосование по реальным соединениям, сходимость состояний),
  `TestLightNodeCheckpointProof` (доказательство по чекпоинту,
  подменённый корень отбрасывается).

## Поведение при разделении сети (что видит получатель перевода)

Сценарий: расщепление 70/30, конфликтная пара переводов (A —
большинству, B — меньшинству), затем слияние.

- **Во время расщепления**: получатель в группе большинства видит
  баланс с веткой A (provisional — применяется FirstWins), получатель
  в группе меньшинства — с веткой B. Большинство (≥ 2/3 участников)
  продолжает финализировать чекпоинты со своей веткой; меньшинство
  чекпоинтов не собирает (порог 2/3 недостижим) — его вид
  неокончательный. «Получено» ≠ «оплачено»: до чекпоинта любой
  перевод — provisional (10.1: побеждает первая по порядку финализации;
  интерфейс статуса — этап 4, `OfflineStatus`).
- **После слияния**: голосование и/или синхронизация цепочки чекпоинтов
  приводят меньшинство к `finalized_txid_list` большинства; узлы
  меньшинства перестраивают состояние (откат проигравшей ветки —
  в симуляции 18 откатов на 18 узлов). Оба получателя видят один
  баланс — победителя. Проигравшая ветка остаётся в журнале (INV-1c)
  и служит материалом `evidence` для `flagged` (7.5).
- **Симметричное расщепление 50/50**: ни одна группа не достигает
  кворума (α = 0,7) и порога подписи (2/3) — чекпоинтов нет, конфликт
  висит до восстановления связности (защита от двойной финализации;
  внешнего арбитра нет — 7.5).

## Отклонения и риски

1. Нумерация правки спецификации: промпт называет её «INV-9»; по
   содержанию правка внесена в INV-1c и INV-3 (см. коммит 6009852 и
   примечание в spec/04). `finalized_txid_list` добавлен в
   proto/checkpoint.proto и spec/07 7.1 — это механизм, названный в
   п. 6 промпта; остальные поля — только авторизованные.
2. Голосование в сети: ответ пира (ветка + вес) пока не подписан —
   вес заявляется отвечающим. Допустимо для v1 (вес ограничен 1–4,
   выборка случайна); подпись ответов голосования — кандидат на этап 6.
3. Симуляция: предлагающий чекпоинт детерминирован (минимальный номер
   среди онлайн) — в реальной сети предлагает любой узел (контент
   детерминирован, конкурирующих предложений не возникает); сбор
   подписей в симуляции упрощён (нет гонок доставки).
4. При f=20% в одном прогоне симуляции чекпоинт не собрался (выборка
   21 валидатора случайно сместилась к злонамеренным) — голосование
   при этом завершилось корректно (победила честная ветка); риск
   задержки чекпоинта при высокой доле злонамеренных в выборке.
   Увеличение M или повторные попытки в следующих эпохах — этап 6.
5. Веса голосования: дифференциация по уровню аттестации отдельных
   устройств (TEE/StrongBox) — этап 6 (нужны данные об устройствах);
   сейчас — сетевой `device_policy` + посевной круг.
6. `Ledger.Finalizer` (интерфейс ядра) не задействован: разрешение
   конфликтов идёт в cons-слое (глобальная финальность — чекпоинт);
   интерфейс оставлен для будущих режимов.

- Финальность воспроизводится в агрессивных сценариях симуляции
  (конфликт, эквивокация, двойной выпуск, расщепление+слияние,
  злонамеренное меньшинство до 30%, холодный старт, офлайн до 1/3).
- Поведение при разделении сети задокументировано (раздел выше).
- Граница малых сетей определена: members_quorum до ~100 участников
  (симуляция), далее decentralized.
- Чекпоинты подписываются в обоих режимах и в переходном
  (`TestCheckpointTransitionalNetwork`, симуляции cold start и
  seed_sunset).
- Лёгкий узел проверяет доказательство баланса по чекпоинту
  (`TestLightNodeCheckpointProof`).
