## 2. Атака A — изоляция якорного/строительного узла

**Цель.** Узел посевного круга (подписант чекпоинтов) или строитель
чекпоинта видит только пиров атакующего и подписывает корень состояния,
расходящийся с честной сетью.

**Параметры атаки.**

| Параметр | Значение | Обоснование |
| --- | --- | --- |
| Число IP/подсетей | 3 различных `/24` (IPv4) | ровно `eclipse_n = 3` |
| Требование к ASN | **нет** — все три `/24` могут быть в одном ASN | ASN-классификации в протоколе нет (`net/eclipse.go:9-10`: «ASN-классификация требует внешних данных — PENDING») |
| Стоимость | 3 VPS в одном AS, либо 3 адреса у одного провайдера | дешевле одной фермы |
| Дополнительно | 1 «затравка» в кэше пиров жертвы (шаг 1 каскада) | кэш без TTL, до 64 адресов, перезапись через PX |

**Шаги (дизайн).**
1. Поднять 3 узла атакующего в трёх `/24` (например
   `203.0.113.0/24`, `198.51.100.0/24`, `192.0.2.0/24` — документационные
   диапазоны; в прогоне — loopback-алиасы, см. §4).
2. Все три объявляют `UserAgent = tnp/<hex network_id>` жертвы —
   фильтр `net/host.go:101` пропускает (строка сравнивается, не
   подпись).
3. Затравка: подключиться к жертве как «обычный пир», отдать в
   peer-exchange (`msgPeers`) адреса трёх узлов атакующего. PX —
   шаг 7 каскада, ответ ничем не аутентифицирован
   (`net/bootstrap.go:337-370`).
4. При следующем рестарте/переподключении жертва берёт кэш (шаг 1) —
   в нём уже только адреса атакующего; `MinPeers*2 = 6` соединений
   набираются из трёх узлов (по 2 соединения на узел).
5. Узлы атакующего отдают жертве свой журнал (`SyncJournalFrom`),
   отфильтрованный: без конфликтующей ветки и без части переводов.
6. Жертва строит чекпоинт по своему состоянию и подписывает корень.

**Ожидаемый признак успеха.**
- `Stats().Peers` жертвы = 6, все — Peer ID атакующего;
- `LinkSpread(txid)` для tx, известной честной сети, даёт `(peers≥1,
  groups=1)` — подтверждение не достигается;
- `state_root` жертвы расходится с честным узлом при одинаковом журнале
  честной сети;
- подписанный жертвой чекпоинт отвергается честными узлами (порог
  подписей) либо, при достаточном числе изолированных подписантов,
  создаёт конкурирующую цепочку.

**Какие проверки сработают.**
- Подпись seed-списка (N-из-M) — атакующий не подделает список.
- `network_id`-фильтр — только если атакующий ошибётся с UserAgent.
- Порог подписей чекпоинта (M/N) — один изолированный подписант не
  финализирует чекпоинт в одиночку.
- `Corroboration` — не даст жертве пометить чужие tx «финализировано»
  (но и не мешает приёму: `applyLive` не гейтится порогом).

**Какие проверки НЕ сработают.**
- ASN-разнообразие — отсутствует.
- Разнообразие за пределами `/24` — отсутствует (три `/24` одного AS
  проходят).
- Защита кэша пиров от отравления — отсутствует (PX → кэш → шаг 1).
- TTL/свежесть кэша — отсутствует.
- Детект эклипса (доля одного источника, смена набора пиров) —
  отсутствует.
- Свежесть seed-списка — `now=0` отключает проверку `SeedListMaxAge`
  (7 суток, `net/seedlist.go:35`), старый подписанный список
  принимается.

## 3. Атака B — поддельное подтверждение офлайн-платежа (двойная трата)

**Цель.** Получатель Bluetooth-платежа видит «финализировано» для
транзакции, которая проиграет конфликт (двойная трата).

**Параметры.** Отправитель + 2 соучастника в 3 разных `/24`
(тот же ASN). Транзакция валидно подписана (иначе `relayAdmit`
отклонит), но конфликтует по `seq`/`prev` с другой веткой.

**Шаги (дизайн).**
1. Отправитель передаёт tx получателю по Bluetooth (офлайн-канал).
2. Получатель публикует tx; она проходит `relayAdmit` (дешёвые
   проверки + подпись + PoW) и `handleTxFromPeer` → `Corroboration.Add`
   (`net/node.go:577`).
3. Два соучастника в двух других `/24` ретранслируют тот же txid
   (валидный конверт) → `groups = 3`.
4. `OfflineStatus` → `OfflineFinalized` (`net/node.go:988`), UI
   показывает «финализировано».
5. Параллельно отправитель публикует конфликтующую ветку; финализация
   выбирает её.

**Признак успеха.** `OfflineStatus(txid)` = `finalized` при том, что
`FinalityView` не содержит txid и `state_root` сети не отражает
перевод.

**Почему срабатывает.** `Corroboration.Add` вызывается до финальности
и до разрешения конфликта; порог считает «доставку», а не
«финализацию». Классификатор `/24` обходится тремя подсетями одного
ASN.

**Контрмера в текущем коде.** Формально есть оговорка в спеке
(12.4: «пока транзакция не опубликована и не подтверждена сетью, она
не является оплатой»), но `OfflineStatus` выдаёт `finalized` по
подтверждению доставкой. Разделение «доставлено N группами» и
«финализировано чекпоинтом» в коде отсутствует.

## 5. Sybil-слой (не сетевая эклипса)

Сетевой sybil (много Peer ID) не даёт кошельков: `register` требует
аттестацию + PoW, `active` — K=3 поручительства от `active`-кошельков
возраста ≥ 3 мес. (README 7.4). Эклипса усиливает sybil только как
сокрытие: изолированный узел не видит `evidence` о нарушениях и не
получает свежих `vouch`. Отдельного сетевого параметра для sybil в
контуре 1 нет — граница между «сетевой sybil» и «социальной» проходит
по поручительствам, и она в коде реализована (`core/ledger/validate.go`,
`core/ledger/invariants.go`).
