### 1.1. `spec/03-validation.md:31` (C11) — якорь слота: текущий период

Факт кода (`core/ledger/validate.go:150-168` — блок M7 в `applySigPowTime`,
`CheckMintChallengeWindow` `validate.go:186-194`):

```go
if tx.Type == wire.Mint && !l.Opts.SkipMintChallengeWindow {
    if !l.CheckMintChallengeWindow(tx.Wallet, l.tt.period, l.tt.now) {
        return reject("E_POW_HARD")
    }
}
```

`l.tt.period` — `periodAt(tx.TimestampClaim)` (`validate.go:229`), то есть **текущий**
период выпуска (период txNow), а не заявляемый `payload.period`. Слот
(`mintChallengeSlot`, `validate.go:206-212`):

```
h = hashThree(addr, period)                      // SHA-256(addr ‖ period_be64), первые 8 байт
period_start = genesis_time + period*period_seconds
slot = period_start + h mod period_seconds
```

Окно: `slot ± mint_challenge_window_hours*3600`; `0` — проверка выключена.

**Было** (`spec/03-validation.md:31`):

```
| C11 | Для `REGISTER`/`MINT`: `POW_ARGON2ID`, сходится, для `MINT` — txNow в окне ±`mint_challenge_window_hours` (поле 51) от слота челленджа `period_start + H(...) mod period_seconds` (поле 61) заявляемого периода (v9.13: окно — от claim) | иначе `E_POW_HARD` |
```

**Стало** (`spec/03-validation.md:31`):

```
| C11 | Для `REGISTER`/`MINT`: `POW_ARGON2ID`, сходится против `target_hard`; для `MINT` — txNow в окне ±`mint_challenge_window_hours` (поле 51) от слота челленджа ТЕКУЩЕГО периода выпуска (v9.14): `slot = period_start + H(address ‖ period) mod period_seconds` (поле 61), где `period = periodAt(txNow)`; поле 51 = 0 — проверка окна выключена | иначе `E_POW_HARD` |
```

Добавлено замечание после таблицы (`spec/03-validation.md:37-44`) — формула слота, якорь
(текущий период, v9.14, решение владельца 03.11.2026), причина фикса (заявка периода `P`
возможна только после его конца — M4; достижимость 1/15 за период, шесть пропусков подряд —
поглощающее состояние), `period_start` от `genesis_time` (9.2) и PENDING по включению
`hash(чекпоинта предыдущей эпохи)` в формулу (код считает `H(address ‖ period)`).

## 2. PLA-F-02 (низкая) — «2^24» против факта 2^40

Факт кода: `TargetLight: 0x0000_0100_0000_0000` (= 2^40, `core/params/params.go:180`);
`HashBelowTarget` сравнивает первые 8 байт хеша (big-endian `uint64`) с таргетом
(`core/crypto/pow.go:16-22`), поэтому ожидаемое число попыток = 2^64 / 2^40 = 2^24.
То есть **2^40 — значение таргета**, 2^24 — производное ожидаемое число итераций.
Erratum: обозначение таргета исправлено на 2^40, hex-значения не менялись; производное
«≈2^24 итераций» сохранено в скобках (иначе теряется основание замеров «~0,6 с хост»
и «~1–4 с телефон»).
