## Шаг 2 — эмуляторный прогон «кража → приманка → миграция → восстановление»

Сеть: конфигуратор (`tnp-testnet configure`), шаблон 1 «Лаборатория»
(sandbox-аттестация для приложения, relaxed, points, эпоха 300 с, VouchK=2,
комиссия выключена), network-id `stage11-prep`, genesis = 91 сут назад,
посевные S122/S01/S128 (окна челленджа P2 достижимы из текущего периода).
Окно отмены миграции — параметр сети (`migrate_delay_days`, поле genesis 49):
выставлено короткое — 1 день (пост-обработка genesis-пакета хелпером вне
репо; см. PENDING ниже). Часы хоста не сдвигались; сдвигались только часы
эмуляторов (узлы внутри эмулятора). Узлы: 2 × tnp-node внутри E1 с SQLite
(журнал переживает рестарты). Два эмулятора: E1 (tnp_api35) — «телефон A»,
E2 (Pixel_9, API 36) — «телефон B»; связность E2→E1 по TCP (adb forward,
ядро поддерживает tcp-транспорт).

### 2.1 Посевной круг → активация → выпуск — выполнено (скриншоты 01–06)

Выпуски посевного круга в окнах P2 — 3/3 accept. Кошелёк A: онбординг
(биометрия → PIN → гардианы 2–3 из реестра) → register (усиленный PoW,
биометрическая подпись) → карточка восстановления → поручительства ×2 →
ACTIVE → баланс 1000 (перевод от посевного). **Отклонение:** выпуск из
приложения заблокирован UI-багом окна челленджа (находка 2 ниже) — баланс
создан переводом; скриншот 05 фиксирует отключённую кнопку при фактически
открытом окне (слот заявляемого периода 4 достижим, ядро бы приняло).

### 2.2 «Кража» — выполнено (скриншоты 07, 10)

Вход по известному PIN на lock-экране (скриншот `07-theft-pin-access…`,
кошелёк A с балансом доступен вору). Дублирующий вход по отпечатку
продемонстрирован в предыдущей сессии (ветка stage11-prep) — тот же
полный доступ.

### 2.3 Тревожный PIN → приманка — заблокирован (находки 3–4 ниже)

Тревожный PIN не удалось задать при онбординге A: переключатель duress
дважды тумблернулся flaky-вводом (состояние выключилось), поле тревожного
PIN не принимало символы (IME-таймауты, ImeTracker onFailed
PHASE_CLIENT_VIEW_SERVED / STATUS_TIMEOUT). Lock-экран E2 (кошелёк B,
duress 7777 задан) — ввод также мёртв (та же деградация IME). Функция
приманки кодом не менялась со стадии 8.1 (демонстрирована в прогоне 8.1-2,
`reports/stage8/sim50/run2/duress-*.png`); в этом прогоне шаг не пройден —
зафиксирован как ограничение среды, не протокола. Проверка «приманка не
влияет на миграцию» по коду: decoy — локальное состояние приложения, ключ
подписи не используется (8.2), протокол миграции его не видит.

### 2.4 Новый кошелёк: регистрация → карточка → StartMigration — частично

Кошелёк B зарегистрирован через приложение (онбординг с duress-PIN и
легендой), карточка восстановления показана (скриншоты 08–09).
Экран StartMigration открыт, старый адрес и пары «гардиан + подпись»
введены (скриншоты 10–12; подписи собраны хелпером по правилу
MigrateStatement{network, old, new, nonce, epoch}). **Блокер:** приложение
генерирует случайный nonce и не показывает его (находка 5 ниже) —
гардиан физически не может подписать правильный statement; публикация
предложения из приложения невозможна. PIN-подтверждение (confirmPin) на
диалоге также нестабильно (IME). Протокольная часть миграции выполнена
CLI-кошельками W9→W10 (тот же путь ядра: applyMigrate/settle/executeMigration).

### 2.5 «Вор» отменяет миграцию — выполнено (артефакт 15)

W9 (ACTIVE, 500, гардианы S122/S01) → W10: MIGRATE propose (nonce 515151)
принят; **отмена старым ключом в окне** (`migrate -mode cancel`, подпись
ключом W9, seq 2) — accept/OK. Задокументировано как подтверждённое известное
ограничение: вор, знающий PIN/владеющий старым телефоном, может отменять
попытки восстановления в 14-дн. окне (в прогоне окно сокращено до 1 дня
параметром сети). Повтор миграции: propose с новым nonce 616161 — accept/OK.

### 2.6 Успешная миграция: settle и проверки — выполнено (артефакты 14, 16, 17)

После сдвига часов за ExecuteNotBefore и транзакции-триггера settle
исполнился. Проверено по экспорту реестра:

| Переносимое | W9 (старый) | W10 (новый) |
| --- | --- | --- |
| статус | ACTIVE → | ACTIVE (унаследован) |
| возраст (activated_at) | 1792578955 → | 1792578955 (перенесён) |
| история выпусков (last_claimed_period) | 0 → | 0 |
| флаги (flagged) | false → | false |
| **баланс** | 500 → | **500** (перенесён) |

Старый кошелёк W9: **EXPIRED (Terminal), баланс 0**. Поручительства
(VouchesReceived/Activators) переносятся тем же кодом executeMigration
(юнит-тесты ядра; экспорт CLI списки не раскрывает — отмечено).
**Повторный REGISTER старого фингерпринта отклоняется:** register с ключом
W9 (seq 1, prev 0, синтетическая цепочка, усиленный PoW, собран хелпером
вне репо) — **reject/E_FINGERPRINT** (чёрный список, R1). Замечание:
register по протоколу всегда seq=1/prev=0 (applyChainChecks), поэтому
«повторный» register — это новая транзакция seq 1 с тем же ключом; ключи
приложения неэкспортируемы (Keystore), демонстрация выполнена на
CLI-кошельке — путь валидации R1 тот же.

## Находки прогона (PENDING — не чинить, фиксация)

1. **E_SIG ~50% на подписях приложения (высокая).** Аудит этапа 9
   (`09738c0`) ввёл строгий каноничный DER + low-s в ядре; подписи Android
   Keystore (BiometricGate/KeystoreWallet.sign, `NONEwithECDSA`) не
   нормализуют s — примерно половина register-подписей приложения
   отвергается E_SIG. В прогоне: регистрации проходили с 4–7-й попытки.
   Go-пути подписи нормализованы (SignDER), Kotlin-путь — нет. Кандидат на
   минор-фикс следующего этапа (нормализация low-s в KeystoreWallet.sign).
2. **Окно челленджа в приложении проверяет не тот период (высокая,
   UI-блокер).** `mobile/query.go MintWindowJSON` передаёт в
   QueryMintWindowOpen текущий период, ядро (M7, №39 — буквальная
   семантика) проверяет слот ЗАЯВЛЯЕМОГО периода. Кнопка Mint отключена
   при фактически открытом окне (скриншот 05) — выпуск из приложения
   практически невозможен (пересечение окон разных периодов ~1/113).
   В 8.1-2 наблюдалось как «окно закрыто», не диагностировано.
3. **IME/текстовый ввод на эмуляторах нестабилен (средняя, блокер
   демо-сценариев).** Lock-экран и отдельные поля периодически «мертвы»
   (ImeTracker: onFailed PHASE_CLIENT_VIEW_SERVED, setFinished
   PHASE_CLIENT_ANIMATION_CANCEL STATUS_TIMEOUT); `input text`/keyevents/
   тапы по клавиатуре не попадают в поле; помогает рестарт Gboard
   (`am force-stop com.google.android.inputmethod.latin`), не всегда.
   Из-за этого: duress-PIN у A не задан (шаг 2.3 заблокирован),
   PIN-диалоги миграции нестабильны. На живых устройствах (блок 8-live)
   требуется проверка.
4. **Генерация ключа с аттестацией падает на сдвинутых часах (средняя).**
   API 36 (Pixel_9): «Failed to generate key pair» мгновенно при часах
   +59 сут; на реальном времени — ок. Регистрации приложения вести в
   реальном времени, сдвигать часы после.
5. **UX-разрыв StartMigration: скрытый случайный nonce (высокая,
   блокер app-миграции).** StartMigrationScreen генерирует nonce
   (`Random().nextInt`) и не показывает его и не принимает ввода;
   гардиан должен подписать MigrateStatement{old, new, nonce, epoch}
   (экран Approve принимает nonce вручную) — владелец не может сообщить
   гардианам правильный nonce. Требуется показать nonce на экране или
   принимать ввод. Протокол миграции проверен CLI-кошельками (2.4–2.6).
6. **configure не выставляет migrate_delay_days (минорная).** Окно отмены —
   параметр сети (genesis 49), но оверрайда в конфигураторе нет; в прогоне
   выставлено пост-обработкой genesis-пакета хелпером вне репо. Кандидат:
   флаг `-migrate-delay-days` в configure.
7. **Эпоха в подписях гардианов чувствительна к границе эпох (информационная).**
   Повторный propose с тем же nonce через границу эпохи даёт
   E_MIGRATE_GUARDIANS (проверка подписи раньше проверки nonce G5) —
   наблюдение для документации approve-флоу: подписи короткоживущие
   (эпоха 300 с в учебной сети).
8. **Урок инфраструктуры:** tnp-node без `-db` — in-memory; рестарт узлов
   стирает журнал (первая серия прогона потеряла эры, переделано с SQLite).
   Для прогонов с рестартами всегда `-db`.
