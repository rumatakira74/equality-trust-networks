## 1. Механика (шаг 1 — протокол и ядро, Go)

- **Тип транзакции** `update_guardians`: TxType 16, payload-тег 25 — закрытый
  перечень 9.3 расширен явным решением владельца (прецедент D2/D4).
  Публикуется в цепочке владельца кошелька, подпись текущим ключом (C8);
  PoW light (не register/mint). Комиссий и наград нет.
- **Payload**: `UpdateGuardiansPropose{NewGuardians ≤ 3, Approvals
  (GuardianApproval: адрес + подпись), Nonce}` / `UpdateGuardiansCancel{
  ProposeSeq}` — ровно один action, как MigratePayload.
- **Хеш смены**: `GuardianChangeStatement{network_id, ward, new_guardians,
  nonce}` (wire/state.go) — каноническое утверждение, подписываемое каждым
  новым гардианом; согласие передаётся вручную (как approve миграции).
  Эпоха в утверждение не входит: окно 48 ч может пересекать границу эпохи,
  подпись не должна протухать на ней.
- **Проверки при публикации** (applyUpdateGuardiansPropose): новый список
  ≤ guardian_personal_count, без дубликатов; каждый новый гардиан — known,
  active, не flagged (№14); лимит подопечных №7 (Wards <
  guardian_personal_max_wards); ровно по одной действительной подписи от
  каждого нового гардиана (VerifyDER над хешем смены); активная смена
  только одна (E_GUARDIAN_UPDATE_ACTIVE); лимит 150 вступивших смен
  (E_GUARDIAN_CHANGE_LIMIT).
- **Окно 48 ч**: константа `GuardianChangeWindowSeconds = 48*3600`
  (не параметр сети; прецедент — отложенный перевод и повышение P).
  До истечения действует старый список, после — новый.
- **Отмена**: подписью владельца (транзакция cancel в цепочке владельца)
  в окне 48 ч; после вступления — E_GUARDIAN_UPDATE_NOTFOUND.
  Только явный ввод PIN — правило приложения (этап 9).
- **Вступление/истечение** (flushPending): при now ≥ EffectiveAt лимит №7
  каждого нового гардиана проверяется заново; при превышении смена
  помечается истёкшей (Expired) и лимит 150 не потребляет. Иначе — новый
  список заменяет старый, счётчик GuardianChanges++.
- **Лимит 150** (решение владельца 21.10.2026): не более 150 вступивших в
  силу смен на кошелёк за всё время; счётчик — поле Wallet.GuardianChanges,
  инкремент при вступлении (детерминирован при replay: flushPending
  вызывается из syncTime детерминированно). Отменённые и истёкшие лимит
  не потребляют.
- **Миграция и списки**: applyMigrate валидирует подписи по текущему
  PersonalGuardians — в окне смены это старый список, после вступления
  новый (тест TestMigrationGuardianListOldAndNew). Интерпретация спеки
  «подписи валидны по списку, действовавшему на момент подписи approve»:
  момент подписи approve ядром не наблюдаем; реализована семантика
  «действующий список на момент публикации propose» — см. PENDING №1.
- **Бухгалтерия wards** (интерпретация №7): при вступлении новые гардианы
  занимают слот (Wards++), ушедшие освобождают (Wards--, пол 0),
  остающиеся не пересчитываются — иначе повторные смены с тем же списком
  исчерпали бы лимит №7 сами о себя.
- **Мост** (mobile/): NewUpdateGuardiansPropose/Cancel,
  GuardianChangeStatementHash, PendingGuardianUpdatesJSON (отсчёт окна,
  статусы canceled/effective/expired), guardian_changes в WalletInfoJSON,
  записи в HistoryJSON («смена гардианов: предложение/отмена»).
  net: QueryPendingGuardianUpdates.

## 2. Приложение (шаг 2 — Flutter/Kotlin)

- **Экран «Гардианы»** (settings/guardians_screen.dart, вход — с экрана
  миграции и из настроек): текущий список, «использовано N из 150»,
  «Перевыбрать», карта активной смены с отсчётом окна, отмена (PIN),
  история смен (Canceled / Took effect / Expired).
- **Перевыбор**: ввод нового списка (≤ 3, hex), хеш смены показывается
  сразу (для передачи гардианам, копируется), ввод пар «гардиан + подпись»,
  публикация — только явный ввод PIN (этап 9), биометрия — разблокировка
  ключа.
- **Экран согласия гардиана**: адрес подопечного, хеш смены, биометрия
  (как ApproveMigrationScreen); подпись передаётся вручную.
- **Тревожный PIN — приманка** (8.2): мост не использует ключ и не
  публикует (signGuardianChange → fake-sig, signTx/submitTx → fake-ok,
  pendingGuardianUpdates → данные легенды); реальный список не меняется.
- **Kotlin-мост**: buildUpdateGuardiansPropose/Cancel, guardianChangeHash,
  signGuardianChange, pendingGuardianUpdates (duress-ветки — как у
  миграции).
- **i18n**: строки в ARB на 5 языках (ru, en, es, pt, zh), fallback en.

### Блокеры прогона и их решения

1. **Приложение не запускалось на эмуляторах** (BLOCKER-emu-app-install.md):
   установка Success, activity «does not exist» (result -92), пакет
   disabled, данных нет — на обоих AVD и на вчерашнем рабочем APK. Причина:
   системный PIN на AVD (остаток прошлых прогонов) → user 0 RUNNING_LOCKED
   после загрузки → сторонние приложения не запускаются. Лечение: -wipe-data.
2. **Сдвиг часов**: `-qemu -rtc base=+50ч` не применяется (guest-часы =
   host-часы через goldfish RTC), `adb root` на playstore-образе недоступен.
   Решение: создан AVD Pixel_9_ga на rootable-образе google_apis (тот же
   API 36), перенесены userdata + **encryptionkey** (без раздела ключей FBE
   userdata пересоздаётся — первая попытка миграции потеряла приложение),
   `adb root` → `date -s`. Для будущих прогонов: либо сразу rootable-образ,
   либо фиксировать способ сдвига часов до прогона.
3. **Вступление смены в узле приложения после рестарта**: сверка журнала
   применяет транзакции с пинированными часами (cons.Replay, C9), поэтому
   flushPending не срабатывает — нужен live-apply (gossip/submit). В прогоне
   триггером стала техническая register CLI-кошелька W9 (accept, gossip).
   См. PENDING №5.

## 6. PENDING

1. **«Подписи для миграции валидны по списку, действовавшему на момент
   подписи approve»** — момент подписи ядром не наблюдаем (в
   GuardianApproval нет времени); реализована семантика «действующий список
   на момент публикации propose» (в окне — старый, после — новый), тесты
   мандата (3.3) проходят. Если владельцу нужна буквальная семантика —
   требуется запись времён/версий списков (решение владельца).
2. **Бухгалтерия wards при смене** — спека не уточняет счётчик №7 для
   update_guardians; реализовано: новые гардианы Wards++, ушедшие Wards--
   (пол 0), остающиеся не пересчитываются. Отменённые/истёкшие смены
   wards не меняют.
3. **Заморозка приложения при таймауте биометрии** (дважды в прогоне;
  лечится перезапуском) — платформенный слой (BiometricGate), не протокол.
4. **Экран History после рестарта приложения/узла показывает «Nothing yet»**
   — история запрашивается до завершения сверки и не обновляется; до
   рестарта записи отображались. UI-баг загрузки, не протокол.
5. **Settle отложенных операций после рестарта узла** — сверка применяет
   журнал с пинированными часами (C9), flushPending срабатывает только при
   live-apply; вступление смены/миграции/перевода может «зависнуть» до
   следующей транзакции. Кандидат на периодический flush по реальным
   часам (решение владельца).
6. **-rtc base не сдвигает guest-часы** (goldfish RTC = хост); для прогонов
   с сдвигом времени использовать rootable-образ (google_apis) + adb root
   date -s, либо иной согласованный способ.
7. **Gossip-фан-аут**: техническая register W9 (триггер сета) не появилась
   в журнале узла n1 при живом экспорте (в узле приложения применилась).
   Наблюдение, на сценарий не влияет; при воспроизведении — кандидат в
   находки net.
