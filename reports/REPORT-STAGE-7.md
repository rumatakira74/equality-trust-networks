# Отчёт: этап 7 — Flutter-приложение поверх платформенного слоя

Ветка: `stage7-flutter` (от `main`, a308bff). Критерий готовности —
полный путь нового участника в эмуляторе: регистрация → гардианы →
поручительства → активация → выпуск → перевод — **выполнен на эмуляторе**
(Pixel_9, API 36; скриншоты `reports/stage7/01–17*.png`).

## 1. Архитектура и управление состоянием

Три слоя (12.1): Flutter (UI) → Kotlin (платформенный слой, этап 6) →
Go (ядро через AAR).

**Управление состоянием: Provider + ChangeNotifier** (`app/lib/state/app_state.dart`).
Выбор против BLoC/Riverpod: состояние приложения — один экран-снапшот
(кошелёк, узел, манифест) с редкими обновлениями; BLoC даёт копию той же
ChangeNotifier-модели в большем объёме кода. Тесты (10/10) мокают
`PlatformService` — интерфейс моста, реализация `MethodChannelPlatformService`
обёрнута тем же интерфейсом.

Поток данных: Flutter-экран → `PlatformService` (абстракция) →
MethodChannel `platform.tnp/app` → `FlutterBridge.kt` → AAR (`mobile/`) →
`net`/`core`. Обратно — JSON-снапшоты (ограничения gomobile: списки —
JSON-строками, числа — int64). Параметры сети приложение не хардкодит:
всё — из `ManifestJSON` (п.1 промпта).

**net/query.go — авторизованное исключение из правила 3** (коммит 2b28a8c,
пометка в коммите: «исключение из правила 3, авторизовано 19.10.2026»).
Причина: data race — ядро без мьютексов, Apply сериализуется приватным
applyMu, фоновый applyLive идёт параллельно с UI-чтением. Сделано:
applyMu → `sync.RWMutex` (Lock — все Apply, RLock — read-only геттеры),
read-only снапшоты состояния для UI. Поведение протокола не изменилось;
`go test -race` на конкурентных apply+query — зелёный. Данные для карты
запросов (п.2 авторизации): прогресс vouch — `Wallet.VouchesReceived` +
`State.Net.Profile.VouchK`; слоты — `SlotCapacity − len(OccupiedSlots)`
(имя `FreeSlots()` обманчиво — возвращает занятые); история —
`AcceptedTxs()`; отложенные — `State.PendingTransfers`; миграция —
`State.PendingMigrations`; окно челленджа — `CheckMintChallengeWindow`;
часы — `State.NetTime/Epoch/CurrentPeriod`; репутация —
AgeDays/Flagged/PublicGuardian/Wards/…; глубина графа — BFS по
vouch-транзакциям журнала.

## 3. Что проверено на эмуляторе (скриншоты `reports/stage7/`)

Полный путь (01–13): биометрия → PIN → выбор гардианов (реестр
синхронизирован с пиром) → register (биометрическая подпись, accepted)
→ vouch×3 от посевного круга V1..V3 → статус ACTIVE → выпуск периода 12
(усиленный PoW, биометрия; баланс 1000 − доля поручителей R ≈ 9.9% = 901)
→ перевод 50 + комиссия 1 (сжигается) → баланс 850, история: регистрация,
выпуск, перевод. Дополнительно: слоты (0 из 0 — слоты растут с возрастом),
реестр (4 кошелька, возраст по часам сети), миграция, QR, BT-экран.

Инфраструктура песочницы: `cmd/tnp-sandbox-peer` — полный узел с
посевным кругом (детерминированные ключи, тот же `SandboxGenesis`),
периоды 1–2 выпускаются автоматически, vouch за каждого нового
REGISTERED кандидата. Для эмулятора пиры запускаются ВНУТРИ эмулятора
(x86_64-сборка, 127.0.0.1:4001/4002): все узлы делят одни часы, а
выпуск по M4 требует завершённого периода (активация в периоде P →
первый выпуск P возможен при текущем периоде ≥ P+1). Часы эмулятора
сдвигались `cmd alarm set-time` (активация при периоде 12, выпуск — при
13). Два пира обязательны: corroboration seq перед подписью требует
согласия 2 пиров (12.4, eclipse).

Латентные баги этапа 6, вскрытые прогоном (коммит b502e37): publicKey
65-байтная точка; DIGEST_NONE+NONEwithECDSA; UNA от initSign;
BiometricGate — свежий промпт при невалидном CryptoObject; порядок
генерации ключа; androidx.biometric 1.4.0-alpha07; TrustedRoots из
genesis (без них E_ATTEST).
