## 1. PIN-лимит (п.1)

**Политика** (PinAttemptPolicy, `android/.../pin/PinAttemptPolicy.kt`;
счётчик — PinAttemptState, SharedPreferences `tnp_pin_attempts`):

| Параметр | Значение |
| --- | --- |
| Порог неудач подряд | 5 |
| Блокировка ввода после порога | 30 с |
| Рост при следующих неудачах | удвоение: 30/60/120/240/480 с, кап 10 мин |
| Сброс счётчика | успешный вход (обычный ИЛИ тревожный — неотличимо, 8.2) или 24 ч без неудач |
| Уничтожение ключа при неудачах | НЕ вводится (опечатка не стоит кошелька) |

**Обоснование.** 4-значный PIN — 10⁴ комбинаций; после ~9 неудач
блокировка достигает капа (10 мин) — полный перебор требует недель
непрерывного ввода при живом экране; каждая попытка дополнительно
стоит PBKDF2 120k итераций. Честный владелец с опечатками
восстанавливается за 30 с. Счётчик не секрет (угроза «стереть данные»
стирает и PIN-файл — это заявленный путь «скрыть можно, обнулить
нельзя», README 8.2). `verify` при активной блокировке не хеширует
(ранний отказ); пустой PIN — отказ без PBKDF2 (см. п. 8, фикс прогона).

**Интеграция:** PinManager.verify (сброс/инкремент), мост
`verifyPin` → `normal | none | locked` + `pinLockRemaining` (мс);
экран блокировки и PIN-диалог деструктивных операций показывают
остаток секунд (l10n ×5: ru/en/es/pt/zh). Политика в спеке/README
8.2 заявлена («ограничение числа попыток») — значения зафиксированы
построчно RU+ENG (спека 8.2, README 8.2).

**Тесты:** JVM `PinAttemptPolicyTest` (рост 30→600 с, кап, окно сброса
24 ч, `AUTH_TIMEOUT_SECONDS == 0`); widget `pin_limit_test.dart`
(5 неудач → сообщение с секундами; в блокировке верный PIN не
проверяется; сброс обычным и тревожным входом; диалог деструктивной
операции).

## 2. FLAG_SECURE (п.2)

**Перечень экранов с пометкой** (окно помечено, пока виден хотя бы
один секретный экран — SecureMode, причины-ключи):

| Экран | Что скрыто |
| --- | --- |
| Вкладка «Кошелёк» (HomeShell) | баланс, история с суммами, отложенные |
| Перевод (TransferScreen) | сумма, получатель, комиссия |
| Выпуск (MintScreen) | сумма выпуска |
| Отложенные (PendingScreen) | суммы отложенных переводов |

Не помечены (публичные данные, UX не ломается): поручительства,
реестр, миграция (адреса без сумм), настройки/гардианы (адреса —
публичное состояние реестра), экран блокировки (нет данных).
Kotlin-приложение (android/): FLAG_SECURE на единственном экране
(баланс/статус).

**Мост:** `setSecureMode(bool)` → `window.setFlags/clearFlags(
FLAG_SECURE)`. **Доказательство в прогоне:** скриншот вкладки
кошелька — полностью пустой (артефакт 06), вкладка настроек в той же
сессии фотографируется (артефакт 07) — рендеринг жив, пустота
вызвана именно флагом.

**Тесты:** widget `flag_secure_test.dart` (пометка на кошельке,
снятие на настройках, удержание при возврате с перевода, пометка
pushed-экранa на публичной вкладке).

## 3. Окно подписи 30 с → 0 (A5)

`AUTH_TIMEOUT_SECONDS = 30 → 0` (`KeystoreWallet.kt`,
setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG)): ключ
без временного окна — каждая операция подписи требует живую
биометрию; авторизация криптографически связана с операцией через
CryptoObject.

**Все пути подписи** (через BiometricGate.signWithBiometric):
перевод, выпуск, отмена отложенного, смена P, миграция
(propose/cancel/statement), смена гардианов, регистрация —
Kotlin-приложение и Flutter-мост. Plain-фолбэк (UNA от initSign,
API 35) без окна подписывает только при успешном повторном initSign
после биометрии, иначе отказ — ослабления нет.

**README 8.1 не менялся** («без временного окна») — код приведён к
заявлению. Комментарии кода синхронизированы.

**Тесты:** JVM `AUTH_TIMEOUT_SECONDS == 0`; прогон — 7 операций
подписи, каждая через CryptoObject-промпт; промпт №5 через 7 с
после подписи №4 (внутри старого 30-с окна) — артефакты 08–10,
logcat (14).

## 4. Приманка (A6)

**Kotlin-приложение** (`MainActivity.kt`): «перевод недоступен» →
правдоподобный путь: сборка tx (тот же PoW и ритм) → тот же
биометрический промпт (plain, без ключа) → «перевод: ожидает
подтверждения».

**Flutter-мост** (все точки ответа приманки):

| Точка | Было | Стало |
| --- | --- | --- |
| signTx | Thread.sleep(400), ok=true (промпта НЕ было — видимый признак) | тот же биометрический промпт (authenticatePlain, та же кнопка «Отмена»), ok по результату |
| submitTx | accepted/fake | accepted/fake → UI: «Перевод отправлен — ожидает подтверждения» (i18n ×5) |
| signMigrateStatement / signGuardianChange | sig="" (пустая строка — видимый признак) | правдоподобная hex-подпись (64 байта SecureRandom) |
| pendingTransfers / pendingMigrations / awaiting | реальные суммы (утечка) | «[]» (легенда без них) |
| balanceWithProof / walletInfo / history | легенда (не менялось) | легенда |

**Реальный реестр не тронут:** в прогоне перевод в приманке (08:10)
не создал tx у пиров — journal_len 10 до и после, новых handleTx нет
(артефакт 15); честный перевод ранее дошёл (TRANSFER seq=2).
Отличимость для владельца сохраняется (владелец сам ввёл тревожный
PIN; выход — обычный PIN, проверено в прогоне).

**Тесты:** widget `decoy_transfer_test.dart` (приманка: ответ
«ожидает подтверждения», журнал мока — только fake-путь, реестр не
тронут; регресс честного перевода — полный путь sign/submit);
обновлён `pin_only_test.dart` (этап 9) на новый ответ.

## 5. A4-константа (№9)

`TargetHard`: `0x0040_0000_0000_0000` (2^54, ~1024 итерации — при
комментарии «2^56, ~64») → **`0x0100_0000_0000_0000` (2^56, ~256
итераций)** в `core/params/params.go` (TestGenesis) и
`core/profiles/profiles.go` (база всех шаблонов). Комментарий
исправлен на честный: ~256 итераций Argon2id 32 МиБ, ~8 с хост.

**Тест «итерации из таргета»** (`core/params/pow_target_test.go`):
ожидаемая работа вычисляется ИЗ константы (2⁶⁴/target = 256) и
сверяется с решением №9 (2^56) для TestGenesis и всех шаблонов
профилей. Регресс PoW: валидный register проходит
(`mobile/query_test.go` — register с усиленным PoW), невалидный →
`E_POW_HARD` (`net/dos_test.go`).

**protocolVersion НЕ поднимался (остался 2):** таргет PoW — параметр
манифеста (идентичность сети через manifest_hash), а не правило
протокола; тестовые сети пересоздаются, живых сетей нет.

**Замер (не запретительный):** хост (i7-1065G7) — поиск nonce для
2^56: 459 итераций, 11,6 с (~25 мс/итерация); прежний 2^54 требовал
бы ~1024 итерации (~25 с). Стоп-вопрос владельцу не потребовался —
правка делает PoW в 4 раза ДЕШЕВЛЕ прежнего фактического значения.
ARM-замер на реальном устройстве — блок 8-live.

## 6. Кодировки надписей (п.7)

**Аудит цепочки** Go (UTF-8) → gomobile/AAR → Kotlin (String, UTF-16)
→ Flutter (Dart) → экран:

- все исходники/ресурсы приложения — UTF-8 (проверено пофайлово);
- байты декодируются в строку в цепочке в одном месте — чтение
  peers.txt; теперь с явным `Charsets.UTF_8` (FlutterBridge);
- логи приложения — logcat (UTF-8 без BOM, артефакт 14);
- строки ресурсов (strings.xml), l10n-каталоги (.arb → generated
  .dart) — UTF-8, без BOM.

**Контрольная сверка «лог против экрана»** (артефакт 17): экраны
ru-локали сфотографированы, OCR (eng-модель) даёт чистые визуальные
аналоги кириллицы («Co3yjaHue KoWeNbKa» = «Создание кошелька»),
сходство с ожидаемыми l10n-строками 0,64–1,00; mojibake-паттерны
(Ð/Ã-последовательности) отсутствуют на всех проверяемых экранах
(онбординг, блокировка, настройки, сообщение лимита). Сбой
кодировки на артефактах прошлых этапов в прогоне НЕ воспроизведён;
статический аудит цепочки искажений не нашёл — сторона приложения
чиста (фикс в корне: явный UTF-8 при декодировании байтов).

**Тесты:** `mobile/encoding_test.go` — строка с кириллицей и
спецсимволами («Сеть доверия №1 — «тест», ünïcode ✓ 日本語») проходит
Go → wire-байты → LoadGenesis → ManifestJSON байт-в-байт (форма,
которую принимает Kotlin и отдаёт во Flutter); widget
`encoding_chain_test.dart` — строка из платформенного слоя
отображается на экране. Для FLAG_SECURE-экранов корректность строк
проверена логом/меткой окна (пустой скриншот = флаг работает,
содержимое — uiautomator-дамп системных промптов + logcat).

## 8. Находка прогона (исправлена в теме, была и на main)

**Пустой PIN брикул экран блокировки.** Android (BouncyCastle)
PBKDF2 отвергает пустой пароль: `SecretKeyFactory.generateSecret` →
`InvalidKeySpecException: Could not generate secret key` (на JVM не
воспроизводится — unit-тест с пустым PIN зелёный). Исключение из
`verifyPin` не перехватывалось в `_submit` → `_busy` залипал →
кнопка «Войти» навсегда отключена (до рестарта приложения). Фикс в
корне: `verify("") → NONE` без хеширования (пустой PIN никогда не
верен — настройка требует 4–16) + try/catch в lock_screen/pin_gate
(платформенная ошибка = «none», `_busy` сбрасывается). Коммит 43d853d.
