# Отчёт: этап 4 — сеть (go-libp2p)

Ветка: `stage4-network` (от `stage3-core`). Пакет `net/` — новый; `core/` не
переписывался (одно исключение — фикс флакующего теста, см. «Отклонения»).
Источники: раздел 12 `docs/KNOWLEDGE.md` v9.2, `spec/`, `core/` этапа 3.

## Что сделано

### 4.1. Хост libp2p — `net/host.go`, `net/config.go`

- Транспорт QUIC + TCP, шифрование Noise; версия зафиксирована в `go.sum`
  (список зависимостей — ниже).
- Peer ID выводится из ключа узла (P-256, `crypto.DeterministicKey` /
  `crypto.GenerateKey`); ключ узла ≠ ключ кошелька.
- Идентификация пиров включает `network_id`: UserAgent = `tnp/<hex(network_id)>`;
  после identify пир с чужим UserAgent отключается немедленно (события
  `EvtPeerIdentificationCompleted/Failed`, `net/host.go:watchNetworkFilter`).
  Все протоколы узла имеют префикс `/tnp/<hex(network_id)>/...`.
- `core/` не переписан: `net/` вызывает `ledger.Ledger`, `store.Store`,
  `smt`, `threshold`, `attest`, `crypto`, `wire`.

### 4.2. DHT (Kademlia) — `net/node.go`, `net/dht-часть`

- Полный узел — режим server, лёгкий — client (12.2), `dht.ModeServer/Client`.
- Ключевое пространство разделено `network_id` двумя способами: префикс
  протокола DHT — `/tnp/<hex(network_id)>` (DHT разных сетей не
  интероперируют), и ключ записи сервиса синхронизации
  `SHA-256("tnp-sync/" || network_id)` (провайдеры записей сети не видны
  другой сети). Полные узлы анонсируют сервис (`Provide`), лёгкие находят
  полные через `FindProvidersAsync`.

### 4.3. GossipSub — `net/gossip.go`

- Тема `tx/<network_id>`; заготовка темы `checkpoint/<network_id>` для этапа 5
  (приём через интерфейс `CheckpointHandler`; проверка пороговой подписи —
  этап 5, здесь только разбор wire-кодирования чекпоинта).
- Политика ретрансляции — валидатор темы (`cheapCheck`): размер, подпись
  (для register — ключ из payload, для остальных — ключ кошелька из
  локального состояния), лёгкий/усиленный PoW по типу транзакции, `seq`/`prev`
  в связке (при seq = tip+1 prev обязан равняться tip). Невалидное не
  пересылается и не публикуется локально (pubsub прогоняет publish через
  валидатор). Полный `apply` — в фоне.
- Дедупликация по `txid`: message ID pubsub = SHA-256(data) = txid.
- Спам: лёгкий PoW + комиссия уже в ядре (12.5); счётчик отклонённых —
  `Stats.SpamRejected`; очередь внеочередных ограничена (4096).
- Эквивокация сетью не отсекается: конфликтная ветка (seq = tip) доставляется
  обеим сторонам, выбор за финализацией (этап 5) — тест
  `TestConflictBranchesDelivered`.

### 4.4. Синхронизация — `net/sync.go`, `net/codec.go`

- Req/res поверх streams, протокол `/tnp/<hex>/sync/1.0.0`: журнал (полная
  сверка из genesis + журнала, INV-3), цепочка кошелька по диапазону `seq`,
  tip, входящие переводы, заголовки чекпоинтов, Merkle-доказательство баланса.
- Replay: при пересчёте журнала часы пинируются на `timestamp_claim` каждой
  транзакции (`net/clock.go:ReplayClock`) — C9 (±30 мин) проверяется на
  момент публикации, а не пересчёта. INV-3: корни состояния узлов сходятся
  (тесты `TestNodesSyncFromScratch`, `TestOfflineNodeCatchesUp`).
- Лёгкий узел (12.5): своя цепочка (`GetWalletRange`), свои входящие
  (`GetIncoming`), заголовки (`GetHeaders`), Merkle-доказательство баланса по
  запросу (`GetProof`, лист = `StateLeaf` из 9 полей, решение D7; проверка
  `core/smt.VerifyProof`) — тест `TestLightNode`.
- Снапшоты из чекпоинтов — интерфейс `SnapshotSource` (`net/levels.go`,
  заглушка `NoSnapshots`); реальные чекпоинты — этап 5.

### 4.5. Bootstrap-каскад — `net/bootstrap.go`, `net/seedlist.go`

Порядок фиксирован (12.3):

1. Кэш прошлых подключений — SQLite `core/store` (meta `peer_cache`, ≤64).
2. Подписанный seed-список — формат полезной нагрузки `net/seedlist`
   (`[версия][network_id][timestamp][пиры]` + `wire.ThresholdSignature`);
   проверка мультиподписи N-из-M через `core/threshold`; свежесть 7 суток
   (предположение, в Документе числа нет). Каналы Telegram/WhatsApp — вне
   кода. Ключи подписантов — синтетические в тестах; реальные — трек
   «Ключи проекта» (раздел 13).
3. Зашитый список (embedded, устаревший fallback) — конфиг.
4. NSD/mDNS — libp2p mDNS в локальной Wi-Fi сети (`mdns.NewMdnsService`,
   сервис `tnp-<hex8>`); при недоступности multicast источник пропускается.
5. Bluetooth-скан — заглушка-интерфейс (`BluetoothScanSource`,
   `ErrNotStage6`); реальный BT — этап 6.
6. QR «добавить узел» и ручной ввод — `ManualAddrs` конфигурации.
7. Peer exchange — протокол `/tnp/<hex>/px/1.0.0` (обмен списками пиров;
   периодический `pxLoop` + раз в каскаде).

«Смешивание источников» — обязательное поведение: кандидаты группируются по
источникам и подключаются по кругу (по одному из каждого источника), до
`MinPeers*2` подключений; данные принимаются только после подтверждения от
N пиров (eclipse, ниже).

### 4.6. Изоляция сетей-инстансов и `invite_only`

- Фильтрация по `network_id` на всех уровнях: UserAgent/identify (немедленное
  отключение чужих), префиксы протоколов (sync/px/DHT), темы gossip, ключи
  DHT. Тест `TestNetworkIsolation`: узел сети 2 подключается к сети 1 —
  соединение закрывается, sync невозможен.
- `invite_only` (12.3): источники 2 (seed-списки) и 3 (зашитый список) не
  используются; адреса первых узлов — из приглашения (`ManualAddrs` =
  QR/ссылка). Тесты `TestInviteOnlyNetwork` (холодный старт первого узла,
  подключение по приглашению, схождение реестра), `TestInviteOnlySkipsChannels`
  (каскад не обращается к запрещённым источникам). Ключ сети из приглашения:
  genesis несёт `InviteKey`; сверка network_id обязательна, использование
  ключа приглашения — этап 6 (QR).

### 4.7. CGNAT: hole punching + relay — `net/cgnat.go`, `net/host.go`

- DCUtR (`libp2p.EnableHolePunching`) для прямых соединений; circuit relay v2
  через добровольные полные узлы (`EnableRelayService` на полном узле —
  конфигурация, не серверы проекта; `EnableNATService`).
- Relay-сервис активен только на достижимых узлах: в продакшене достижимость
  определяет AutoNAT; в тестах/эмуляции — `ForcePublic`.
- Эмуляция CGNAT в тестах: узлы с `NoAnnounce` (адресная фабрика пуста) не
  принимают входящих напрямую; резерв слота на relay (`relayv2client.Reserve`)
  даёт адрес `relay/p2p-circuit/p2p/<node>`. Тест `TestRelayCGNAT`: два узла
  без публичных адресов обмениваются транзакциями через relay.

### 4.8. Уровни узлов — `net/levels.go`, `net/config.go`

- Полный: хранит и проверяет реестр, ретранслирует, DHT server, relay.
- Лёгкий: своя цепочка + входящие + заголовки + доказательства, DHT client,
  опрос входящих `PollInterval` (`net/node.go:lightPollLoop`).
- Переключение по условиям (зарядка + Wi-Fi) — интерфейс `LevelSwitcher`
  (`HeadlessSwitcher`/`FixedSwitcher`); Android-триггеры — этап 6.

### 4.9. Eclipse-защита — `net/eclipse.go` (критерий этапа)

- Подтверждение данных от N несвязанных пиров (`Corroboration`): каждый txid
  учитывается по уникальным Peer ID (gossip-доставка + ответы sync).
  **PENDING: вопрос №35 (добавлен в QUESTIONS.md)** — значение N и критерий
  несвязанности; локальный дефолт N = 3.
- Тест изоляции `TestEclipseIsolation` (обязателен для готовности): узел,
  все источники которого контролируются атакующим, применяет транзакцию, но
  подтверждение < N — единственная версия реестра **не принимается как
  окончательная**; посторонний источник доводит подтверждение до N без
  противоречия (корни сходятся). До финализации (этап 5) это единственный
  статус окончательности.

### 4.10. Офлайн-канал — `net/sidechannel.go`

- Интерфейс `SideChannel`: полезная нагрузка — wire-`Transaction`; in-memory
  реализация `MemSideChannel` для тестов (реальный BT-стек — этап 6).
- Полученное через `OnOfflineTx` кладётся со статусом «ожидает публикации»;
  `PublishAwaiting` проверяет `seq`/`prev` полным apply (12.4: быстрая
  находка эквивокации — конфликт фиксируется, применённой остаётся одна
  ветка) и публикует. «Получено по Bluetooth» ≠ оплата: `OfflineStatus` =
  `awaiting_publication | published | finalized`; финализация — заглушка до
  этапа 5 (подтверждение N пирами). Тесты `TestSideChannelAwaitingPublication`,
  `TestSideChannelPublishPropagates`.

### 4.11. Тесты и CI

- Интеграционные (in-process, localhost/эмерджентные порты):
  `TestNodesSyncFromScratch` (3 узла, схождение корней), `TestOfflineNodeCatchesUp`
  (офлайн-узел догоняет), `TestConflictBranchesDelivered` (обе ветки, без
  падений, инварианты целы), `TestNetworkIsolation`, `TestInviteOnlyNetwork`,
  `TestInviteOnlySkipsChannels`, `TestRelayCGNAT`, `TestLightNode`,
  `TestEclipseIsolation`, `TestSpamNotRelayed` (издатель-нарушитель без
  валидатора: подпись/PoW/размер/чужая сеть + поток 200 tx — не ретранслируются,
  очередь не переполняется, валидные проходят), `TestSeedList*`,
  `TestSideChannel*`, `TestCheapCheckPoW`.
- Отдельными процессами: `TestMultiProcessSync` — сборка `cmd/tnp-node`,
  три процесса на localhost; A публикует, B подключается к A, C — к B; корни
  состояния сходятся.
- Замеры: `TestMeasureGossipThroughput`, `TestMeasureSyncTime` (числа ниже).
- CI: добавлен `.github/workflows/net.yml` (gofmt/vet/test по `net/`, `cmd/`,

## Ручная проверка на отдельных машинах (критерий готовности)

Сборка на каждой машине: `go build -o tnp-node ./cmd/tnp-node`.

1. Машина A (публикатор):
   `./tnp-node -demo-tx -status-file a.json -node-key a`
2. Прочитать адрес A из `a.json` (`addrs[0] + /p2p/ + peer_id`, порт открыть
   в файрволе).
3. Машина B: `./tnp-node -peer <адрес A> -status-file b.json -node-key b`
4. Машина C: `./tnp-node -peer <адрес B> -status-file c.json -node-key c`
5. Убедиться: `journal_len` = 2 у всех, `state_root` совпадает у A/B/C.

Лёгкий узел: `-level light -own-wallet <hex-адрес>`. Relay-узел (CGNAT):
`-force-public`; узел за NAT: `-relay <адрес relay> -no-announce`.
Тестовая сеть: genesis детерминирован от `-network-id` (посевной круг
V1–V3, синтетический корень аттестации); для продакшена распространение
genesis — этап 6.

## Отклонения и найденные проблемы

1. **Флак теста этапа 3** (`core/ledger/e2e_test.go:TestReplayFromStore`):
   `AcceptedTxs()` итерирует map — порядок сохранения в SQLite был
   недетерминирован, replay ломался (E_VOUCH_CANDIDATE при vouch раньше
   register). Воспроизводится на чистой `stage3-core` (`-count=10`).
   Исправлена сортировкой в тесте (каузальный порядок сценария);
   рекомендация этапу 5 — каузальный `AcceptedTxs()` в ядре. Ядро не менялось.
2. **Пробел ядра**: `SeedMembers` не сохраняет публичные ключи посевного
   круга (ключи есть в манифесте) — первый tx посевного кошелька не прошёл
   бы C8. Исправлено фиксапом после `ledger.New` (`net/node.go:seedPublicKeys`)
   без изменения ядра; отметить для этапа 5.
3. **Replay и C9**: пересчёт журнала пинирует часы на `timestamp_claim`
   (иначе C9 ±30 мин отклонял бы старые транзакции). Побочный эффект:
   во время полной сверки живой apply идёт с теми же пинированными часами
   (кратко, сериализовано `applyMu`).
4. **Конфликтные ветки не входят в журнал** (применяется одна ветка) — по
   сети доставляются обе (gossip), но sync переносит только журнал; полный
   перенос конфликтных веток между узлами — вместе с финализацией (этап 5).
5. mDNS в CI-контейнерах не тестируется (нет multicast) — источник
   пропускается каскадом; проверка на реальных Wi-Fi сетях — этап 6.
6. DCUtR hole punching на localhost не наблюдаем (нет NAT) — проверен
  relay-путь; DCUtR включён и сработает на реальных сетях (этап 6).
