FINDING-fix-native-strings-01: нативные строки Android из ARB — остатки и решения владельца

Тема: fix-native-strings (п.а+п.б+п.в FINDING-fix-lang-tails-01). Дата: 05.11.2026.
Ветка: fix-native-strings.

Что закрыто в этой теме
-----------------------
п.а+п.б — строки вне вызова Dart получают источник в ARB:
- шесть ключей добавлены во все девять ARB (шаблон app_en.arb,
  fallback en): appLabel, nodeChannelName, nodeNotificationTitle,
  nodeNotificationText, errTxNotFound, signDefaultTitle;
- gradle-задача generateNativeStrings (app/android/app/build.gradle.kts)
  пишет res/values/strings.xml (en) и res/values-<lang>/strings.xml для
  восьми локалей; запуск — preBuild.dependsOn, то есть до обработки
  ресурсов; сгенерированные файлы в .gitignore и не коммитятся;
- NodeService.kt читает node_channel_name / node_notification_title /
  node_notification_text, FlutterBridge.kt — err_tx_not_found (3 места)
  и sign_default_title;
- label приложения: manifestPlaceholders appLabel по умолчанию
  "@string/app_name" (манифест android:label="${appLabel}"), поэтому в
  сборке конструктора label берётся из ARB и локализуется системной
  локалью; сетевая сборка по-прежнему переопределяет его через
  -P TNP_APP_LABEL.

п.в — AppState.startNode ждёт готовности до 15 с (75 x 200 мс) вместо
5 с и пишет фактическое время ожидания в лог (Stopwatch).

Проверено локально: flutter analyze чисто, flutter test 61/61, сборка
flutter build apk --debug проходит; сгенерированы девять strings.xml,
значения всех девяти локалей сверены с ARB скриптом (RU/EN — глазами),
в APK label и строки присутствуют по локалям (aapt2 dump badging /
resources), android:label разрешается в @string/app_name.

Остатки, не передающиеся через ARB
----------------------------------
1. Хост этапа 6 (android/) остаётся с литералами. NodeService.kt
   компилируется в двух хостах с разными пакетами R, поэтому ресурс
   ищется по имени (resources.getIdentifier), а при отсутствии имени
   берётся прежний литерал. В android/app/src/main/res/values/strings.xml
   имена другие (node_channel, node_notification), поэтому хост этапа 6
   показывает русские литералы. Решение владельца: привести имена
   ресурсов этапа 6 к сгенерированным и добавить там values-<lang>, либо
   оставить как есть (этап 6 — конструкторская сборка, не продукт).

2. Язык нативных строк — системная локаль, язык интерфейса — выбор в
   настройках приложения. Если они расходятся, уведомление узла, label в
   launcher и текст NOTFOUND будут на языке системы, а интерфейс — на
   выбранном. Это штатное поведение Android, но расхождение заметно.
   Варианты: (а) принять; (б) прокидывать выбранный язык в Android
   (LocaleManager / AppCompatDelegate.setApplicationLocales, API 33+);
   (в) для NOTFOUND вернуть приём FINDING-03 — код переводится в Dart
   через ARB (extension LocalizedError), нативное сообщение остаётся
   диагностикой. Сейчас NOTFOUND показывается как
   «Ошибка: NOTFOUND: <строка>» (TnpPlatformException.toString), то есть
   с префиксом кода.

3. Fallback негативной кнопки промпта подписи в FlutterBridge.kt —
   литерал "Cancel" (шаблон ARB). Dart передаёт значение из ARB, литерал
   срабатывает только если аргумент не пришёл; в этой теме не правился.

4. Прочие нативные сообщения моста (Err("NONODE", "узел не запущен") и
   подобные) остаются русскими литералами: это диагностика, пользователю
   показывается перевод по коду (NONODE -> errNoNode). Класс закрыт
   приёмом FINDING-03, в ARB не переносится.

Решения, требующие владельца
----------------------------
1. Сетевые сборки: label остаётся литералом Eq-<hash8> (v9.10, решение 7)
   и не локализуется — это идентификатор сети, а не имя. Подтвердить, что
   для сетевых сборок так и должно быть, а локализованный app_name — только
   для универсальной сборки конструктора.

2. signDefaultTitle в русском ARB совпадает с confirmOperation
   («Подтвердите операцию») — два ключа с одинаковым значением. Оставить
   оба (разная семантика: заголовок промпта подписи и общее подтверждение
   операции) или переиспользовать confirmOperation и убрать ключ.

3. Тест генератора: app/test/native_strings_test.dart покрывает вход
   генератора (шесть ключей в девяти ARB) и совпадение имён ресурсов со
   сборкой и Kotlin, но не сам код генератора — он живёт в
   build.gradle.kts и из Dart не запускается. Фактическая генерация
   проверяется сборкой APK в CI (задача падает на пропавшем ключе).
   Вынос генератора в отдельный скрипт с JUnit-тестом мандатом не
   требовался; нужен ли он — решение владельца.

4. Ресурс-обфускация: NodeService ищет строку по имени (getIdentifier),
   поэтому при включении shrinkResources/обфускации ресурсов поиск
   сломается и строка молча уйдёт в fallback-литерал. Сейчас release
   включает только R8-минификацию кода, ресурсы не обфусцируются. Учесть
   при включении.

5. Замер bootstrap ~11 с взят из мандата; в этой сессии прогона на
   устройстве/эмуляторе не было, поэтому фактическое время в логе
   («TnpNode: готовность узла — N мс») ещё не снято. Нужен эмуляторный
   прогон, чтобы подтвердить запас 15 с.

Замечание по окружению (не относится к правкам)
-----------------------------------------------
Сборка хоста этапа 6 (android/, Gradle 8.11.1) в этом окружении не
запускается: единственная доступная JVM — 25.0.5, Gradle 8.11.1 её не
поддерживает (отказ на старте, до чтения исходников). CI android.yml
использует Java 17, где сборка идёт. Общий файл NodeService.kt
проверен компиляцией во Flutter-хосте (compileDebugKotlin — успешно).
