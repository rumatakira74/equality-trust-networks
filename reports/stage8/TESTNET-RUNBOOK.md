# TESTNET-RUNBOOK — живой прогон закрытой тестовой сети

Статус: **к прогону после появления Android-устройств (блок 8-live)**.
Ранбук написан целиком по результатам эмуляторного прогона этапа 8
(`reports/stage8/testnet-demo-output.txt`, скрипт `testnet-demo.sh`);
всё, что требует живого железа, помечено **[live]**.

## 1. Состав и роли

~10 узлов, локальный Wi-Fi **без выхода в интернет** (12.3: bootstrap-каскад
не нужен — invite_only, адреса первых узлов приходят в приглашении).

| Роль | Кол-во | Кто | Что делает |
| --- | --- | --- | --- |
| Посевной круг | 3 | V1–V3 (ключи детерминированы, в манифесте) | vouch новичкам, чекпоинты (переходный режим до seed_sunset, №15) |
| Полные узлы-раннеры | 2–3 | телефоны владельцев, на зарядке + Wi-Fi (12.2) | DHT-сервер, ретрансляция gossip, сверка журнала |
| Участники полного пути | 3–4 | новые люди | регистрация → vouch×3 → ACTIVE → выпуск → перевод |
| Наблюдатель | 1 | любой телефон | холодный старт с нуля, сверка state_root |

Все устройства: Android ≥ 8 (minSdk 26), биометрия BIOMETRIC_STRONG
(7.2: без настроенного отпечатка регистрация невозможна), Keystore/TEE
(**[live]** StrongBox проверить отдельно, отчёт этапа 6).

## 2. Подготовка (до встречи)

1. `go build ./cmd/tnp-testnet ./cmd/tnp-node` (linux/amd64 для хоста;
   для телефонов всё делает приложение — APK).
2. Генерация сети: `tnp-testnet generate -network-id ИМЯ -out СЕТЬ
   [-genesis-time T]`. Живая сеть: `-invite-key-hex` со случайным ключом
   (32 байта, `openssl rand -hex 32`) — детерминированный ключ только
   для тестов. Проверить таблицу слотов челленджа в выводе generate:
   у посевного круга должен быть хотя бы один достижимый период
   (окно ±48 ч достижимо из периода P+1 только для «поздних» слотов —
   вопрос №39; иначе посевной круг не сможет выполнить V3-условие
   «≥ 2 завершённых периодов выпуска» и не сможет поручаться).
3. Собрать release-APK (`flutter build apk --release`, R8, подпись
   debug/test). **[live]** Установка на устройства разных производителей
   и версий Android — отдельный чек-лист (блок 8-live).
4. Раздать: genesis.bin + приглашение (invite.txt: `tnp://invite?net=…&
   genesis=…&key=…&peer=…`) — QR/ссылка; genesis-файл кладётся в
   `<files>/networks/genesis.bin` приложения (debug-сборка: `adb run-as`;
   release: внешний каталог до первого запуска), пиры — в peers.txt.

## 3. Порядок операций (сценарий прогона)

Шаги, отмеченные *(проверено в эмуляторе)*, повторяют testnet-demo.sh.

### 3.1. Холодный старт сети
1. V1 запускает первый узел (приложение с genesis-файлом или
   `tnp-node -genesis-file genesis.bin -listen /ip4/0.0.0.0/udp/4001/quic-v1`).
   Адрес узла (IP:порт + peer ID) дописывается в приглашения.
2. V2, V3 подключаются по приглашению; сверка журнала с нуля
   (пустая сеть — журнал пуст, сверка успешна). *(проверено в эмуляторе)*
3. Остальные узлы подключаются каскадом по приглашениям/peer exchange.
   Ожидание: все видят peers ≥ 2, журнал_len согласован.

### 3.2. Подготовка посевного круга (выпуски в окнах челленджа)
Посевному кругу нужно ≥ 2 завершённых периодов выпуска (V3) и возраст
≥ 90 дней (V2 — от genesis-времени). Выпуски идут ТОЛЬКО в окнах
челленджа ±48 ч (7.6, №39):
1. Из таблицы слотов (generate-output) выбрать достижимые окна
   (колонка ДОСТИЖИМО) для V1–V3.
2. В окне каждого посевного кошелька — выпуск периода
   (`tnp-testnet mint -seed V1 -period N …` или через приложение).
   Ожидание: accept/OK; вне окна — E_POW_HARD. *(проверено в эмуляторе:
   accept в окне, E_POW_HARD вне окна)*
3. После ≥ 2 выпусков у каждого — посевной круг готов поручаться.

### 3.3. Регистрация участников
1. Участник запускает приложение, проходит онбординг: биометрия →
   PIN (+ тревожный PIN по желанию, 8.2) → выбор гардианов (2 из 3,
   из реестра) → регистрация (усиленный PoW + биометрическая подпись).
   *(проверено в эмуляторе)*
2. Ожидание: кошелёк REGISTERED появляется в реестре всех узлов
   (сверка ≤ 30 с; в маленьких сетях gossip-меш мал — доставка чаще
   через периодическую сверку, фикс этапа 8 — сверка и по событию
   identify).

### 3.4. Поручительства и активация
1. Каждый из V1–V3 поручается за кандидата (vouch, 7.4) — при личной
   встрече через QR/BT или через узлы сети. *(проверено в эмуляторе:
   vouch accept; от кошелька без выпусков — E_VOUCH_PERIODS)*
2. При K = 3 поручительствах кандидат становится ACTIVE. Ожидание:
   статус ACTIVE в реестре, слоты поручителей заняты.
   *(проверено в эмуляторе)*

### 3.5. Выпуск в окне челленджа
1. Участник ждёт завершения периода активации (M4) и своего окна
   (±48 ч; приложение показывает только открыто/закрыто — точный слот
   не публикуется). В окне — выпуск: усиленный PoW + биометрия.
   Ожидание: баланс = эмиссия − доля R поручителям (первые 12
   выпусков, ~10%). *(проверено в эмуляторе: 1000 − R = 901)*

### 3.6. Переводы
1. Обычный перевод: комиссия видна до отправки (fee = max(fee_min,
   rate×amount), сжигается), получатель получает ровно сумму.
   *(проверено в эмуляторе: 50 + fee 1)*
2. Отложенный перевод свыше P = 3000: средства блокируются на 48 ч
   (D), отмена до дедлайна возвращает всё. *(проверено в эмуляторе:
   3500 + fee 35 → pending → cancel → возврат)* **[live]** перевод
   по Bluetooth при личной встрече (12.4) — эмулятор без BT-стека.

### 3.7. Эквивокация и evidence (по договорённости, один кошелёк-«нарушитель»)
1. «Нарушитель» подписывает две ветки выпуска одного seq (разные nonce)
   и публикует обе: первая — accept, вторая — конфликтная ветка
   (EQUIVOCATION_BRANCH_LOST, доставляется обоими). *(проверено)*
2. Любой участник публикует evidence с обеими ветками: кошелёк
   помечается flagged, выпуск приостанавливается на 3 периода (№12),
   повторное нарушение — навсегда; vouch от flagged запрещён (№14).
   *(проверено: accept, E_VOUCH_FLAGGED на повторном vouch)*

### 3.8. Миграция (один доброволец)
1. Новый кошелёк регистрируется; старый (с балансом) предлагает
   миграцию: подписи 2 из 3 личных гардианов (MigrateStatement).
2. Ожидание: pending-миграция (исполнение через 14 дней); отмена
   старым ключом до исполнения. *(проверено в эмуляторе: propose +
   cancel)* **[live]** полный перенос на второе физическое устройство
   с биометрией гардианов при личной встрече.

### 3.9. Тревожный PIN (реалистичный сценарий, по договорённости)
1. Участник с заданным тревожным PIN «сдаёт» телефон условному
   «принуждающему»: вход тревожным PIN открывает режим-приманку —
   правдоподобный остаток и история, интерфейс неотличим, ключ
   подписи не используется. *(проверено в эмуляторе: остаток по
   легенде 847, история пуста, перевод недоступен)*
2. После ухода «принуждающего» — вход обычным PIN, реальный кошелёк
   на месте. *(проверено: 850)*

### 3.10. Холодный старт наблюдателя
1. Свежий узел без журнала подключается к любому узлу сети.
2. Ожидание: полный журнал синхронизируется с нуля, state_root
   совпадает с другими узлами. ⚠ До решения №40 узлы,
   перезапускавшиеся с БД, могут разойтись с холодно стартовавшими
   на сетях с демереджем (в прогоне этапа 8 расхождение было);
   при расхождении — сверить журналы и пересчитать с нуля.
   *(проверено в эмуляторе: журнал 11 tx с нуля)*

### 3.11. Чекпоинты
Переходный режим (посевной круг N-из-M) до seed_sunset (100 active
или 24 эпохи, №15): узлы с ключами посевного круга подписывают
чекпоинты эпох (`tnp-node -wallet V1 …`). Ожидание: чекпоинты в цепочке,
finalized_txid_list фиксирует выбор конфликтных веток. **[live]**
голосование на живых часах суток (в эмуляторе часы сдвигались).

## 4. Требования к среде

- Wi-Fi-точка без интернета; все устройства в одной подсети;
  multicast разрешён (mDNS-обнаружение — шаг 4 каскада; **[live]**
  проверить на реальном роутере).
- Часы устройств: сетевое время недоступно (нет интернета) —
  источник правды для C9 (±30 мин) — часы устройства; **[live]**
  сверить расхождение часов телефонов (допуск ±30 мин, иначе
  транзакции отвергаются E_TIME).
- Зарядка для полных узлов (12.2: полный узел — зарядка + Wi-Fi).

## 5. Критерии успеха прогона

- [ ] 10 узлов на связи ≥ 30 мин, peers ≥ 2 у каждого;
- [ ] посевный круг: ≥ 2 выпусков в окнах у каждого;
- [ ] ≥ 3 участника: регистрация → vouch×3 → ACTIVE;
- [ ] выпуск в окне челленджа у каждого активного участника;
- [ ] обычный перевод с комиссией и отложенный с отменой;
- [ ] evidence на эквивокации: flagged + приостановка выпуска;
- [ ] миграция propose + cancel;
- [ ] тревожный PIN: приманка неотличима, реальный кошелёк цел;
- [ ] холодный старт наблюдателя: журнал и state_root сошлись
      (при расхождении — см. №40);
- [ ] чекпоинты переходного режима в цепочке.

## 6. Известные ограничения (из этапа 8)

1. **№39**: окно челленджа достижимо только для «поздних» слотов —
   до решения вопроса живой прогон может упереться в закрытые окна
   у посевного круга (выбор ключей/имени сети с достижимыми окнами —
   в generate-output).
2. **№40**: расхождение state_root между store-replay и sync-replay
   при демередже — до фикса сверять журналы, не только корни.
3. Конфликтные ветки не доставляются сверкой (только gossip) —
   холодно стартующий узел не видит старых конфликтов; финальность
   восстанавливается чекпоинтами (finalized_txid_list).
4. Малые сети: gossip-меш < 3 пиров — доставка транзакций чаще
   через сверку (≤ 30 с), не мгновенная.
5. SQLite узла в приложении отключён (№38, в памяти) — **[live]**
   проверить на живом телефоне до прогона.
