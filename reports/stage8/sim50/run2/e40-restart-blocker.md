# Ошибка: рестарт узла из БД невозможен при vouch-ах в журнале (№40 — старт-блокер)

Прогон 8.1-2 (50 узлов, эра 2), флот 48 headless-узлов, журнал 143 tx
(4 REGISTER, 20 MINT, 90 VOUCH, переводы, миграция). Зафиксировано
2026-10-20, 17:28–17:45 UTC (сдвинутое время 2026-11-18 20:28–20:31).

## Симптом

`pkill tnp-node` → рестарт 48 узлов из их SQLite-БД (`-db`) → ВСЕ узлы
падают на старте с одинаковой ошибкой и процесс завершается:

```
tnp-node: узел: net: replay: cons: replay: tx 0000…0000: E_VOUCH_EPOCH
```

96 отказов по флоту (48 узлов × 2 попытки — при сдвинутых часах и при
реальных). Флот полностью мёртв, журнал 143 tx заперт в БД: ни один узел
не может подняться, холодный старт не может засинхронить журнал (нет
ни одного живого источника).

Существенно: сдвиг часов НЕ причина — узлы падают так же при
реальном времени. Причина — сами vouch-ы в журнале.

## Корневая причина

`cons.Replay` (пересчёт из БД при старте узла, net/node.go initLedger →
cons.Replay) применяет журнал с часами `pinClock` (cons/replay.go):

```go
func (c *pinClock) NetTime() uint64 { return c.t }   // пинировано
func (c *pinClock) Epoch() uint64   { return c.inner.Epoch() }  // ЖИВЫЕ часы
func (c *pinClock) Period() uint64  { return c.inner.Period() } // ЖИВЫЕ часы
```

`applyVouch` V8 (core/ledger/validate.go) требует `vp.Epoch == текущая
эпоха часов`. Vouch-ы эры 1 созданы в эпохах 26260–26271 (12 разных
эпох за ~1 ч); при replay живая эпоха одна (26300+ на момент рестарта)
— мэтч невозможен в принципе: НИ одна живая эпоха не покрывает
vouch-ы нескольких эпох одновременно. Следствие: любой журнал с
vouch-ами более чем одной эпохи делает рестарт из БД перманентно
невозможным, пока №40 не решён.

Сравнение с известным: в демо этапа 8 №40 проявился как расхождение
состояний (store-replay V3 4899 против sync-replay 4774, Δ125 демереджа,
state_root A/B ≠ C). Здесь — жёстче: не расхождение, а полный отказ
старта. Сетевой путь (net.SyncJournalFrom) применяет vouch-ы корректно —
он пинирует часы каждой транзакции (net.ReplayClock: NetTime И Epoch/
Period от timestamp_claim).

## Решение (авторизовано владельцем; cons не тронут, протокол не изменён)

- `net.Node.ImportJournal(txs)` — применение журнала пинированным
  путём (семантика сетевой сверки): для каждой tx часы пинируются на её
  `timestamp_claim` (net.ReplayClock), apply + postApply + retryPending
  под applyMu. Коммит 65e266f, пометка «БЛОКЕР 8.1-2, авторизовано
  владельцем».
- `tnp-node -import-db ПУТЬ` — загрузка tx из указанной SQLite и импорт
  до старта сети (без гонки с gossip). Узел поднимается с чистой/новой
  БД, `-import-db` указывает на старую.
- Регрессионный тест `TestImportJournalPinnedVouch` (net/integration_test.go):
  vouch прошлой эпохи — живой apply даёт E_VOUCH_EPOCH, ImportJournal
  применяет (пинирование воспроизводит эпоху публикации).

## Результат восстановления

- 48/48 узлов подняты: `импорт журнала из …nodeNN.db: применено 143 из 143`.
- state_root после восстановления ПОЛНОСТЬЮ совпал с состоянием до
  падения (0ed3b3c30fb2828b… — sync-replay семантика в обоих путях),
  50 ACTIVE кошельков, балансы идентичны (S81 5000, S164 980).
- Узлы флота сейчас работают в памяти + импорт (без `-db`): повторный
  рестарт до решения №40 — только через `-import-db`.

## Открытые вопросы

1. №40 повышается до критического: до фикса (пинировать Epoch/Period в
   cons.pinClock, кандидат в этап 9) узлы с vouch-ами в журнале не могут
   переживать рестарт из БД. Живые устройства (приложение) не
   затронуты: у них inMemoryDb (№38) и sync-путь.
2. Импорт — путь восстановления, не замена №40: он не даёт
   store-replay-семантики (демередж по историческим границам) —
   расхождение из демо этапа 8 остаётся открытой частью №40.
