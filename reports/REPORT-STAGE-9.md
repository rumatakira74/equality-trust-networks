## 1. №40 — пинирование Epoch/Period в cons.Replay (старт-блокер 8.1)

`cons.pinClock` пинирует все три метода часов на `timestamp_claim` каждой
транзакции; эпоха/период вычисляются арифметически от genesis (конвенция
30 сут — `net.RealClock`, `mintChallengeSlot`). Семантика — та же, что у
сетевой сверки (`SyncJournalFrom`/`ImportJournal`, `net.ReplayClock`).

Проверка против дофиксного состояния (обе воспроизведены, затем закрыты):

- рестарт из БД с vouch-ами двух эпох — до фикса `NewNode` падал с

  после — узел поднимается, state_root сходится с до-рестартным;
- store-replay против холодной синхронизации — до фикса state_root
  A ≠ B=C и демередж не оседал (Δ из прогона этапа 8), после —
  A=B=C, демередж по историческим границам периодов, ненулевой и

## 2. №41 — позиционный якорь сверки SyncJournalFrom

Якорь = позиция в нумерации журнала ПИРА + txid транзакции на границе
(pos−1). `SyncFromPeer` хранит якорь на каждого пира (`syncAnchors`):
первая сверка — с начала (заодно полный corroboration всего журнала
этим пиром), далее — строго новые транзакции: трафик сверки не
квадратичен по журналу. Пир проверяет якорь: не совпал (перестройка
журнала, другой порядок вставки) — отвечает с начала, сверка
выравнивается; дубликаты отсеиваются дедупом вне cheapCheck.

Закрытый дефект прежней семантики «после своей длины»: ранние
транзакции (позиции пира < своей длины) не доставлялись никогда —
воспроизведено негативным контролём (доверие позиции 1 без якоря:
журнал 2 из 3, ранний пропуск вечен).

Формат `msgGetJournal`: after + blob якоря; старые клиенты (без blob) —
доверие позиции, старые пиры поле игнорируют: деградация к прежнему
поведению в обе стороны.

Тесты: `net/sync_anchor_test.go` — `TestSyncAnchorContinuation`
(продолжение только новыми, 2 из 5; пустая сверка без изменений),
`TestSyncAnchorRealignsOnDivergence` (перестройка у пира — полный проход,
якорь переустановлен, состояние не разошлось),
`TestSyncAnchorDeliversEarlyGap` (ранний пропуск доставляется).

## 3. №42 — cpEpochOverdue при строителе без узла (PENDING, протокол не менялся)

Разбор и 5 вариантов с трейдоффами — в `QUESTIONS.md` (№42), решение за
владельцем: (A) очередь строителей из первых K участников состава,
ротация через epoch/2; (B) строитель только из кошельков с живыми
узлами (liveness не консенсусные данные — фрагментация, eclipse-рычаг);
(C) ускоренный фолббек epoch/2; (D) пропуск застрявшей эпохи (нужно
определение «пустой» эпохи); (E) объявления узлов в реестре (новый тип
данных). Рекомендация разбора: (A), дополнение на случай «весь состав
без узлов» — (D).

Попутная находка разбора: фолббек `cpEpochOverdue` переключается по
ЛОКАЛЬНЫМ часам (`time.Since(epochDueAt)`) — узлы переключаются
«кто-когда», в окне фолббека возможны несколько строителей и та же
фрагментация вариантов, что и блокер 8.1 (один раз за каждую
застрявшую эпоху). Протокол не менялся.

## 5. PIN-only на деструктивных экранах (решение владельца)

Биометрическое ПОДТВЕРЖДЕНИЕ убрано с деструктивных экранов: перевод
(сеть и Bluetooth-платёж), выпуск, миграция propose. Подтверждение —
только явный ввод PIN (`app/lib/screens/pin_gate.dart`: один экран,
один ритм, ответ на тревожный PIN неотличим — приманка активируется на
платформе, операция «проходит» правдоподобно без реальной подписи).
Биометрия после PIN-подтверждения — только разблокировка ключа
Keystore (заголовок «Разблокировка ключа», не подтверждение
операции). Смена/удаление PIN в приложении отсутствует — убирать
нечего (отмечено; при появлении экран обязателен к PIN-гейту по спеке
8.2).

Вход — отпечаток или PIN: LockScreen предлагает отпечаток только когда
приманка не активна (`biometricLoginAllowed`); мост `biometricLogin` →
`BiometricGate.authenticatePlain` (разблокировка без подписи); при
активном тревожном PIN вход по отпечатку отключён.

Тесты (`app/test/pin_only_test.dart`, 5): перевод требует PIN (без PIN
подписи нет, неверный PIN — ошибка неотличима); тревожный PIN на экране
перевода открывает приманку (signFake/submitFake, правдоподобный
успех); тревожный PIN жив после переводов и рестарта; регресс этапа 8 —
с тревожным PIN приложение не блокируется (оба PIN распознаются);
отпечаток отключён при активной приманке. FakePlatformService
моделирует PinManager (оба PIN одним кодом) и decoy-пути signTx/submitTx.

`flutter analyze` — чист; `flutter test` — 15/15; APK debug собирается.
