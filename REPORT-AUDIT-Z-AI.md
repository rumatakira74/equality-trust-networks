### 🔴 AUDIT-Z-01. Недетерминированный возврат донатов при закрытии пула — расхождение состояния между узлами

**Файл:** `core/ledger/modules.go:225-242` (`applyPoolClose`, цикл возврата
по `pool.Donations`), усилитель — `core/ledger/modules.go:514-528`
(`payContribution`, списание из пула).

**Описание:** возврат донатов при `refund_if_unmet` обходит карту
`pool.Donations` (порядок итерации map в Go рандомизирован от запуска к
запуску) и усекает возврат по остатку `pool.Balance`
(`refund := amount; if refund > pool.Balance { refund = pool.Balance }`).
Когда `Balance < ΣDonations`, какой донор получит возврат первым — зависит
от случайного порядка итерации. Узлы, применяющие один и тот же журнал,
получают **разные** состояния.

**Путь воспроизведения (все условия достижимы протоколом):**
1. Профиль с модулями `pool` + `contribution` (валидация комбинаций
   `core/profiles/profiles.go:313-334` это сочетание не запрещает).
2. Донаты A и B в пул с `goal > 0`, `refund_mode = refund_if_unmet`
   (`Balance = 100`, `Donations{A:60, B:40}`).
3. Подтверждённый вклад (2 подтверждения, `ContributionConfirmN = 2`),
   оплаченный из этого пула: `Balance = 70` при ΣDonations = 100.
4. Создатель закрывает пул (`applyPoolClose`): цель не достигнута →
   возврат. Если итерация начнётся с A: A получает 60, B — 10; если с B:
   B получает 40, A — 30. Итоговые балансы A/B и `state_root` различаются
   между узлами.
5. Следствие: `stateRootMatches` (`net/cons.go:848-856`) перестаёт
   сходиться у части узлов — они не подписывают и не принимают чекпоинты;
   голосование/перестройки не лечат (расхождение в применённом состоянии).

**Предложение:** сделать возврат детерминированным: сортировка адресов
доноров перед итерацией (или пропорциональный возврат `amount × Balance /
ΣDonations` с фиксированным округлением); добавить property-тест «два
порядка обхода Donations дают одинаковое состояние». Дополнительно —
рассмотреть запрет drain пула ниже ΣDonations (`payContribution` платит
только сверх донатов), тогда усечение станет недостижимым.

### 🟠 AUDIT-Z-02. Тихое уничтожение предложения: перевод/погашение несуществующему получателю ломает INV-8

**Файлы:**
- `core/ledger/validate.go:760-763` — transfer (free/recurring): списание
  у отправителя выполнено всегда, зачисление — только `if recipient != nil`;
- `core/ledger/modules.go:348-353` — redeem: то же для провайдера;
- `core/ledger/settle.go:169-171` — исполнение отложенного перевода:
  `if rcpt := l.State.Wallet(pt.Recipient); rcpt != nil`.
- Спека: `spec/03-validation.md:120,128` (T2/T10) — существование
  получателя требуется только для restricted/peer-redeem; для free правила нет.

**Описание:** в режиме `free` перевод на произвольный 32-байтовый адрес
(не кошелёк) проходит валидацию: сумма списывается у отправителя, никому
не зачисляется, `TotalBurned` не увеличивается. Аналогично redeem
не-зарегистрированному провайдеру (`inProviders` проверяет только
fingerprint-членство, `core/ledger/modules.go:166-175`, — кошелёк «не
обязан существовать») и исполнение отложенного перевода, чей получатель
к моменту дедлайна исчез из реестра. Нарушается консервация
`INV-8` (`core/ledger/invariants.go:46-59`: Σбалансы + burned = minted),
но **инварианты ядра проверяются только в property/fuzz-тестах** — боевой
узел молча накапливает расхождение учёта.

**Воспроизведение:** transfer на случайный адрес (free-режим) → баланс
отправителя уменьшился, получателя нет, `TotalMinted − TotalBurned` >
Σбалансов.

**Предложение:** выбрать одну семантику и зафиксировать в spec/03:
(a) reject неизвестного получателя (`E_TRANSFER_RECIPIENT` — симметрично
T10), либо (b) «burn-адрес»: инкремент `TotalBurned` на незачисленную
сумму (и в redeem, и в flushPending). Вариант (a) также защищает от
опечаток в адресе.

### 🟠 AUDIT-Z-03. Байт 0x7C ('|') в seq делает отложенный перевод неисполнимым навсегда

**Файлы:** `core/ledger/state.go:347-356` (`WalletByKey` — поиск `|`
с конца), `core/ledger/settle.go:156` (`sender := l.State.WalletByKey(k)`),
ключ строится в `core/ledger/state.go:314-316` (`ptKey = addr ‖ '|' ‖
8 BE-байт seq`).

**Описание:** адрес (32 байта) в ключе не ограничен алфавитом, seq
кодируется 8 байтами big-endian без экранирования. `WalletByKey` ищет
последний `|` — если любой байт seq равен 0x7C (например seq = 124:
`00…00 7C`), разделителем считается байт seq, адрес отрезается неверно,
`Wallets[неверный_ключ] = nil`, исполнение пропускается (`continue`,
`settle.go:158-160`). Отложенный перевод никогда не исполняется; средства
навсегда висят в `Locked` (после дедлайна cancel уже отклоняется —
`E_CANCEL_EXPIRED`, `validate.go:778-780`).

**Оценка вероятности:** для seq < 65536 срабатывает при младшем байте
0x7C (seq = 124, 380, 636 … — каждое 256-е значение seq) либо втором
байте 0x7C (диапазоны 0x7C00–0x7CFF и т. п.). Для долго живущего кошелька
реалистично.

**Смежное (тот же корень):** `cons.ConflictKey` (`cons/vote.go:198-202`)
и `conflictWallet` (`net/cons.go:236-244`) — ключ `wallet|seq` разбирается
сканом с конца; при 0x7C в seq `branchApplied`/`needsRebuild` читают
чужой/несуществующий кошелёк и дают лишний `rebuildToFinality`
(консенсус не ломается — replay детерминирован, но узел зря перестраивает
состояние).

**Предложение:** хранить адрес отправителя полем `PendingTransfer` (и
разбирать ключ конфликта по фиксированной длине: адрес всегда первые
32 байта) вместо эвристики «последний `|`». Тест: seq = 124, отложенный
перевод, дедлайн прошёл — перевод обязан исполниться.

### 🟠 AUDIT-Z-04. Snowball α = 0.6 в коде против утверждённого 0.7 (комментарий, спека, симуляция)

**Файлы:**
- код: `cons/params.go:50` — `SnowballAlpha: 0.6`;
- комментарий там же: `cons/params.go:21-22` — «α = 0,7 (кворум веса:
  живость при доле злонамеренных ≤ 30%…)»;
- утверждённое решение: `docs/development-plan.md:108` — «Snowball k = 10,
  α = 0.7, β = 4» (утверждено 18.10.2026, этап 5);
- симуляция: `sim/sim.go:138` использует 0.7;
- программистская документация: `programming-docs/docs/03-protocol.md`
  («k=10, α=0.7, β=4»).

**Описание:** фактический кворум голосования по конфликтам — 0.6, т. е.
безопасность консенсуса слабее утверждённой (победа ветки атакующего при
весе > ~40% вместо > 30%). Значение — runtime-дефолт каждого узла,
детерминизм не страдает, но параметр безопасности расходится с решением
владельца.

**Предложение:** привести `DefaultParams()` к утверждённому 0.7 (или
переутвердить 0.6 решением владельца и поправить комментарий/спеку/доки).
Кандидат в `QUESTIONS` — «какое значение каноническое».

### 🟠 AUDIT-Z-05. DoS живости чекпоинтов: поток эквивокаций замораживает закрытие эпох сети

**Файлы:** `net/cons.go:361-364` (`if n.hasUnresolvedConflict() { return }`
в `cpTick` до всей логики сборки), `net/cons.go:923-931`
(`hasUnresolvedConflict` — любой `Snowball`-конфликт с `Final = false`),
параметры: `VoteInterval = 2 c` (`net/config.go:160-161`),
`SnowballBeta = 4` (`cons/params.go:51`).

**Описание:** один незавершённый конфликт блокирует сборку чекпоинта у
**всех** узлов (чекпоинт фиксирует сходимость — и правильно). Но конфликт
создаётся дёшево: две валидные транзакции одной пары `seq/prev`
(лёгкий PoW ≈ 0.6 с/tx, `params.go:180`). Конфликт финализируется не
раньше чем за β раундов ≈ 8 с (2 c × 4) и только при устойчивом кворуме.
Атакующий с несколькими кошельками поддерживает ≥ 1 незавершённый
конфликт в каждый момент (новая эквивокация каждые < 8 с), и тогда:
чекпоинты не строятся никогда → замораживаются адаптивная комиссия
(`core/ledger/fee.go` — источник: цепочка чекпоинтов), дедлайны пулов
(`settlePools` по эпохам), `seed_sunset`, финальность `finalized_txid_list`,
границы сетевого времени (`cons.Clock`). Сеть остаётся живой для переводов,
но теряет финализацию на неограниченный срок.

**Обоснование достижимости:** obstacle только «hasUnresolvedConflict»;
список конфликтов глобальный по узлу, лимита числа одновременных
конфликтов нет; очередь `deferred` и DoS-трекер (`net/dos.go`) не
ограничивают темп создания конфликтов легитимно подписанными tx.

**Предложение (по возрастанию сложности):** (a) ограничить одновременные
незавершённые конфликты (например, блокировать чекпоинт только конфликтами
последних K минут, старше — финализировать по FirstWins с записью в
журнал как несогласованные); (b) включать в чекпоинт открытые конфликты
отдельным полем (финализация кошелька-эквивокатора откладывается, но
эпоха закрывается); (c) требовать усиленный PoW для второй ветки конфликта.

### 🟡 AUDIT-Z-06. recurring + модули pool/contribution — комбинация не запрещена genesis-валидацией и бричит переводы

**Файлы:** `core/profiles/profiles.go:343-355` (валидация recurring: только
`unit=quota(resource_id)` и `transfer_mode ∈ {restricted, peer-redeem}` —
про модули тишина), `core/ledger/ledger.go:56-116` (2.6 — тоже),
`core/ledger/modules.go:94-112` (`spendWithFee` → `Spendable` →
`RefreshCohorts`; при `fresh_transfer_window = 0` все когорты уходят в
`Liquid` — `core/ledger/state.go:398-413`), `core/ledger/state.go:443-454`
(`RecurringSpendable` считает **только когорты**).

**Описание:** в recurring-сети любая операция через `spendWithFee`
(донат в пул; non-recurring redeem недостижим, pool-donate достижим при
включённом модуле) конвертирует периодные метки в `Liquid`, после чего
`RecurringSpendable() = 0` навсегда: все переводы дают `E_BURNED`
(`TotalBalance` нетронут, сгорания нет — единицы «заморожены», история не
сходится с семантикой сгорания). Шаблон №8 (subscriber-resource) включает
только redeem — недостижимо через конфигуратор, но достижимо ручным
genesis (валидаций нет ни в `profiles.Validate`, ни в `ledger.New`).

**Предложение:** добавить в `profiles.Validate`/`ledger.New` правило
«recurring ⇒ modules ⊆ {redeem}» (или сделать `RecurringSpendable`
суммирующим и `Liquid`, если семантика допускает).

### 🟡 AUDIT-Z-07. `cons.Clock.Period()` — вторая, несовместимая конвенция периодов (мёртвый код-ловушка)

**Файлы:** `cons/time.go:99-132` (календарные месяцы UTC) против

неиспользуемом месте).

арифметике ядра; если календарная конвенция канонична для v9.5 (якорь
слота №39 «календарные периоды от genesis-времени») — зафиксировать выбор

### 🟡 AUDIT-Z-08. StrongBox жёстко отключён — расхождение с 7.2 (TEE/StrongBox)

**Файл:** `android/app/src/main/kotlin/platform/tnp/android/keystore/KeystoreWallet.kt:145-151`:
`isStrongBoxCapable(): Boolean = false` (константа), `minSecurityLevel()`
всегда 1; `setIsStrongBoxBacked` нигде не вызывается.

**Описание:** `KNOWLEDGE 7.2` и `device_policy = strict` заявляют
«TEE/StrongBox»; фактически ключ всегда генерируется в TEE, StrongBox не
используется даже на совместимых устройствах. Комментарий «StrongBox=2»
остаётся недостижимой веткой. Это не ослабляет текущий minLevel = 1, но
заявленный уровень аппаратной защиты не реализован.

**Предложение:** реализовать детекцию
`PackageManager.FEATURE_STRONGBOX_KEYSTORE` + `setIsStrongBoxBacked(true)`
на API ≥ 28 (или явно зафиксировать в доке, что v1 — только TEE, и убрать
упоминания StrongBox как достижимые).

## Проверено и чисто (чтобы исключить дублирование при следующих аудитах)

**Криптография и подписи**
- ECDSA P-256, каноничный DER, low-s: подпись (`core/crypto/keys.go:52-64`)
  и строгий верификатор (`core/crypto/keys.go:131-174`: high-s, неканоничные
  INTEGER, нулевые/вне-порядка компоненты отклоняются). Ed25519 в коде нет —
  и не заявлен: `spec/00-overview.md:26`, `docs/KNOWLEDGE-4.md:119` (P-256
  подтверждена; Ed25519 — отвергнутая альтернатива).
- Keystore-подписи: `NONEwithECDSA` + `DIGEST_NONE` — подпись готового
  signing_hash без повторного хеширования (`KeystoreWallet.kt:59-91`);
  нормализация low-s на клиенте (`SignatureNormalizer.kt`, поле N совпадает
  с P-256), соответствует строгому верификатору ядра.
- Биометрия: `setUserAuthenticationParameters(0, BIOMETRIC_STRONG)` — окно 0,
  каждая подпись через `CryptoObject`; `setInvalidatedByBiometricEnrollment(true)`
  (`KeystoreWallet.kt:77-83`).
- Fingerprint = SHA-256(pub ‖ protocol_id) (`core/crypto/keys.go:107-112`);
  адрес = SHA-256(fingerprint ‖ network_id), единая точка
  (`core/crypto/address.go:19-34`); привязка листа аттестации к ключу
  SPKI-сравнением (`core/ledger/validate.go:443-457`), challenge-формула и
  challenge-в-цепочке (`validate.go:459-467`).

**Genesis и network_id**
- `network_id = H(manifest ‖ genesis)` с пустым network_id в обоих
  кодированиях; manifest_hash — по манифесту с пустым network_id; цикл
  разорван корректно (`core/wire/genesis.go:487-523`); верификация
  само-сертификации `VerifySelfCertified` (`genesis.go:533-553`); глобальная
