# 2. Genesis-пакет и манифест сети

Источник: разделы 3.1, 3.3, 4, 13, 17.
Схемы: `proto/genesis.proto`.

## 2.1. Структура

```
GenesisPackage {
  Manifest      manifest = 1;  // публичная часть
  GenesisRecord genesis  = 2;  // связка
}
Manifest {
  bytes network_id = 1; string display_name = 2;
  ProfileParams profile = 3;
  repeated SeedMember seed_circle = 4;
  SeedSunset seed_sunset = 5;
  bytes genesis_hash = 6;
}
GenesisRecord {
  bytes network_id = 1; bytes manifest_hash = 2;
  uint64 genesis_time = 3; uint64 epoch_zero = 4;
  uint32 protocol_version = 5;
  SeedSunset seed_sunset = 6; bytes invite_key = 7;
}
```

- Сеть создаёт конструктор: шаблон профиля → параметры → genesis-пакет и
  приложение (3.1). У каждой сети свои `network_id`, genesis, посевной круг
  и профиль; между сетями нет обмена (3.1).
- **Манифест публичен, его хеш записан в genesis, после запуска он неизменен**
  (кроме процедуры раздела 13) — 3.3.
- `manifest_hash = SHA-256(canonical(Manifest))`. Предъявление `attest` несёт
  хеш манифеста: потребитель видит, из какой сети и с какими гарантиями
  приходит «человек» (3.3).
- `network_id` — 32-байтный уникальный идентификатор, генерируется при
  создании сети, входит в манифест и в конверт каждой транзакции (решение D1).
- `invite_key` существует только для `network_access = INVITE_ONLY`: ключ сети
  передаётся в приглашении (QR/ссылка), каналы и зашитые списки не
  используются (12.3); в манифесте не публикуется.
- Состав хеша `genesis_hash` и связка манифест ↔ genesis — PENDING: вопрос №27.

## 2.2. Параметры профиля

Полная таблица параметров — раздел 4 Документа; схема — `ProfileParams`
(`proto/genesis.proto`). Классификация:

- **[P] Защитные** — не меняются никогда, в `mutable_bounds` не входят (13):
  `vouch_k` и правила поручительств (`voucher_min_age_days`,
  `voucher_min_mint_periods`, `slot_tiers`, `seed_slot_count`,
  `slot_free_mint_periods`, `slot_free_days`, `voucher_reward_*`),
  `transfer_delay_hours` (D = 48 ч), `transfer_mode`, размер и режим эмиссии
  (`issuance_mode`, `issuance_amount`, `issuance_period_months`), `unit`,
  `device_policy`, `signing_auth`, `checkpoint_mode`, `params_mutable`,
  `entry_mode`, `registered_expiry_days`, `sandbox`, пороги гардианов
  (`guardian_*_threshold/count`, `guardian_min_age_days`,
  `guardian_max_wards`, `migrate_delay_days`), `timestamp_tolerance_seconds`,
  `mint_challenge_window_hours`.
- **[M] Изменяемые** при `params_mutable = true` — только в границах
  `mutable_bounds` (раздел 2.4): `accrual_window_periods`,
  `demurrage_rate_micros`, `demurrage_floor`, `transfer_moratorium_days`.
- **Значения этапа 1.2** (не зафиксированы в v1): `fee_min`, `rate_min`,
  `rate_max`, `delayed_threshold_default` (P), `delayed_threshold_max`
  (`P_max`), демередж для профилей 5 и 7, параметры PoW, длительность эпохи.

## 2.3. Посевной круг

```
SeedMember { bytes address = 1; bytes public_key = 2; }
```

- Посевной круг задан в genesis и ограничен `seed_sunset` (13). Это
  единственное исключение из «без администратора», и оно самоликвидируется
  по правилу из genesis (1.3, 13).
- Рекомендация: посевной круг ≥ 300 кошельков (7.7, пункт 5: доля фермы к
  60-му месяцу 5,4% при 300 против 12,1% при 100; эффект насыщается после ~300).
- Особые права посевного круга (13): поручитель (10 слотов в первый год, 7.4)
  и подписант чекпоинтов переходного периода (9.1). После `seed_sunset`
  основатели теряют оба права.
- Члены посевного круга получают статус `active` из genesis-чекпоинта эпохи 0
  (решение D8): иначе невозможен холодный старт — поручитель обязан быть
  `active` (7.4), а валидаторов переходного периода подписывает именно посевной
  круг (9.1).
- Первые узлы посевного круга постоянно онлайн в хрупкий период холодного
  старта (первые ~10 узлов, 12.3).

### `seed_sunset`

```
SeedSunset { oneof condition { uint64 active_wallets = 1; uint64 deadline_epoch = 2; } }
```

После порога (число `active`-кошельков или срок) посевной круг теряет особые
права поручителя и подписанта чекпоинтов (13). Параметр в Документе помечен ❓
(раздел 4) и входит в открытый вопрос 3 раздела 18 — PENDING: вопрос №15.
Спецификация фиксирует только механику: узел перестаёт учитывать метку `seed`
при проверке прав с эпохи, следующей за выполнением условия.

## 2.4. `mutable_bounds`

```
MutableBound { string param = 1; uint64 min = 2; uint64 max = 3; }
```

- Для каждого изменяемого параметра в genesis заданы границы `[min, max]`
  (например, ставка демереджа от 0 до 3% — 13).
- Защитные параметры сюда не входят никогда (раздел 2.2).
- Порядок изменения (13): предложение любого `active`-кошелька → публичное
  окно подписей (длительность ❓) → порог ≥ 2/3 `active`-кошельков (❓) →
  публичная задержка активации не менее 30 дней → активация в заданную эпоху.
- **Неретроактивность** (инвариант ядра, 3.2): смена не отзывает статус
  `active`, не меняет прошлые балансы и историю, действует только на будущие
  операции.
- Wire-формат транзакции сигнализации отсутствует в закрытом перечне 9.3 —
  PENDING: вопрос №8. В v1 спецификации сети с `params_mutable = true`
  считаются допустимыми на уровне параметров, но протокол смены кодируется
  после решения вопроса.
- В песочнице `params_mutable` всегда `false` (13).

## 2.5. Уровень гарантий

Вычисляется из манифеста, а не заявляется (3.3). Формула:

```
guarantee_level(manifest):
  if profile.sandbox                          → EDUCATIONAL
  if device_policy = STRICT
     and checkpoint_mode = DECENTRALIZED
     and entry_mode = OPEN_VOUCH               → HIGH
  else                                        → MEDIUM
```

- Высокий — `strict` + `decentralized` + `open_vouch`; средний — `relaxed`
  или `members_quorum`; учебный — `sandbox` (3.3).
- Пограничные случаи (например, `strict` + `members_quorum`) Документом не
  зафиксированы; формула относит их к MEDIUM — PENDING: вопрос №22.
- Партнёр сам выбирает, каким сетям доверять: «репутация без вердиктов» (3.3).

## 2.6. Проверка genesis-пакета узлом

| # | Условие | Результат |
| --- | --- | --- |
| 1 | `SHA-256(canonical(manifest)) = genesis.manifest_hash` | иначе genesis невалиден |
| 2 | `manifest.network_id = genesis.network_id`, длина 32 байта | иначе невалиден |
| 3 | `manifest.seed_sunset = genesis.seed_sunset` | иначе невалиден |
| 4 | Все обязательные поля профиля заданы и непротиворечивы (например, `slot_tiers` покрывают все возраста; `rate_min ≤ rate_max`) | иначе невалиден |
| 5 | `params_mutable = true` ⇒ `mutable_bounds` непуст и не содержит защитных параметров | иначе невалиден |
| 6 | `sandbox = true` ⇒ `params_mutable = false` (13) | иначе невалиден |
| 7 | Посевной круг непуст; рекомендация ≥ 300 (7.7) | предупреждение, не отказ |
| 8 | `network_access = INVITE_ONLY` ⇒ `invite_key` передан вне манифеста | иначе невалиден |
