# 4. Инварианты ядра

Источник: раздел 3.2 (закрытый перечень — расширению не подлежит) плюс
следствия из 7.3–7.5, 9.1, 10.1–10.3, 13, необходимые для property/fuzz-тестов
этапа 3.

## 4.0. Нотация

- `L` — финализированный журнал (последовательность транзакций, упорядоченная
  финализацией); `L_w` — цепочка кошелька `w`.
- `σ = fold(apply, σ_genesis, L)` — состояние, пересчитываемое каждым узлом;
  `σ.balance(w)`, `σ.status(w)`, `σ.flags(w)`, `σ.seq(w)`, `σ.slots(g)` и т.д.
- `params` — неизменные параметры профиля (при `params_mutable` — кусочно:
  `params(e)` для эпохи `e`).
- `accept(tx, σ, params) ∈ {true, code}` — функция проверки из spec/03.
- Утверждение «машино-проверяемо» означает: существует предикат
  `P(L, σ, params) → bool`, вычислимый эталонной реализацией без оракулов;
  в fuzz-тестах (этап 3) генерируются случайные потоки транзакций, и `P`
  проверяется после каждого `apply`.

## 4.1. Инварианты из раздела 3.2

### INV-1. Подписи и запрет двойной траты

```
INV-1a  ∀ tx ∈ L: VerifyECDSA(pk(tx.wallet), signing_hash(tx), tx.signature)
INV-1b  ∀ tx ∈ L: tx.seq = σ.seq(tx.wallet) + 1  ∧  tx.prev = txid(prev_tx)
        (первая транзакция: seq = 1, prev = 0^32)
INV-1c  ∀ w ∀ s: |{ tx ∈ L : tx.wallet = w ∧ tx.seq = s }| ≤ 1
        — по финализированному множеству (см. правку этапа 5 ниже);
          в журнале хранения (store) конфликтные ветки присутствуют обе
INV-1d  ∀ точки финализации: σ.balance(w) ≥ 0
```

Машино-проверяемо: INV-1a — прямая проверка; INV-1b — обход цепочек;
INV-1c — индекс `(wallet, seq)`; INV-1d — после каждого `apply`.
Двойная трата = две транзакции с одним `seq`/`prev` — тривиально
обнаруживается и доказывается (9.1).

> **Правка этапа 5 (авторизована промптом этапа 5; в промпте названа
> «INV-9» — по содержанию это INV-1c и INV-3).** Конфликтные ветки
> (эквивокация, один `wallet`+`seq`, разное содержимое) обязаны попадать
> в журнал хранения: альтернативное множество фиксируется в
> `finalized_txid_list` чекпоинта эпохи (spec/07 7.1). Replay (INV-3)
> применяет ветку, чей txid входит в `finalized_txid_list` покрывающей
> эпохи; проигравшая ветка остаётся в журнале как альтернатива (и как
> материал `evidence`, 7.5). Так пересчёт состояния честно воспроизводит
> выбор финализации, а не только её результат.

### INV-2. Активация только через `vouch`

```
INV-2a  ∀ w: σ.status(w) = ACTIVE ⇒
          |{g : g ∈ activators(w)}| = vouch_k
          ∨ (w ∈ seed_circle ∧ epoch(w) < seed_sunset_epoch)
INV-2b  ∀ w: σ.status(w) = REGISTERED ∧
          (epoch − σ.registered_epoch(w)) > registered_expiry_days ⇒
          σ.status(w) = EXPIRED
```

Активация кошелька — только через K поручительств; посевной круг задан в
genesis и ограничен по времени (3.2). `EXPIRED` терминален: повторная
активация невозможна, требуется новая `register` с новым ключом (7.3).

### INV-3. Реестр публичен внутри сети

```
INV-3  ∀ w: reconstruct(genesis, L, checkpoints) = σ
        ∧ любой узел может вычислить σ.balance(w), σ.status(w), σ.seq(w)
```

Машино-проверяемо: пересчёт состояния из genesis + журнала + чекпоинтов
детерминирован; тест — сравнение состояния полного узла и перестроенного
с нуля (этап 3/5). С правкой этапа 5 (INV-1c): `checkpoints` включает
`finalized_txid_list` — выбор ветки при конфликте восстанавливается из
чекпоинта, а не из порядка прихода транзакций.

### INV-4. Манифест и уровень гарантий

```
INV-4a  SHA-256(canonical(manifest)) = genesis.manifest_hash
INV-4b  guarantee_level = f(manifest)   // вычисляется, не заявляется (3.3)
INV-4c  manifest неизменен после запуска (кроме процедуры раздела 13)
```

### INV-5. Отложенные крупные переводы обязательны

```
INV-5  params.transfer_mode = FREE ∧ params.sandbox = false ⇒
        ∀ tx ∈ L (TRANSFER/send, amount > P(wallet)):
          executed(tx) ⇒ finalized_at(tx) ≥ claimed_at(tx) + 48h ∧ ¬canceled(tx)
```

Правило действует во всех сетях с передаваемыми единицами, кроме песочницы;
отключено быть не может (3.2). Машино-проверяемо: журнал pending-переводов
сверяется с моментами финализации и отмен.

### INV-6. Неретроактивность смены параметров

```
INV-6a  изменение параметра, активированное в эпохе E, не меняет
        σ.status(w) (не отзывает active) и не меняет прошлые балансы и историю
INV-6b  ∀ tx с периодом/эпохой операции < E: tx проверялся по params(до E)
```

Машино-проверяемо: воспроизведение журнала с кусочными параметрами даёт то
же состояние, что и непрерывное применение.

### INV-7. Право форка

```
INV-7  ∀ финализированный чекпоинт C:
        fork_package(C) — валидный genesis (та же история до эпохи C)
```

Любой участник может продолжить сеть на прежних правилах с той же историей
(3.2). Машино-проверяемо: сборка форк-пакета из чекпоинта и проверка
валидности genesis-пакета по spec/02, раздел 2.6.

## 4.2. Следствия для property-тестов (обязательные для ядра)

### INV-8. Сохранение предложения

```
∀ эпохи e:
  Σ_w σ.balance(w) + Σ_pools balance(pool) + burned(e) =
  Σ_mint minted(e) + Σ guardian_reward(e)
```

где `burned(e)` — комиссии и демередж; R-доля поручителям НЕ входит в правую
часть отдельно: её источник — выпуск самого поручаемого (7.4), суммарная
эмиссия не растёт. Награда гардианам — единственное исключение (новая эмиссия,
11). Машино-проверяемо на каждом чекпоинте (`Checkpoint.total_supply`).

### INV-9. Ограничение эмиссии

```
INV-9a  ∀ w ∀ p: |{ tx ∈ L_w (MINT) : p ∈ claimed(tx) }| ≤ 1
INV-9b  Σ_w minted(w, p) ≤ issuance_amount × |{w : σ.status(w) = ACTIVE на p}|
INV-9c  ∀ tx (MINT): claimed(tx) ⊆ [max(activated_period, last+1), current−1]
        ∧ |claimed(tx)| ≤ accrual_window
```

Эмиссия постоянна: 1000 × число `active`-кошельков в месяц (10.1); двойной
выпуск за один период — закрытый перечень `evidence` (7.5); накопление
ограничено окном (10.1).

### INV-10. Мораторий

```
INV-10  ∀ tx ∈ L (TRANSFER/send, REDEEM, POOL_DONATE — расходующие):
          net_time(tx) − register_time(tx.wallet) ≥ transfer_moratorium_days
```

`transfer` с молодого кошелька доступен через 7–30 дней после `register`
(7.6); проверяется каждым узлом, статус не снимает (мораторий от `register`).

### INV-11. Слоты поручителя

```
INV-11a  ∀ g: occupied_slots(g) ≤ S(age(g))   // 3 / 5 / 10
INV-11b  ∀ g ∀ слот s: s.candidate активирован ∧ mint_periods(candidate) ≥ 3
           ∨ age(s) ≥ 90 дней ∧ ¬activated(s.candidate)  ⇒  s освобождён
```

Слоты ограничивают одновременно занятых поручаемых (7.4). Граничный случай
(кандидат `active`, но < 3 периодов выпуска — слот занят неопределённо долго)
— PENDING: вопрос №32.

### INV-12. `flagged` и последствия `evidence`

```
INV-12a  flagged(w) — монотонно: установлен ⇒ не снят никогда
INV-12b  flagged(w) ⇒ mint приостановлен (N месяцев; повтор — навсегда)
INV-12c  flagged(w) ⇒ ∀ p ≥ epoch_evidence: доля R поручителям(w) = 0
INV-12d  денежных штрафов нет: σ.balance(w) не уменьшается фактом evidence
```

### INV-13. Один фингерпринт — один адрес

```
INV-13a  ∀ w1 ≠ w2: fingerprint(w1) ≠ fingerprint(w2)
INV-13b  fingerprint в чёрном списке (миграция, 11) ⇒ register отклоняется
```

Повторная `register` с тем же фингерпринтом и другим адресом отвергается
(7.2); мигрировавший фингерпринт навсегда в чёрном списке (11).

### INV-14. PoW на каждую транзакцию

```
INV-14  ∀ tx ∈ L: pow_valid(tx, params.pow_params)
        ∧ (tx.type ∈ {REGISTER, MINT} ⇒ algorithm = POW_ARGON2ID)
```

Лёгкий PoW на каждую транзакцию, усиленный — на `register` и выпуск (9.3,
7.6).

## 4.3. Формат property/fuzz-тестов (этап 3)

1. Генератор: случайные потоки транзакций (валидные, невалидные, конфликтные:
   два `seq`, дубль-`mint`, отмена вне окна, `vouch` без слота...).
2. Оракул: `apply` по таблицам spec/03 → код `OK`/`E_*`.
3. Проверяем после каждого шага: INV-1..INV-14 (дешёвые — каждый шаг,
   INV-3/7/8 — на границах эпох).
4. Каждое отклонение генератора обязано совпадать с предсказанным кодом `E_*`
   (метаморфный тест: мутация валидной транзакции меняет ровно один код).
5. Тестовые векторы `vectors/` — фиксированные точки того же оракула.
