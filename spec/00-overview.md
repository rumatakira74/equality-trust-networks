## 0.2. Соглашения

- **Хеши** — SHA-256, 32 байта. Нулевой хеш `0^32` — 32 нулевых байта.
- **Подпись кошелька** — ECDSA P-256 (secp256r1), DER-кодировка (раздел 12.1:
  «скорее всего подпись P-256»; подтвердить на целевых устройствах — вопрос 7
  раздела 18). Подпись кошелька не покидает устройство: ключ в Android Keystore
  неэкспортируем (8.1).
- **Время** — Unix-секунды, UTC; календарь UTC (9.2). Источник правды — эпохи
  чекпоинтов. Заявленный `timestamp_claim` допускается при расхождении с сетевым
  временем не более ±30 мин (9.2, 17).
- **Canonical-кодирование protobuf** — поля сериализуются в порядке номеров,
  unknown-поля запрещены, `bytes` — как есть. Все хеши и подписи вычисляются
  только по canonical-кодированию.
- **Адрес кошелька** — 32 байта, функция от `walletFingerprint`
  (раздел 7.2: `walletFingerprint = SHA256(attestedPublicKey ‖ protocolId)`).
  Точная деривация адреса из фингерпринта — PENDING: вопрос №2.
- **protocol_id** — строка UTF-8 `"tnp-v1"`. Рабочее название продукта — открытый
  вопрос 1 раздела 18; строка заменяема до публикации.
- **Идентификаторы полей и код — на английском; пояснения — на русском.**

## 0.3. Правила работы с неполнотой Документа

1. Закрытые перечни (типы транзакций 9.3; инварианты 3.2; последствия
   `evidence` 7.5) не расширяются. Всё новое — только через явное решение
   пользователя, зарегистрированное в `QUESTIONS.md`.
2. Если Документ не определяет механизм, нужный для кодирования, спецификация
   вводит минимальное решение, помечает его `PENDING: вопрос №N` и дублирует
   в `QUESTIONS.md`. Такие места собраны в разделе 0.6.
3. Числа берутся из раздела 17: K = 3, слоты 3/5/10, R = 10%, посевной круг
   ≥ 300 — подтверждены симуляцией (7.7). Значения P, `P_max`, демереджа,
   комиссии — «выбирается прогонами модели, этап 1.2» и в v1 не зафиксированы.

## 0.4. Коды отклонения

Каждая проверка узла (spec/03) завершается кодом: `OK` — принять;
`E_*` — отклонить. Коды стабильны и используются в тестовых векторах и
property-тестах этапа 3.

### Общие (все транзакции)

| Код | Условие отклонения |
| --- | --- |
| `E_NET` | `network_id` не совпадает с сетью узла |
| `E_VER` | `protocol_version` не поддерживается узлом |
| `E_UNKNOWN_WALLET` | кошелёк отправителя не зарегистрирован (нет валидной `register`) |
| `E_SEQ` | `seq ≠ last_seq + 1` (для `register`: `seq ≠ 1`) |
| `E_PREV` | `prev ≠ txid` последней транзакции цепочки (для `register`: `prev ≠ 0^32`) |
| `E_SIG` | подпись ECDSA P-256 неверна над `signing_hash` |
| `E_TIME` | `timestamp_claim` вне ±30 мин от сетевого времени |
| `E_POW_LIGHT` | лёгкий PoW отсутствует или не сходится |
| `E_POW_HARD` | усиленный PoW отсутствует, не сходится или вне окна челленджа |
| `E_TYPE` | `type` не совпадает с активной веткой `payload` |
| `E_DUP` | `txid` уже известен (повторная публикация) |

### По типам (см. spec/03)

`E_ATTEST`, `E_ATTEST_POLICY`, `E_FINGERPRINT`, `E_SBOX` (register);
`E_VOUCH_*` (vouch); `E_STATUS`, `E_FLAGGED_MINT`, `E_MINT_AMOUNT`,
`E_ACCRUAL_WINDOW`, `E_MINT_DOUBLE` (mint); `E_TRANSFER_MODE`,
`E_TRANSFER_RECIPIENT`, `E_MORATORIUM`, `E_BALANCE`, `E_CANCEL_*`,
`E_THRESHOLD_BOUNDS` (transfer); `E_EVIDENCE_*` (evidence);
`E_MIGRATE_*` (migrate); `E_GUARDIAN_*` (guardian_offer);
`E_POOL_*` (pool); `E_REDEEM_*` (redeem/receipt); `E_CONTRIBUTION_*` (contribution).

## 0.6. Реестр решений спецификации (всё — с PENDING в QUESTIONS.md)

| № | Решение | Обоснование из Документа |
| --- | --- | --- |
| D1 | `network_id` включено в конверт транзакции | узлы различают пиров по `network_id` (12.3); защита от replay между сетями |
| D2 | Отмена отложенного перевода и смена P — действия (`oneof action`) внутри типа `TRANSFER`, а не новые типы | закрытый перечень 9.3; механизмы описаны в 8.3, типов для них нет |
| D3 | Отмена миграции — действие внутри типа `MIGRATE`, публикуемое в цепочке старого кошелька | закрытый перечень 9.3; отмена старым ключом описана в 11 |
| D4 | Личные гардианы фиксируются в `register` (назначаются при создании кошелька, 11) | отдельного типа назначения гардианов в 9.3 нет |
| D5 | `pool_id` = txid транзакции `pool_create` | типизированный счёт без адресов (6.3) |
| D6 | Пороговая подпись чекпоинта — N-из-M набор подписей ECDSA P-256, не BLS | сравнение и обоснование — spec/07 |
| D7 | Лист sparse Merkle-дерева включает статус, метки, эпохи — сверх «балансы и seq» | attest (6.1) требует доказуемого состояния из чекпоинта |
| D8 | Члены посевного круга получают статус `active` из genesis-чекпоинта эпохи 0 | иначе невозможен холодный старт: поручитель обязан быть `active` (7.4) |
| D9 | `evidence` публикуется в цепочке подателя (любой кошелёк) | «доказательство подаёт любой узел» (7.5); транзакция требует цепочки и подписи |
| D10 | `redeem`/`pool_donate` наследуют правила списания `transfer` (мораторий, демередж, лёгкий PoW) | «перевод единицы кошельку-поставщику» (6.2), «правила списания — как у transfer» |

## 0.7. Что НЕ входит в спецификацию v1

- Реализация кода протокола (этапы 2–3 плана).
- Сетевой слой: bootstrap-каскад, DHT/gossip, eclipse-защита (раздел 12,
  этап 4).
- Выборочное голосование Snowball-подобное (9.1) — механизм финализации
  между чекпоинтами; его симуляция — этап 5. Спецификация фиксирует лишь
  интерфейс: «побеждает ветка, выбранная финализацией» (7.5).
- Смена параметров (`params_mutable = true`): порядок раздела 13 (предложение →
  окно подписей → порог ≥ 2/3 → задержка ≥ 30 дней → активация в эпоху)
  описан, но wire-формат транзакции сигнализации в закрытом перечне 9.3
  отсутствует — PENDING: вопрос №8.
- Тайные голосования, ZK-доказательства членства (вопрос 9 раздела 18).
