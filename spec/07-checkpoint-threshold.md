# 7. Чекпоинт и пороговая подпись

Закрывает два открытых вопроса этапа 0 (development-plan): формат чекпоинта
и схему пороговой подписи. Источник: разделы 9.1, 9.2, 12.5, 6.1, 13, 17;
открытые вопросы 3 и 7 раздела 18 Документа.

## 7.1. Формат чекпоинта

Чекпоинт — подписанный пороговой подписью хеш корня состояния (9.1):

```
Checkpoint {
  bytes  network_id           = 1;
  uint64 epoch                 = 2;   // эпоха 0 — genesis-чекпоинт
  bytes  state_root           = 3;   // корень sparse Merkle-дерева состояния
  bytes  prev_checkpoint_hash = 4;   // цепочка чекпоинтов
  uint64 network_time          = 5;  // сетевое время эпохи (9.2)
  uint32 protocol_version      = 6;  // (13)
  uint64 active_wallets        = 7;  // для seed_sunset, адаптивной комиссии
  uint64 total_supply          = 8;  // для INV-8 (spec/04)
  repeated bytes participants  = 9;  // состав подписантов M
  uint64 threshold             = 10; // N
  ThresholdSignature threshold_sig = 11;
  repeated bytes finalized_txid_list = 12; // [этап 5] txid, финализированные
                                    // в эпохе (выбранные ветки конфликтов —
                                    // по одной на (wallet, seq); альтернативы
                                    // остаются в журнале хранения, INV-1c)
}
checkpoint_hash = SHA-256(canonical(Checkpoint без threshold_sig))
```

Чекпоинт даёт: детерминированный порядок «до/после», безопасные снапшоты
для лёгких узлов и время для сети (9.1). Снапшоты = state commitments (12.5).

### 7.1.1. Sparse Merkle-дерево состояния

- Лист — `StateLeaf` (балансы, `seq`, статус, метки, эпохи, `last_claimed_period`,
  личный порог P) — решение D7: attest (6.1) требует доказуемого состояния
  (статус, `flagged`) из чекпоинта. Состав листа — PENDING: вопрос №30.
- Индекс листа = адрес кошелька (32 байта); дерево фиксированной глубины
  256 (разреженное); пустой лист → `0^32`.
- `state_root` — корень дерева на конец эпохи; строится каждым полным узлом
  детерминированно.
- Merkle-доказательство (`MerkleProof`) — для лёгких узлов (12.5) и
  предъявлений attest (6.1).

### 7.1.2. Эпохи и время

- Длительность эпохи — параметр `epoch_seconds`; значение ❓ (раздел 17) —
  PENDING: вопрос №16.
- Сетевое время не может сдвигаться между чекпоинтами более чем на заданный
  предел (9.2) — параметр консенсуса этапа 5.
- «1-е число месяца» = первая эпоха, начавшаяся после 00:00 UTC 1-го числа
  по консенсусному времени (9.2).
- В переходном режиме холодного старта первые чекпоинты подписывает
  фиксированный набор ключей посевного круга с жёстким расписанием
  отключения `seed_sunset` (9.1).

## 7.2. Схема пороговой подписи: сравнение и решение

Требования из Документа:

1. Подписанты — кошельки участников; ключи — ECDSA P-256 в Android Keystore,
   неэкспортируемые (7.2, 8.1, 12.1: «в стандартной библиотеке есть ECDSA
   P-256»; BLS в Keystore отсутствует).
2. Три режима (9.1): `decentralized` (выборка валидаторов эпохи),
   `members_quorum` (≥ 2/3 участников, малые сети), переходный посевной круг
   (N-из-M, 9.1; seed-списки тоже подписаны «мультиподписью N-из-M», 12.3).
3. Верификатор предъявлений — лёгкая библиотека Go со сборками JVM и JS (6.1);
   проверка чекпоинта должна быть дешёвой и без тяжёлых зависимостей.
4. Аудит криптографии независимой стороной — этап 9.

### Сравнение

| Критерий | N-из-M набор подписей (ECDSA P-256) | BLS-агрегат |
| --- | --- | --- |
| Ключи подписантов | те же аппаратные ключи Keystore (неэкспортируемые) | требуется ОТДЕЛЬНАЯ BLS-ключевая пара: Keystore BLS не поддерживает → программный ключ вне защищённого железа |
| Связь подписанта с кошельком | прямая: подписант = адрес кошелька | нужна регистрация/делегация BLS-ключа — новый механизм и новая поверхность атаки |
| Зависимости ядра | стандартная библиотека (`crypto/ecdsa`) | pairing-библиотека (blst/herumi) в Go-ядре + JVM + JS |
| Проверка лёгким клиентом | N проверок ECDSA (микросекунды, без новых зависимостей) | pairing (тяжелее, новые зависимости в каждой сборке верификатора) |
| Размер чекпоинта | N × ~72–96 байт (DER ECDSA); при N ≤ сотен и редких эпохах — единицы килобайт | одна подпись ~48–96 байт |
| Проверка «кто подписал» | тривиальна: список `SignatureShare` | агрегат скрывает множество; для N-из-M всё равно нужен список подписантов и, возможно, proof-of-possession |
| Аудит | стандартная ECDSA, экосистема знакома | pairing-кривые (BLS12-381), аудит сложнее |
| Отказоустойчивость | N-из-M: до M − N подписантов могут отсутствовать | то же при порогной схеме, но с программными ключами |

### Решение (этап 0)

**Фиксируется N-из-M набор подписей ECDSA P-256** (`ThresholdSignature` =
`repeated SignatureShare`). Обоснование:

1. Единственная схема, совместимая с аппаратными ключами кошельков: BLS
   потребовал бы вторых, программных ключей — потеря главного преимущества
   платформы (ключ не покидает Keystore, 7.2) и нового вектора кражи.
2. Нулевые новые криптозависимости в ядре (12.1 выбирает Go в том числе
   ради стандартной ECDSA P-256) и в лёгких сборках верификатора (6.1).
3. Издержки (размер O(N), проверка O(N)) пренебрежимы: чекпоинты редкие
   (эпохи), N ограничен размером сети; при 1 млн участников и members_quorum
   2/3 подписей не требуется физически — см. 7.3.
4. Единый механизм для всех трёх режимов и для подписи seed-списков (12.3).
5. Проще аудит (этап 9).

### 7.2.1. Валидность чекпоинта

```
valid_checkpoint(C):
  C.epoch = prev.epoch + 1  ∧  C.prev_checkpoint_hash = checkpoint_hash(prev)
  ∧ |{s ∈ C.threshold_sig.signatures :
       s.signer ∈ C.participants
       ∧ VerifyECDSA(pk(s.signer), checkpoint_hash(C), s.signature)}|
    ≥ C.threshold
  ∧ C.participants соответствует правилам режима (7.3)
  ∧ C.network_time в пределах сдвига от prev.network_time (9.2)
```

## 7.3. Режимы (`checkpoint_mode`, 9.1)

| Режим | `participants` (M) | `threshold` (N) |
| --- | --- | --- |
| `decentralized` | выборка валидаторов эпохи | N ≥ 2/3 M — PENDING: вопрос №17 (правила выборки и порог) |
| `members_quorum` | все `active`-кошельки на эпоху | ≥ 2/3 участников (9.1) |
| переходный (посевной круг) | ключи посевного круга из genesis | N-из-M; состав и порог — PENDING: вопрос №15 (вопрос 3 раздела 18) |

- В `members_quorum` подпись ставит кошелёк участника его же аппаратным
  ключом — дополнительных ключей не появляется.
- Переходный режим действует до `seed_sunset`; после — режим из манифеста.
- Для очень больших сетей в `members_quorum` подписи может собирать
  агрегирующий узел (любой участник), не меняя схемы: набор подписей
  композиционален.

## 7.4. Слоты челленджа выпуска и чекпоинты

Слот челленджа `mint`: `H(address ‖ period ‖ hash(чекпоинта предыдущей
эпохи))` — непредсказуем заранее (7.6). Используется `checkpoint_hash`
финализированного чекпоинта предыдущей эпохи: до его финализации слот
неизвестен никому, включая владельца кошелька.
