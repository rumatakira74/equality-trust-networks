
# Тема Фиксы F5 и F16 (находки аудита контура 1 высокой значимости: подменной адрес приманки, офлайн-финальность) — ветка fix-f5-f16

**Предусловие:** аудиторский прогон контура 1 слит (merge `bce8773`), план обновлён (`9363ea8`). Запуск — по команде владельца (дана). Ветка `fix-f5-f16` — от свежего `main`. Основание: две находки высокой значимости аудита контура 1 (`reports/REPORT-AUDIT-FRONTIER-PASS.md`, п. 2 и п. 5). **F5:** режим-приманка подменяет остаток и историю, но `walletAddress` (`FlutterBridge.kt:354`) возвращает реальный адрес без проверки `duress.active`, карточка восстановления показывает его (`recovery_card_screen.dart:109`, `app_state.dart:84,136`) — заявление README 8.2:404 «адрес в режиме-приманке по сети не совпадёт с реальным» не выполняется локально: принуждающий видит реальный адрес на экране и проверяет баланс любым клиентом — приманка разоблачается. **F16:** порог `eclipse_n` применяется только к `OfflineStatus` (`net/node.go:988` — единственное `Confirmed`), а `Corroboration.Add` (`net/node.go:577`, `net/sync.go:387`) идёт до финальности — 3 соучастника в 3 несвязанных /24 дают жертве «финализировано» для tx, которая проиграет конфликт: двойная трата в офлайн-канале (Bluetooth-платёж). Живых сетей нет. Правило CI-verify: сессия этапа НЕ ждёт статусов CI.

**Цель:** приманка неотличима и по адресу — нападающий не может увидеть или иным путём получить реальный адрес с телефона жертвы в режиме приманки; «финализировано» для офлайн-требования достигается только подтверждениями из финализированных веток — соучастники до финальности его не дают. Честный путь не ломается (латентность подтверждения без неприемлемого роста).

**Задачи:**

1. **F5 — подменной адрес в приманке.** В режиме-приманки ВСЕ точки выдачи адреса возвращают подменной адрес: мост `walletAddress` (`FlutterBridge.kt:354`), карточка восстановления (`recovery_card_screen.dart:109`), `app_state.dart:84,136` и любые другие точки по факту кода — полный список точек в отчёте. Требования к подменному адресу: (а) ≠ реальному; (б) валидного формата — синтаксически неотличим от настоящего; (в) стабильный между сессиями и рестартами (смена адреса выдаёт приманку); (г) НЕ деривируется от реального ключа/фингерпринта; (д) персистентен в легенде приманки (`tnp_duress` — генерируется при создании легенды, живёт с ней). QR карточки восстановления в приманке — подменной адрес (и адреса гардианов — по факту: если легенда приманки уже подменяет их, сверить согласованность; если нет — не расширять скоуп без стоп-вопроса). Реальный адрес не появляется в UI, логах и артефактах прогона, пока активна приманка. Выход обычным PIN — реальный адрес. README 8.2 не трогать — код приводится к заявлению.

2. **F16 — Corroboration только из финальности.** Порог `eclipse_n` и учёт Corroboration должны гейтить «финализировано» офлайн-требования, а не только `OfflineStatus`: подтверждение засчитывается только если оно пришло из финализированной ветки — пир подтверждает tx в контексте финализированного state_root/чекпоинта (точная механика — по факту кода, предложение с обоснованием в отчёте; если видишь несколько равнозначных механик — один стоп-вопрос владельцу до реализации). 3 соучастника до финальности НЕ дают «финализировано» ни при каком раскладе. Честный путь: латентность подтверждения до/после — замер в прогоне п. 4, неприемлемый рост — стоп-вопрос. Если спека описывает семантику Corroboration/подтверждения офлайн — синхронно RU+ENG построчно, только где расходится. `protocolVersion`: если правка F16 меняет приём tx — НЕ поднимать самовольно, стоп-вопрос владельцу.

3. **Тесты.** Обязательные: (1) двойная трата офлайн-канала — tx A подтверждена 3 «соучастниками» до финальности, конфликтная ветка побеждает → «финализировано» не выставляется, OfflineStatus не Confirmed; (2) честный путь — tx подтверждается после финальности → «финализировано» достижимо, латентность в норме; (3) F5 — приманка: адрес стабилен между рестартами, валиден, ≠ реальному; реестр не тронут; выход обычным PIN — реальный адрес; (4) регресс полного честного пути перевода/офлайн-платежа без приманки и конфликтов. По задетым пакетам `-race`.

4. **Контрольный прогон eclipse (headless) + эмуляторный прогон приманки.** Контрольный прогон — по образцу A3-флуда (`cmd/tnp-testnet/flood.go`) и дизайну `reports/audit-frontier-pass/eclipse-sybil-design.md`: жертва — отдельный процесс с отдельной БД (`-role victim`), 3 атакующих на `127.0.0.1` / `127.0.1.1` / `127.0.2.1` (три /24 без контейнеров), негативный контроль `-link-groups=false|true`, метрики — `LinkSpread(txid)` → (peers, groups), `journal_len`, `state_root`, `OfflineStatus(txid)`, латентность честного подтверждения до/после. Доказательство фикса: «финализировано» через соучастников до финальности не достигается ни в одном прогоне; на негативном контроле (без группировки) поведение объяснено. Артефакты — `reports/fix-f5-f16/` (логи .txt; *.log исключается .gitignore). Эмуляторный прогон приманки: экран кошелька и карточка восстановления показывают подменной адрес (скриншоты), реальный адрес в прогоне отсутствует, выход обычным PIN восстанавливает реальный адрес.
