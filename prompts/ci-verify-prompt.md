# CI-verify — подтверждение зелёного CI на ветке (запускается после финального отчёта этапа с «CI pending»)

**Параметр:** имя ветки (подставляется при запуске; например `stage14-attestation`).

**Шаги:**

1. Fast-forward локального `main` до origin; сделать checkout ветки; сверить tip ветки с финальным отчётом этапа — если расходится, остановиться и отчитаться (ничего не перезапускать без сверки).
2. Проверить статусы всех jobs последнего коммита ветки по всем запущенным workflows (core, net, cons, flutter, android) — `gh run list --branch <ветка>` или через GitHub Actions. В сводку: workflow, job, статус, время, номер прогона.
3. Все зелёные → вывести финальную сводку готовности: tip ветки (SHA), таблица jobs, «ветка готова к merge по подтверждению владельца». Коммитить нечего — сводка текстом.
4. Красные jobs → причина по логам прогона. Причина в репо — чинить как мини-задачу: фикс-коммит с пометкой «CI-verify fix»; перед пушем — полный локальный набор (`gofmt -l .` пусто, `go vet ./...` чисто, `go test ./...` зелёные; затронутый Dart — `flutter analyze` чисто; затронутый Kotlin — сборка модуля проходит); после пуша снова дождаться CI и вернуться к шагу 2. Причина вне репо — BLOCKED-external с обоснованием в сводке.
5. Вопросов не задавать; находка вне предмета CI — `FINDING-*.txt` + коммит с пометкой + продолжать; находка с протокольными последствиями — FINDING и остановиться на этом пункте, отчитаться.
6. После прогона: остановить Gradle-демоны и оставленные процессы, проверить `pgrep`.
7. Merge в `main` выполняет сам агент после явного подтверждения владельца в сессии («merge одобрен»): no-ff merge с сообщением в стиле предыдущих этапов, затем push `origin main`; SHA merge-коммита — в сводку. CI на main после merge не ждать (CI pending). Remote-ветки не удалять — удаление за владельцем в GittyUp.

**Правила:** промпт не меняет код, кроме фиксов красных jobs; задачи этапа не повторяет; протокольных решений не принимает.
