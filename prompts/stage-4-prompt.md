## Задача

Сетевой слой поверх ядра: headless-узлы находят друг друга, обмениваются транзакциями и синхронизируют реестр; изоляция сетей-инстансов; защита от eclipse; офлайн-канал как интерфейс. Всё поверх `core/ledger` — валидация и применение уже написаны, сеть только доставляет и запрашивает.

## Подэтапы

### 4.1. Хост libp2p
- Транспорт QUIC + TCP, шифрование Noise; версия `go-libp2p` зафиксировать в `go.sum`, список зависимостей — в отчёт (проверка лицензий по 16.3.4).
- Peer ID из ключа узла; идентификация протоколов включает `network_id` (пир чужой сети отсеивается сразу).
- `net/` — новый пакет; `core/` не переписывать, только вызывать его интерфейсы.

### 4.2. DHT (Kademlia)
- Полный узел — режим server, лёгкий — режим client (12.2).
- Ключевое пространство DHT разделено `network_id` (провайдеры записей сети не видны другой сети).

### 4.3. GossipSub — распространение транзакций
- Тема `tx/<network_id>`; заготовка темы `checkpoint/<network_id>` для этапа 5 (интерфейс подписи — `core/threshold`, сбор подписей не реализуется).
- Политика ретрансляции: дешёвая проверка до gossip (подпись, лёгкий PoW, размер, `seq`/`prev` в связке) — невалидное не пересылается; полный `apply` — в фоне (12.5, спам: лёгкий PoW + комиссия уже в ядре).
- Дедупликация по `txid`; конфликты (эквивокация) **не отсекаются сетью** — доставляются обе ветки, выбор за финализацией (этап 5).

### 4.4. Синхронизация (req/res поверх streams)
- Цепочка кошелька по диапазону `seq`; полная сверка из genesis + журнала (INV-3, replay уже есть в `core/store`).
- Лёгкий узел (12.5): своя цепочка, свои входящие, заголовки чекпоинтов, Merkle-доказательства баланса по запросу (`core/smt`).
- Снапшоты из чекпоинтов — только интерфейс (реальные чекпоинты — этап 5).

### 4.5. Bootstrap-каскад (раздел 12.3, порядок фиксирован)
1. Кэш прошлых подключений (SQLite, `core/store`).
2. Подписанный seed-список: формат полезной нагрузки определить в `net/seedlist`; проверка мультиподписи N-из-M через `core/threshold`. Каналы Telegram/WhatsApp — **вне кода**, только формат; ключи проекта — синтетические для тестов (реальные — трек «Ключи проекта»).
3. Зашитый список адресов (embedded, устаревший fallback).
4. NSD/mDNS: libp2p mDNS-дискавери в локальной Wi-Fi сети.
5. Bluetooth-скан — заглушка-интерфейс (реальный BT — этап 6).
6. QR «добавить узел» и ручной ввод — конфигурация узла.
7. Peer exchange: обмен списками пиров с подключёнными.
- «Смешивание источников» — обязательное поведение (12.3): узел не доверяет единственному источнику.

### 4.6. Изоляция сетей-инстансов и `invite_only`
- Фильтрация пиров по `network_id` на всех уровнях (handshake, DHT, gossip).
- `invite_only` (12.3): адреса первых узлов и ключ сети передаются в приглашении (QR/ссылка = конфиг); каналы и зашитый список не используются; несовместимые пиры отключаются.

### 4.7. CGNAT: hole punching + relay (раздел 12.2)
- Hole punching (DCUtR) для прямых соединений; circuit relay v2 через добровольные полные узлы.
- Ретранслятор — конфигурация полного узла (добровольный, не серверы проекта); эмуляция CGNAT в тестах (узлы без публичного адреса соединяются только через relay/DCUtR).

### 4.8. Уровни узлов (раздел 12.2)
- Полный (хранит и проверяет реестр, ретранслирует, DHT server) / лёгкий (свои данные + заголовки + доказательства, DHT client).
- Переключение по условиям (зарядка + Wi-Fi) — интерфейс + headless-конфиг; Android-триггеры — этап 6.

### 4.9. Eclipse-защита (раздел 12.3, критерий этапа)
- Подтверждение данных от **N несвязанных пиров** (N — параметр, PENDING; локальный дефолт 3, пометить в отчёте).
- Тест изоляции: узел, все источники которого контролируются атакующим, обязан либо получить противоречие от постороннего источника, либо не принять единственную версию реестра как окончательную (до финализации — этап 5).

### 4.10. Офлайн-канал (раздел 12.4)
- Интерфейс `SideChannel`: полезная нагрузка — wire-`Transaction` из `core/wire`; полученный кладётся в `core/store` со статусом «ожидает публикации».
- При публикации — проверка `seq`/`prev` (уже в `core/ledger`); «получено по Bluetooth» ≠ оплата: интерфейс получает статус финализации (заглушка до этапа 5).
- In-memory реализация для тестов; реальный BT-стек — этап 6.

### 4.11. Тесты
1. Интеграционные: N headless-узлов in-process + отдельными процессами на портах; синхронизация реестра с нуля; узел офлайн → подключается и догоняет; конфликтные ветки доставлены обе, никаких падений; `invite_only`-сеть; relay-сценарий без публичных адресов.
2. Eclipse-тест (4.9) — обязателен для готовности этапа.
3. Спам: невалидные (подпись/PoW/размер) не ретранслируются и не переполняют очередь.
4. CI: расширить `core.yml` или добавить `net.yml`; `go test ./...` зелёный, gofmt/vet чистые.

### 4.12. Отчёт `/reports/REPORT-STAGE-4.md`
Что сделано; версии всех зависимостей и их лицензии; замеры (пропускная способность gossip, время полной синхронизации N узлов, память узла, размер служебного трафика); задетые PENDING-вопросы с рекомендациями; что передано этапу 5 (голосование, чекпоинты) и этапу 6 (Bluetooth, Android-триггеры уровней узла).

4. Голосование, чекпоинты, пороговая подпись в работе — этап 5: только интерфейсы.
5. Реальные сетевые порты/адреса в тестах — только localhost/эме­ржентные порты; никаких внешних сервисов.
6. Имена файлов — английские; комментарии в коде — русские. **Все отчёты этапов пишутся только в `/reports/REPORT-STAGE-N.md`** (этап 4 → `/reports/REPORT-STAGE-4.md`), не в пакеты кода.

## Критерий готовности (development-plan, этап 4)

Headless-узлы синхронизируют реестр (в CI — процессы на одной машине, отдельные машины — ручная проверка по инструкции из отчёта); eclipse-тест пройдён; `invite_only`-сеть работает; лёгкий узел получает заголовки и доказательства; офлайн-канал оставляет транзакцию в статусе «ожидает публикации».
