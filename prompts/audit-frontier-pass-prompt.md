# Тема Аудиторский прогон контура 1 (ширина) — ветка audit-frontier-pass (только чтение)

**Предусловие:** тема UI-защиты владельца слита в `main` (merge ветки `ui-owner-protection`) — аудит должен видеть её правки; если ветка ещё не слита — остановись и задай один стоп-вопрос владельцу. Запуск — по команде владельца (дана). Ветка `audit-frontier-pass` — от свежего `main`. **Режим: только чтение и `reports/` — код, спека, README, промпты НЕ трогать; находки не править (правки — отдельные темы по решению владельца).** Основание: план аудитов платформы, контур 1 «ширина» (privacy/следы, спека-vs-код, supply-chain инвентаризация, черновики red-team сценариев, eclipse/sybil дизайн). Живых сетей нет. Правило CI-verify: сессия НЕ ждёт статусов CI.

**Цель:** полная инвентаризация расхождений и каналов утечки по пяти пунктам — каждое наблюдение либо «соответствует», либо точное расхождение с цитатой и файлом/строкой; без единой правки кода и документов.

**Пункты:**

1. **Privacy / следы на устройстве.** Инвентаризация всех каналов, которыми баланс/адреса/суммы/история могут покинуть телефон: (a) содержимое SQLite ядра (core/store) — что именно лежит на диске в открытом виде, пути файлов в приватном каталоге; (b) logcat — все Log.d/Log.i/Log.w/Log.e в android/, app/, mobile/, net/, cmd/ с суммами, адресами, ключами, PIN-намёками; (c) системные скриншоты/превью «недавних» — какие экраны НЕ покрыты FLAG_SECURE (после темы UI); (d) allowBackup/debuggable в манифестах (debug и release); (e) временные файлы/кэш. Каждый канал — файл/строка + оценка (низкая/средняя/высокая) + рекомендация (НЕ реализовывать).

2. **Спека-vs-код.** Сверка заявлений с фактом: README (8.1 аутентификация/окно, 8.2 приманка, 12.5 персистентность, 9.3/9.11, 7.x аттестация) и спека docs/KNOWLEDGE-*.md v9.13 (разделы 7–9, 11) против кода. Каждое заявление — подтверждено/расходится (цитата + файл/строка). Отдельно: дрейф RU/ENG спеки — разделы, где ENG отстаёт от RU (перевод 9.4–9.7 pending), и внутренние противоречия спеки.

3. **Supply-chain инвентаризация.** Полный перечень зависимостей: go.mod/go.sum (прямые + транзитивные, версии, закрепление), app/pubspec.yaml + pubspec.lock, Gradle (build.gradle.kts, версии AGP/compileSdk и т.п.). Для каждой прямой зависимости — известные проблемы безопасности по состоянию знаний модели (без сети; пометка «требует CVE-сверки govulncheck/osv-scanner — контур 2»). Итог — SBOM (таблица или cyclonedx-json) в артефакты.

4. **Черновики red-team сценариев (APK, динамический).** Исполнимые пошаговые сценарии (НЕ исполнять в этом прогоне): tapjacking/overlay против PIN-промпта, task hijacking (taskAffinity), манипуляция intent/exported-компонентами, Frida/Objection-чеклист (обход FLAG_SECURE, hook биометрии, дамп памяти). Для каждого: цель, шаги, ожидаемый признак успеха, контрмера в текущем коде (есть/нет).

5. **Eclipse/sybil дизайн атаки.** Сценарий целенаправленной изоляции якорного/строительного узла против LinkSpread, /24-классификатора (eclipse_n) и seed-пиннинга: параметры атаки (число IP/подсетей, требования к ASN), какие проверки сработают/не сработают, параметры контрольного прогона по образцу A3-флуда (cmd/tnp-testnet). НЕ исполнять.

**Правила:** только чтение + `reports/`; FINDING вне пяти пунктов — в отчёт с пометкой «FINDING вне мандата», не чинить; событийные коммиты (только reports/), после рестарта сессии — сверка живого состояния с последним коммитом; не коммитить файлы больше 1 МБ (логи — .txt, *.log исключается .gitignore), сумма артефактов этапа — до ~5 МБ; стоп-вопрос при блокере (нужно действие владельца / риск ошибки или перерасхода); финал — чистое дерево, пуш ветки `audit-frontier-pass`, отчёт «CI pending» (reports/** не триггерит workflows — свести номера прогонов, если появились); merge в `main` — только после проверки Vibe и подтверждения владельца; в конце — сводка (tip ветки, таблица наблюдений по пунктам 1–5, перечень FINDING, путь отчёта), без вопросов.

**Отчёт:** `reports/REPORT-AUDIT-FRONTIER-PASS.md` — таблицы по пунктам 1–5 (канал/заявление/зависимость/сценарий → файл/строка → статус → рекомендация), SBOM, артефакты `reports/audit-frontier-pass/`. Код и документы не меняются — при merge в main попадают только reports/.
