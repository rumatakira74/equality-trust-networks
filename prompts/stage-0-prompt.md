# Задача: спецификация протокола (Этап 0 плана development-plan)

## Контекст

Ты формализуешь спецификацию платформы сетей доверия по документу `KNOWLEDGE.md` (v9.2), лежащему в рабочей папке. Этот документ — единственный источник истины. Ничего не берёшь из внешних протоколов и не добавляешь от себя.

## Что сделать

1. **Wire-формат транзакций** (раздел 9.3): protobuf-схемы для всех типов ядра
   (`register`, `vouch`, `mint`, `transfer`, `migrate`, `evidence`, `guardian_offer`)
   и модулей (`pool_create`, `pool_donate`, `pool_close`, `pool_claim`,
   `redeem`/`receipt`, `contribution_claim`, `contribution_confirm`, раздел 6).
   Общие поля: `wallet`, `seq` (строго +1), `prev`, `type`, `payload`,
   `timestamp_claim`, `protocolVersion`, подпись ECDSA P-256.
2. **Genesis-пакет и манифест сети** (разделы 3.3 и 4): схема полей всех параметров
   профиля, хеш манифеста, `mutable_bounds`, посевной круг, `seed_sunset`.
3. **Таблицы проверки** для каждого типа транзакции: «условие → принять/отклонить»
   с точки зрения каждого узла. Покрыть: статусы кошелька, возраст поручителя,
   пул слотов, K поручительств, окно накопления `accrual_window`, мораторий
   `transfer`, PoW (лёгкий/усиленный), комиссию, отложенные крупные переводы
   (P, D = 48 ч), демередж, `evidence` и метку `flagged`.
4. **Инварианты ядра** (раздел 3.2) как проверяемые утверждения для будущих
   property/fuzz-тестов — каждое сформулировано формально и Machine-проверяемо.
5. **Тестовые векторы** (файлы): корректная транзакция каждого типа, эквивокация
   (две транзакции с одним `seq`), двойной выпуск, нарушение моратория, выход за
   окно накопления, отмена отложенного перевода.
6. **Машина состояний кошелька**: `registered → active → expired`, метка
   `flagged`, слоты поручителя — диаграмма и таблица переходов.

Дополнительно закрыть два открытых вопроса (раздел 18): формат чекпоинта
(подписанный пороговой подписью корень sparse Merkle-дерева) и схема пороговой
подписи — сравни N-из-M набора подписей и BLS, зафиксируй одну, обоснуй.

## Структура результата

- `spec/` — спецификация в Markdown (разделы 1–6);
- `proto/` — `.proto`-файлы;
- `vectors/` — тестовые векторы;
- `QUESTIONS.md` — всё, чего не хватило в документе.

Идентификаторы полей и код — на английском; пояснения и комментарии — на русском.

## Правила

- Работай **только из документа**; если данных не хватает — не достраивай своей
  фантазией, а выведи вопрос в `QUESTIONS.md` и пометь места спекуляцией как
  «PENDING: вопрос №N».
- Закрытые перечни (типы транзакций, инварианты, последствия `evidence`)
  принципиальны: расширять только по явному указанию.
- Числа бери из раздела 17: K = 3, слоты 3/5/10, R = 10%, посевной круг ≥ 300 —
  подтверждены симуляцией (раздел 7.7). Значения P, `P_max`, демередж, комиссия —
  помечай как «выбирается прогонами модели, этап 1.2».
- Код протокола не реализовывать — только спецификация, схемы и векторы.

## Критерий готовности

Спецификация v1: по ней можно начать этапы 2–3 (криптопримитивы и ядро реестра),
не возвращаясь к проектированию. Каждый тип транзакции имеет wire-формат и таблицу
проверок, инварианты сформулированы проверяемо, тестовые векторы на месте.
