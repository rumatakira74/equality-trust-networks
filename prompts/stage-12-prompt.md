# Промпт: этап 12 — профиль №8 «Абонентский ресурс»: recurring-единицы и идентификация сети

> Контекст: платформа сетей доверия (Equality Project). Решения владельца 27.10.2026 уже внесены в спеку v9.10 (docs/KNOWLEDGE.md + ENG, в main) и план (docs/development-plan.md, «Этап 12»). Порядок (решение владельца): этап 12 реализуется до блока 8-live — эмулятора достаточно, живые Android-устройства не требуются; изменения genesis (network_id, деривация адреса №2) вносятся до первых живых прогонов. Мотивация: организатор привязывает к единице повторяющийся ресурс (процессорное время, дисковое пространство по абонентской плате); бизнесу невыгодно перетекание остатка в новый период. Это коммерческий сценарий — триггер коммерческой лицензии (раздел 16.2): recurring = on — технический маркер коммерческого использования.

## Решения владельца (27.10.2026)

1. `recurring` — периодная метка на единицах: каждая выпущенная единица несёт `period`; перевод единицы периода P отвергается после границы периода P+1. Не сброс баланса: история остаётся публичной и проверяемой. По умолчанию `recurring = off`.
2. Идентификация сети: само-сертифицирующийся `network_id = H(manifest ‖ genesis)` + человекочитаемый `slug` (метка, не идентичность). Зарезервированная константа `network_id = "global"` для глобальной сети; пустого идентификатора нет — `network_id` участвует в подписи и валидации всегда (защита от replay между сетями).
3. Новый режим переводов `peer-redeem`: участник → участнику и участник → поставщику — для потока recurring-квот между участниками.
4. Genesis-валидация комбинаций: `recurring = on` только при не-глобальном `network_id` И `unit = quota(resource_id)` И `transfer_mode ∈ {restricted, peer-redeem}`. В глобальной сети recurring запрещён (нет организатора, определяющего период); комбинация global+rec не существует.
5. Имена файлов APK: `equality-{global|slug}-{std|rec}-v{версия}.apk`; генерируются конфигуратором автоматически из параметров сети. Имя — эргономика и лицензионная прозрачность, не идентичность.
6. `applicationId` на сеть: `io.equality.<slug>` (глобальная — `io.equality.global`); одинаковый `applicationId` у двух сетей недопустим — Android перезапишет чужое приложение вместе с данными кошелька.
7. Label приложения: `Eq-` + первые 8 символов `SHA-256(network_id)` (например `Eq-4f2a9c1d`); не из slug и не обрезкой slug — slug может совпадать у разных организаторов. Глобальная сеть — тот же алгоритм от `network_id = "global"`.
8. `display_name` (вариант 1): человекочитаемое имя сети до ~24 символов, необязательный параметр конфигуратора (по умолчанию `slug`); показывается только внутри приложения (онбординг, экран «О сети», карточка восстановления) и всегда в паре с Eq-хешем («Monte Cloud · Eq-4f2a9c1d»), никогда отдельно; в launcher не используется.
9. Иконка (вариант 3 — гибрид): adaptive icon; background — детерминированный цвет из `SHA-256(network_id)` (палитра Equality, ~16 цветов; одна сеть — один цвет всегда); foreground — логотип организатора (необязательный параметр) или автогенерированный идентикон из `network_id`; для rec-сборок — небольшой бейдж в углу foreground, у std — нет.

### Шаг 2 — ядро: genesis, сгорание, peer-redeem

1. Genesis-поля: `recurring` (on/off, дефолт off), `slug`, деривация `network_id = H(manifest ‖ genesis)`; константа `network_id = "global"`. `network_id` участвует в подписи и валидации транзакций у каждого узла всегда.
2. Genesis-валидация комбинаций: `recurring = on` только при не-глобальном network_id, `unit = quota(resource_id)`, `transfer_mode ∈ {restricted, peer-redeem}`; ошибочные комбинации (recurring в глобальной сети, recurring + free, recurring + не-quota unit, recurring + посторонний transfer_mode) отвергаются при сборке сети.
3. Правило сгорания: каждая выпущенная единица несёт метку периода `period`; перевод единицы периода P отвергается после границы периода P+1 — в валидации `transfer`/`redeem` у каждого узла. Не сброс баланса: история остаётся публичной и проверяемой.
4. Режим `peer-redeem`: перевод участник → участнику и погашение участник → поставщик через `redeem`.
5. Шаблон профиля №8 в `core/profiles` (развитие профиля 3: подписка → равная квота за период → сгорание → передача квоты участниками → погашение поставщиком через redeem); шаблон генерирует валидный genesis-пакет.
6. Тесты: сгорание на границе периода (перевод внутри окна принимается, после границы P+1 отвергается), ошибочные комбинации отвергаются при сборке сети, replay между сетями (транзакция сети A отвергается узлом сети B; `network_id = "global"` участвует в валидации так же).

### Шаг 3 — конфигуратор (cmd/tnp-testnet)

1. Параметры сети: `recurring` on/off, `slug`, `display_name` (необязательно, по умолчанию slug), логотип организатора (необязательно).
2. Автогенерация из параметров: `network_id` (деривация), имя файла APK `equality-{global|slug}-{std|rec}-v{версия}.apk`, `applicationId` `io.equality.<slug>` / `io.equality.global`, label `Eq-` + первые 8 hex `SHA-256(network_id)`.
3. Иконка (adaptive icon): background — детерминированный цвет из SHA-256(network_id) по палитре Equality (~16 цветов), foreground — логотип организатора или автогенерированный идентикон из network_id; для rec-сборок — бейдж в углу foreground, у std — нет.
4. Шаблон профиля №8 доступен в `tnp-testnet configure`; валидация комбинаций выдаёт понятные ошибки.

### Шаг 4 — приложение (Flutter)

1. `display_name` в онбординге, на экране «О сети» и в карточке восстановления — всегда в паре с Eq-хешем, никогда отдельно; в launcher не используется (label целиком `Eq-<хеш>`).

### Шаг 5 — эмуляторный прогон

1. Сеть профиля №8 (recurring=on, transfer_mode=peer-redeem): выпуск квоты за период → перевод внутри периода принимается → перевод через границу P+1 отвергается → peer-redeem участнику → погашение поставщиком (redeem).
2. Тот же шаблон со recurring=off: переводы без сгорания; имена APK различаются (std/rec).
3. Глобальная сеть: recurring=on отвергается при сборке.
4. Скриншоты и артефакты — reports/stage12/01–…; после прогона — уборка процессов (Gradle-демоны, qemu, tnp-node, tnp-testnet).
