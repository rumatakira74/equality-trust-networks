# Этап 14 — аттестация: привязка листа и корни Google (ветка stage14-attestation)

**Предусловие:** этап 13 слит (merge `5469e90`), CI на main зелёный по всем 8 jobs пяти workflows. Запуск — по команде владельца (дана). Ветка `stage14-attestation` — от свежего `main`. Основание: аудит от 01.11.2026 (`reports/AUDIT-equality-trust-networks.md`, разделы A1, A2, A12) — «один человек ≈ один кошелёк» через аппаратную аттестацию в текущем коде не работает.

**Цель:** гарантия начинает работать: регистрируемый ключ привязан к аттестованному листу; цепочки проверяются до настоящих корней Google (оба корня); синтетические корни — только в sandbox; нулевой PoW-таргет вне sandbox отклоняется genesis-валидацией; спека честно отражает, что аттестация даёт и чего не даёт.

**Задачи:**

1. **A1 — привязка листа (критическая).** В `core/attest` / `core/ledger/validate.go` (`applyRegister`): после существующих проверок (цепочка до корня R2/R3, уровень защиты, verifiedBootState/deviceLocked/патч, совпадение challenge R4/R4b) добавить обязательную проверку: SPKI публичного ключа сертификата-листа равен регистрируемому `AttestedPublicKey` (сравнение байтов SPKI). Идентичность адресов не меняется: fingerprint остаётся от ключа, совпадающего с листом. Несовпадение — reject новой ошибкой (например `E_ATTEST_KEY_MISMATCH`); проверка у каждого узла, replay даёт тот же вердикт. Мост (`mobile/mobile.go`) и Kotlin-сторона: убедиться, что в `register` уходит ровно тот ключ, для которого получена цепочка; честный Android-путь не должен сломаться.

2. **A2 — корни Google (высокая).** Убрать детерминированный корень `DeterministicKey("tnp-android-root:" + network_id)` из прод-пути (`mobile/mobile.go` — `TrustedRootsDER`, `cmd/tnp-node/main.go`). Встроить ОБА корневых сертификата Google hardware attestation: действующий RSA-корень и новый ECDSA P-384 (Remote Key Provisioning с 10.04.2026); цепочка валидна, если доходит до любого из встроенных корней; корни — отдельным файлом-набором, добавление корня при ротации — коммит. Сертификаты брать ТОЛЬКО из официальных источников Google (страница attestation root / публикация нового корня); если в среде нет сети — статус BLOCKED-external с обоснованием, сертификаты из памяти модели не воспроизводить. Синтетические корни: разрешены только для genesis с `sandbox = true` — genesis-валидация: не-sandbox сеть с синтетическими корнями → reject. Тестовые векторы и юнит-тесты, использовавшие синтетику, перевести на sandbox-genesis или test-only внедрение, не ослабляя прод-валидацию.

3. **Срок цепочки при replay.** Сертификаты устройств короткоживущие (~2 мес): валидность листа проверять на момент `tx.TimestampClaim` (NotBefore ≤ TimestampClaim ≤ NotAfter), а не на часы узла — чтобы replay старых регистраций не расходился с live. Сделать минимально для аттестации; более широкий txNow-рефакторинг — этап фикса времени, не трогать, отметить в отчёте.

4. **A12 — target=0.** Genesis-валидация: вне sandbox отклонять genesis с нулевым PoW-таргетом (молчаливое отключение PoW запрещено); в sandbox допустимо (симуляции).

5. **Спека и манифест гарантий (честная правка, RU+ENG синхронно).** `docs/KNOWLEDGE-1..5.md` и `docs/KNOWLEDGE-ENG-1..5.md` (v9.11 → v9.12, перечень правок в шапке): 7.1/7.2 — аттестация подтверждает настоящее устройство с защищённым железом, но НЕ уникальность устройства (несколько attested-ключей на устройстве возможны и после фикса; основной барьер — поручительства); 7.6 — формулировка «ферма = ферма дорогих устройств» после A1; 3.3/манифест — строгая аттестация теперь обеспечена корнями Google, но без замера на живых устройствах не заявлять больше проверенного (DISCLAIMER остаётся). README — только в части аттестации. Поля 61/51 и семантика M4/M5 — НЕ в этом этапе (заходом с фиксом времени).

**Тесты (обязательные):**

- Негативные: валидная цепочка + AttestedPublicKey != SPKI листа → reject; не-sandbox genesis с синтетическим корнем → reject; не-sandbox genesis с target=0 → reject; лист просрочен на момент TimestampClaim → reject.
- Положительные: существующие векторы и тесты регистрации зелёные; sandbox-сеть с синтетикой и target=0 работает (симуляции не ломаются); регистрация с совпадающим листом принимается.
- Регресс: replay-изоляция сетей и векторы (`vectors/`) не падают.

**Предкоммитная проверка (обязательно):** `gofmt -l .` — пусто; `go vet ./...` — чисто; `go test ./...` — зелёные (в CI с `-race`); форматирование — отдельным коммитом от смысловых правок (`gofmt -w`, пометка «formating only»). Dart — `flutter analyze` чисто; Kotlin — сборка модуля проходит. Итог: зелёный CI на ветке по всем jobs или BLOCKED-external с обоснованием в отчёте.
