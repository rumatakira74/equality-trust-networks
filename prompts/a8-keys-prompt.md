# Тема A8 — ключи подписи APK (боевая release-подпись: единый std + отдельный rec) — ветка a8-keys

**Предусловие:** тема fuzz-долгов слита (merge `d5d3e86`), CI main зелёный. Ветка `a8-keys` — от свежего `main`. Основание: находка A8 аудита (`reports/AUDIT-equality-trust-networks.md`: release-APK подписан debug-ключом — `android/app/build.gradle.kts`; подтверждена повторным аудитом 01.11.2026) и «release debug-подпись» (средняя) аудита контура 1 (`reports/REPORT-AUDIT-FRONTIER-PASS.md`). Решения владельца: единый боевой ключ для всех std-сетей + отдельный боевой ключ для rec-сетей (recurring; комбинация global+rec не существует по genesis-валидации — глобальная сеть всегда std); точка конфигурации — в конфигураторе; приватные ключи не покидают машину владельца (CI — без боевых ключей). Живых сетей нет. Правило CI-verify: сессия темы НЕ ждёт статусов CI.

**Цель:** release-сборки обоих видов (`equality-{global|slug}-{std|rec}-v*.apk`) подписываются боевыми ключами (std — все std-сети, rec — все rec-сети); приватные ключи и пароли не появляются ни в git, ни в CI, ни в логах, ни в отчёте; отпечатки сертификатов опубликованы в репо; CI работает без боевых ключей.

**Задачи:**

1. **Инвентаризация подписи (шаг 0).** По факту кода: как подписываются сборки сейчас (`android/app/build.gradle.kts` — release с debug-подписью, flutter/android-джобы CI), как конфигуратор `cmd/tnp-testnet configure` генерирует сборочные параметры сети (имя APK по конвенции, `applicationId`, label Eq-хеш, иконка) и как эти параметры доходят до сборки. Таблица «точка сборки → текущая подпись → где задаётся» — в отчёт.

2. **Боевые ключи std + rec (генерация локально).** Два keystore: `tnp-std` и `tnp-rec`, генерация на этой машине локально keytool'ом: каталог вне клонов репо (по умолчанию `~/.tnp-signing/`, можно переопределить), RSA, размер и срок валидности — по стандартной практике Android-подписи с обоснованием в отчёте (срок ≥25 лет), отдельные пароли keystore и ключа, разные для std и rec. Пароли сгенерировать и сохранить в `~/.tnp-signing/credentials.txt` (chmod 600): в отчёт, лог и артефакты пароли НЕ печатать — только путь к файлу. Приватные ключи не попадают в git: `.gitignore`-паттерны (`*.jks`, `*.keystore`, локальные signing-конфигурации с паролями); в предкоммитной сверке — `git status` чист и `git ls-files '*.jks' '*.keystore'` пуст. Если для генерации или каталога нужно действие, доступное только владельцу — стоп-вопрос (один конкретный).

3. **Точка конфигурации подписи в конфигураторе.** `configure` по типу сети выбирает ключ (std → `tnp-std`, rec → `tnp-rec`; глобальная сеть — std) и подключает его к release-сборке; signing-конфиг (пути/пароли) читается из локального файла вне git (генерируется `configure` или первым запуском; путь передаётся флагом или env, дефолт — `~/.tnp-signing/`); отсутствие или недоступность ключей — явная диагностика и отказ собирать release; debug-сборки не затрагиваются. CI-джобы и workflows не править: боевых ключей в CI нет и не появится; если текущие CI-джобы release-сборки затрагиваются твоими правками — зафиксируй в отчёте отдельным пунктом, workflows без стоп-вопроса не менять. Если видишь несколько равнозначных механик подключения signing-конфига — один стоп-вопрос владельцу до реализации.

4. **Сборка и верификация.** Собрать release-APK обоих видов (std-сеть и rec-сеть; тестовые genesis из `cmd/tnp-testnet`), имена по конвенции; подписать боевыми ключами; `apksigner verify --print-certs` — отпечатки SHA-256 сертификатов в отчёт; установка и запуск одной release-APK (std) в эмуляторе — онбординг виден (полный путь участников не требуется). Артефакты `reports/a8-keys/` (вывод apksigner, выжимка логов сборки, скриншот установки). APK в git не коммитить.

5. **Публикация отпечатков.** Файл `docs/RELEASE-KEYS.md` в репо: отпечатки SHA-256 обоих сертификатов, назначение каждого (std/rec), дата генерации, строка-пример проверки установленной APK (`apksigner verify --print-certs ...`). Это публичная информация для участников и поставщиков; wire fingerprint-манифест (мини-этап 12.2) не трогать.

6. **Закрытие находок и отчёт.** A8 → «Решено» в `reports/AUDIT-equality-trust-networks.md`; «release debug-подпись» → «Решено» в `reports/REPORT-AUDIT-FRONTIER-PASS.md`. README/DISCLAIMER — не трогать (тема A10), единственное исключение: если README утверждает debug-подпись релизной сборки как факт — построчная правка факта. Спеку не трогать (подпись APK — вне протокола). Отчёт `reports/REPORT-A8-KEYS.md`: инвентаризация, механика signing-конфига, параметры ключей (алгоритм, размер, срок, alias; без паролей), верификация, отпечатки, изменённые файлы, номера прогонов CI со статусами на момент пуша («CI pending»).

**Предкоммитная проверка (обязательно):** `gofmt -l .` — пусто; `go vet ./...` — чисто; `go test ./...` — зелёный, по задетым пакетам `-race`; `flutter analyze` чисто, `flutter test` зелёный; сборка release-APK (std и rec) с боевыми ключами проходит — предмет темы; `git ls-files '*.jks' '*.keystore'` пуст; `git status` чист. Форматирование — отдельным коммитом от смысловых правок (пометка «formatting only»).

**Финализация:**

- Промежуточные коммиты после каждого завершённого пункта (событийные чекпоинты); после рестарта сессии — до любых действий сверить живое состояние с последним коммитом ветки и отчитаться планом.
- Ресурсная дисциплина: тяжёлые параллельные прогоны не запускать; go-тесты — с `GOMAXPROCS=6`; Gradle-сборки — по одной за раз.
- Финальный коммит — чистое дерево (`git status` чист); ветку `a8-keys` запушить. CI в сессии НЕ ждать: свести номера прогонов всех workflows и закончить отчётом «CI pending».
- Merge в `main` НЕ делать: только после зелёного отчёта CI-verify и подтверждения владельца (слепой аудит ветки — по отдельному промпту после пуша).
- После прогона: остановить Gradle-демоны и оставшиеся процессы сборки (проверить `pgrep`), эмулятор погасить.
- В конце вывести сводку: tip ветки (SHA), механика signing-конфига в двух предложениях, параметры ключей (без паролей), отпечатки SHA-256, путь к credentials-файлу (без содержимого), изменённые файлы, номера прогонов CI («CI pending»), путь отчёта.

**Правила:** предмет темы — только боевая подпись APK. НЕ трогать: протокол/wire/`protocolVersion`, спеку, genesis-семантику, мультиподпись N-из-M и трек «Ключи проекта»/раздел 13 (владение и передача ключей — отдельное решение владельца), A9 (симуляция), A10 (README-эталон), остальные FINDING аудита контура 1, wire fingerprint-манифест 12.2, код ядра/сети/консенсуса. Приватные ключи и пароли — никогда в git, CI, логах, отчёте, артефактах. CI — без боевых ключей. Не коммитить файлы больше 1 МБ; сумма артефактов темы — до ~5 МБ. Находка вне мандата — `FINDING-*.txt` + коммит с пометкой + продолжать; критический блокер прогона — с пометкой «критический блокер прогона». Если для продолжения нужно действие, доступное только владельцу, ИЛИ ты заблокирован и есть риск ошибки, напрасной работы или перерасхода токенов (включая выбор между равнозначными механиками) — остановись и задай в чате один конкретный вопрос; лучше один короткий стоп-вопрос, чем цикл попыток; продолжать после ответа. В конце — только сводка, без вопросов.
