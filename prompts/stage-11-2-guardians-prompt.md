# Промпт: мини-ветка stage11-2-guardians — перевыбор личных гардианов

Выполняй шаги строго по порядку. Каждый пункт — одна законченная инструкция.

## Решение владельца (21.10.2026, выполнять буквально, своего не вносить)

1. Смена личных гардианов после register вводится в протокол. Прежнее ограничение D4 «назначаются навсегда» отменено: сеть может запускаться без посевного круга, а публичные гардианы (возраст ≥ 12 мес.) недостижимы в первый год.
2. Новый тип транзакции update_guardians в закрытом перечне ядра (9.3). Расширение перечня — явное решение владельца; прецедент D2/D4.
3. Лимит: не более 150 вступивших в силу смен гардианов на кошелёк за всё время существования (решение владельца 21.10.2026, повышено с 15). Отменённые и истёкшие смены лимит не потребляют.

## Шаг 0 — подготовка

1. git fetch.
2. Создать ветку stage11-2-guardians от свежего origin/main.
3. Не трогать: main, remote-ветки, README.md, доковские репозитории.

5. Известные падения net-тестов (TestVoteFinalityNetwork, TestSideChannelPublishPropagates) воспроизводятся и на чистом main — регрессом не считать, не чинить.

## Шаг 1 — протокол и ядро (Go)

1. Тип транзакции update_guardians: публикуется в цепочке владельца кошелька, подпись текущим ключом.
2. Payload: новый список личных гардианов (≤ 3, как при register) + пары «адрес нового гардиана + подпись гардианом хеша смены». Согласие передаётся вручную — как approve миграции.
3. Проверки при публикации: новые гардианы active; не flagged (№14); лимит подопечных guardian_personal_max_wards (№7) не превышен; активная смена только одна.
4. Окно вступления в силу — 48 ч (константа, не параметр сети; прецедент — отложенный перевод и повышение P). До истечения действует старый список, после — новый.
5. Подписи гардианов для миграции валидны по списку, действовавшему на момент подписи approve.
6. Отмена смены: подписью владельца в окне 48 ч, только явный ввод PIN.
7. Если к моменту вступления лимит №7 у нового гардиана превышен — смена не вступает в силу, помечается истёкшей.
8. Лимит смен: не более 150 вступивших в силу на кошелёк за всё время. Счётчик — из истории цепочки кошелька. При исчерпании update_guardians отклоняется.
9. Комиссий и наград за смену нет. Смена видна в публичной истории кошелька.

## Шаг 2 — приложение (Flutter)

1. Экран «Гардианы» в настройках: текущий список, «Перевыбрать», ввод пар «гардиан + подпись», отсчёт окна 48 ч, отмена, индикация остатка лимита («использовано N из 150»). Доступ с экрана миграции.
2. Экран согласия гардиана: адрес подопечного, хеш смены, биометрия (как ApproveMigrationScreen). Подпись передаётся вручную.
3. Публикация и отмена смены — только явный ввод PIN (правило этапа 9).
4. Тревожный PIN открывает режим-приманку: операции «смены» в приманке затрагивают только данные приманки, реальный список гардианов не меняется.
5. Все строки в ARB на 5 языках (ru, en, es, pt, zh), fallback en.

## Шаг 3 — тесты

1. Go: публикация и валидации (active, flagged, лимит №7, одна активная смена, лимит 150 — исчерпание → отклонение).
2. Go: окно 48 ч (пинирование часов, как в существующих replay-тестах), отмена, вступление/истечение.
3. Go: миграция с подписями гардианов по старому списку в окне и по новому после вступления.
4. Flutter: widget-тесты экрана «Гардианы» (данные, PIN-only, тревожный PIN не трогает реальный список, остаток лимита) и экрана согласия гардиана.

## Правила

- Промежуточный коммит: после каждого завершённого шага и раз в ~30 минут активной работы. В сообщении коммита — session-ID.
- После рестарта сессии: сверить живое состояние с последним коммитом ветки и отчитаться планом. Ничего не перезапускать без сверки.
- PENDING не додумывать: зафиксировать в отчёте и идти дальше.
- Финальный коммит — чистое дерево. Скриншоты — в репо; бинарники и scratch — нет.
- Пуш ветки и merge в main — только после подтверждения владельца.
- Remote-ветки не удалять.
