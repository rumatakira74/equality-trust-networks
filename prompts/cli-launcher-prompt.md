# Тема CLI-launcher: автозапуск сессий CLI по крону — машина владельца (рут-сессия)

**Предусловие:** запуск по команде владельца (дана). **Рут на сессию выдан** — можно ставить crontab и скрипты в $HOME; системные пакеты НЕ ставить без явной необходимости. Машина владельца: Linux, 8 ядер, 16 ГБ ОЗУ. На машине клоны: `equality-trust-networks` (tnp, публичный) и `mistral-harness-workflows` (приватный репо диспетчера) — найти фактические пути (`ls ~`, `git remote -v`; при неоднозначности — стоп-вопрос). Харнесс — Vibe Code CLI: найти бинарник, версию и точный синтаксис headless-запуска (неинтерактивный прогон с промптом без ожидания человека; флаги модели и thinking-уровня; `--help`, при неясности — docs.mistral.ai). Живых сетей нет; правило CI-verify: статусов CI НЕ ждать.

**Цель:** владелец перестаёт запускать CLI-сессии вручную. Крон на этой машине каждые 10 минут проверяет очередь задач в приватном репо; при появлении задачи лаунчер сам запускает headless-сессию CLI: стартовое сообщение и промпт берутся из файла задачи (последнего в очереди), модель и thinking-уровень — из шапки задачи.

**Архитектура (реализовать как предписано; отступления — только через стоп-вопрос):**

1. **Очередь задач** — в приватном репо `mistral-harness-workflows`, каталог `cli-jobs/` (коммит в main: репо живёт в main, изменения только аддитивные, ничего существующего не трогать):
   - `queue/NNNNNNN-topic.md` — файлы задач (кладёт Vibe из Work-чата; серийник в имени растущий). Формат — YAML-шапка + стартовое сообщение:
    ```
    ---
    topic: audit-fuzz-debts
    target_repo: tnp
    prompt_path: prompts/audit-fuzz-debts-prompt.md
    model: <имя модели как в CLI>
    thinking: max
    timeout_min: 240
    ---
    <стартовое сообщение — первой строкой в сессию>
    ```
   - `processed/` — отработанные задачи; лаунчер переносит файл сюда, дополняя имя суффиксом статуса: `.done` / `.timeout` / `.failed` / `.skipped`.
   - `logs/` — локальные логи; добавить в `.gitignore` репо.
   - `launcher.sh` — сам лаунчер (версионируется здесь же).
   - `README.md` — контракт очереди кратко: формат шапки, статусы, команда запуска, как тестировать.
   - Одна задача = один запуск; повторный запуск того же файла исключён (файл покидает `queue/`).

2. **Лаунчер** (bash, комментарии в коде на русском):
   - `flock` на время всего прогона (никаких параллельных запусков); в cron-окружении задать PATH явно (типовая ошибка крона).
   - `git pull --ff-only` приватного клона; клон `target_repo` тянуть только при наличии задачи.
   - Взять ПОСЛЕДНЮЮ (по серийнику в имени) задачу из `queue/`; остальные файлы в `queue/` пометить `.skipped` (перекрыты более новой задачей).
   - Предзапускные проверки: нет уже идущей автоматической сессии (lock-файл + `pgrep` процесса CLI); свободной памяти >2 ГБ, иначе отложить (exit 0, задача остаётся в `queue/`); файл промпта существует; дедуп — файл с этим именем уже есть в `processed/` → `.skipped`.
   - Запуск headless-сессии в каталоге клона `target_repo`: модель и thinking из шапки (найденный синтаксис флагов зафиксировать в README); режим авто-подтверждений (рут на сессию выдан владельцем); ввод сессии = стартовое сообщение + пустая строка + строка «Полный промпт (исполняй буквально):» + содержимое файла промпта; вывод сессии писать в `logs/NNNNNNN-topic.log`.
   - Таймаут из шапки (по умолчанию 240 мин): по истечении убить сессию и её процессы-детей (`pkill -P`/группа процессов), статус `.timeout`.
   - После завершения: перенести файл задачи в `processed/` с суффиксом статуса; закоммитить перенос и запушить в приватный репо (учётные данные владельца настроены); лог сессии обрезать до последних 2000 строк.
   - Лаунчер НЕ: выбирает модель сам, не создаёт и не мёржит ветки, не пишет в Telegram, не трогает `dispatcher.py` и `.github/` — он только запускатель.
   - Флаг `--dry-run`: показать выбранную задачу и параметры без запуска сессии (для самотеста).

3. **Крон:** строка `*/10 * * * * flock -n /tmp/tnp-cli-launcher.lock <путь-клона>/cli-jobs/launcher.sh >> <путь-клона>/cli-jobs/logs/launcher.log 2>&1`. Установка аккуратно: `crontab -l` → дописать свою строку → установить целиком; существующие записи НЕ трогать; проверить активность сервиса cron (`systemctl is-active cron` или аналог) и что конфликтующих записей нет.

4. **Сквозной тест:** положить в `queue/` тестовую задачу (шапка: `target_repo: tnp`, модель — самая дешёвая из доступных в CLI, `thinking: off` или `low`, `timeout_min: 15`; сообщение: «Диагностический прогон лаунчера. Ничего в репозитории не менять: без веток, коммитов и правок. Ответь одной строкой LAUNCHER-OK и заверши сессию.») → дождаться тика крона → проверить: ответ LAUNCHER-OK в логе; файл в `processed/*.done`; коммит-пуш переноса в приватном репо; повторного запуска того же файла нет. Если ожидание тика дольше 12 минут — допускается ручной прогон лаунчера для теста, но факт установки крона доказать отдельно (строка в `crontab -l` + живой лог крона).

**Пункты:**

1. **Среда:** пути клонов обоих репо; бинарник/версия CLI; дословно найденный headless-синтаксис и флаги модели/thinking (в отчёт); git push работает неинтерактивно.
2. **Скелет** `cli-jobs/` в приватном репо (п.1) — коммит и пуш в main.
3. **launcher.sh** по архитектуре (п.2): `bash -n` обязателен, `shellcheck` если установлен; прогон `--dry-run` на тестовой задаче.
4. **Крон** (п.3) с доказательством установки.
5. **Сквозной тест** (п.4) с цитатой лога в отчёт.
6. **Отчёт:** `reports/REPORT-CLI-LAUNCHER.md` в приватном репо (main): среда и найденный синтаксис; строка крона; результат теста (цитата лога); контракт шапки задачи; ограничения — машина должна быть включена, лаунчер не выбирает модель сам, статусы задач в Telegram — вне темы (интеграция отдельной темой).
7. **Финал:** чистые деревья обоих клонов (кроме предписанных коммитов), крон установлен и виден в `crontab -l`, тест отработал, отчёт запушен; сводка (пути, синтаксис, строка крона, статус теста, что класть в очередь) без вопросов.

**Правила:** событийные коммиты; комментарии в коде на русском; правки вне темы (`dispatcher.py`, `.github/`, код tnp) запрещены; после рестарта сессии — сверка живого состояния с последним коммитом и этим планом; стоп-вопрос при блокере (нужно действие владельца / риск для системы или перерасход токенов); не коммитить файлы больше 1 МБ; ничего не удалять и не менять в системе сверх crontab и файлов в $HOME.
