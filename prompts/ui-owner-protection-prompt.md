# Тема UI-защиты владельца (A5, A6, PIN-лимит, FLAG_SECURE, A4-константа, кодировки надписей) — ветка ui-owner-protection

**Цель:** физический доступ к разблокированному телефону нападающим не даёт ни данных (скриншоты/«недавние»), ни подписей (каждая операция — живая биометрия), ни брутфорса PIN; приманка неотличима для нападающего и управляема владельцем; PoW-константа соответствует решению №9. Поведение честного владельца меняется минимально: понятная политика PIN и биометрия на каждую подпись.

**Задачи:**

1. **PIN-лимит.** Сейчас неверный PIN даёт только фикс-задержку 350 мс. Добавить счётчик неудачных попыток PIN с обоснованной политикой: рост задержки и/или временная блокировка после N неудач, сброс счётчика (успешный вход/время) — значения N и профиль роста с обоснованием в отчёте. Уничтожение ключа при неудачах НЕ вводить (опечатка не должна стоить кошелька). Если политика PIN заявлена в README/спеке — зафиксировать синхронно RU+ENG, построчные правки; не заявлена — в отчёт.

2. **FLAG_SECURE.** Экраны с балансом и иными секретами не должны попадать в системные скриншоты и превью «недавних приложений»: FLAG_SECURE на окнах этих экранов (перечень экранов — с обоснованием в отчёте; способом Flutter/Kotlin по факту кода). Нюанс артефактов: скриншот экрана с FLAG_SECURE выходит пустым — это само доказательство работы флага в прогоне; остальные экраны остаются фотографируемыми, UX не ломать.

3. **Окно подписи 30 с → 0 (A5).** `AUTH_TIMEOUT_SECONDS = 30` (`KeystoreWallet.kt`) → 0: ключ без временного окна — каждая операция подписи требует повторной биометрии. Проверить ВСЕ пути подписи (перевод, миграция, `update_guardians` и др. по факту кода). README 8.1 уже заявляет «без временного окна» — код приводится к заявлению, README не трогать. Тест: после одной операции подписи вторая требует новую биометрию (в окне 30 с раньше — не требовала).

4. **Приманка (A6).** Режим-приманка (`MainActivity.kt`) возвращает «перевод недоступен» — заменить на правдоподобное «ожидает подтверждения» (гардианами/сетью) по спеке 8.2. Проверить ВЕСЬ путь приманки, включая Flutter-сторону (аудитором не проверен): перевод в режиме приманки выглядит для нападающего как обычный ожидаемый перевод; реальный реестр не тронут; никаких видимых признаков примаки. Отличимость для владельца сохраняется — владелец сам инициировал режим и знает пароль приманки.

5. **A4-константа (№9).** `TargetHard` привести от фактических 2^54 (`0x0040_0000_0000_0000`) к 2^56 по решению №9 (этап 6): константа + комментарий + сверка с формулировками доков, где она заявлена (построчно). Тест «итерации из таргета»: тест вычисляет ожидаемую работу PoW из константы и сверяет с комментарием/заявлением. `protocolVersion`: если изменение константы меняет приём tx (фактическая сложность PoW) — поднять и зафиксировать в отчёте; живых сетей нет. Если замер в эмуляторе покажет запретительное время подписи на референс-профиле — НЕ менять значения самовольно: остановиться и задать один стоп-вопрос владельцу. ARM-замер на реальном устройстве — 8-live, отметить в отчёте.

6. **Тесты, эмуляторный прогон, документация.** Обязательные тесты: (1) PIN-лимит: N неудач → блокировка/рост задержки, успешный вход сбрасывает; (2) FLAG_SECURE: окно помечено, скриншот пуст, прочие экраны не помечены; (3) вторая операция подписи требует биометрию (окно 0); (4) приманка: ответ «ожидает подтверждения» на Flutter-пути, реестр не тронут; (5) A4: тест «итерации из таргета» + регресс PoW (валидный tx проходит, невалидный PoW → E_POW*); (6) регресс: честный перевод вне приманки проходит полный путь. Эмуляторный прогон «нападающий с разблокированным телефоном»: скриншоты (баланс — пустой), серия неверных PIN (лимит работает), двойная подпись (вторая требует биометрию), перевод в режиме приманки (правдоподобный ответ); артефакты в `reports/ui-owner-protection/` (логи — .txt, конвенция stage16/net-dos: *.log молча исключаются .gitignore). Документация: сверить формулировки спеки 8.2 и README 8.1 с фактом после правок — синхронно RU+ENG, построчные правки, только где расходится; отчёт аудита: A5, A6 → «Решено», A4 — по факту (`reports/AUDIT-equality-trust-networks.md`).

7. **Кодировки надписей UI.** По артефактам прошлых этапов часть надписей отображается со сбоем кодировки (mojibake). Сначала определить сторону сбоя: приложение (искажение на экране эмулятора) или артефакт (искажение только в сохранённых логах/текстах — окружение записи). Проверить ВСЮ цепочку передачи строк: Go (UTF-8) → gomobile/AAR → Kotlin (String) → Flutter (Dart), включая тексты экранов, Toast/диалоги, сообщения об ошибках ядра (коды E_* с текстами), строки ресурсов, запись логов в файлы (UTF-8 без BOM). Кириллица и латиница должны отображаться корректно на всех проверяемых экранах (выборка — с обоснованием в отчёте). Фикс — в корне (явный UTF-8 при декодировании байтов, конвертация ресурсов в UTF-8), НЕ пере-кодировкой уже искажённого текста. Если сбой артефакт-стороной (окружение записи логов) — починить запись артефактов (UTF-8), само приложение не трогать, зафиксировать в отчёте. Тест: строка с кириллицей и спецсимволами проходит цепочку Go → Kotlin → Flutter и отображается корректно; для FLAG_SECURE-экранов скриншот пуст (п. 2) — корректность строки проверить логом/меткой окна; доказательные артефакты — в `reports/ui-owner-protection/`.

**Предкоммитная проверка (обязательно):** `gofmt -l .` — пусто; `go vet ./...` — чисто; `go test ./...` — зелёный, по задетым пакетам `-race`; `flutter analyze` — чисто, `flutter test` — зелёный; сборка модулей проходит.
