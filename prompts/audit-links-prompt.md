## Что проверяется

Объект — все файлы *.md четырёх репо (README*, docs/, KNOWLEDGE*.md, prompts/, reports/, audit/ и любые другие), включая ссылки в HTML-тегах внутри markdown и ссылки на изображения. Типы:

1. **Внешние URL** (http/https, кроме github.com/rumatakira74): curl, таймаут 10 с, до 2 повторов при таймауте/5xx, User-Agent браузера, редиректы отслеживать (-L). Классификация: 2xx/3xx = OK; 401/403/429 = «неоднозначно (возможен бот-блок)» — битой НЕ считать; остальные 4xx/5xx, DNS-ошибка, таймаут после повторов = БИТАЯ. При 405 на HEAD — повторить GET.
2. **GitHub-ссылки на репо владельца** (github.com/rumatakira74/...): для blob/tree — существование файла/каталога в указанной ветке/теге; для 4 своих репо проверять по локальным клонам (с учётом ветки в ссылке), прочие (зеркало базы знаний и др.) — запросом raw.githubusercontent.com/API. Ссылки вида raw.githubusercontent.com — аналогично.
3. **Относительные ссылки** (file.md, ./docs/01-x.md, ../..., каталоги): целевой файл/каталог существует в клоне; путь считается от каталога документа-источника. Ссылка вида file.md#anchor проверяется и на файл (этот пункт), и на якорь (п.4).
4. **Якоря** (#section внутри документа и file.md#section межфайловые): целевой заголовок существует. Слаг-правила GitHub: lowercase; пробелы → дефисы; пунктуация удаляется; кириллица и Unicode-буквы сохраняются; повторяющиеся заголовки получают суффиксы -1, -2. Реализовать слаггер точно, проверить на кириллических заголовках вручную на 2–3 примерах. Пустые ссылки вида [x]() битыми не считать, но перечислить в отчёте отдельным списком.

## Задачи

1. Во всех 4 клонах: git fetch; убедиться, что аудит идёт по свежему origin/main (в конвейерном клоне tnp: git checkout main && git pull --ff-only; остальные клоны только читать, их состояние не менять — если клон стоит не на main, содержимое читать через git show origin/main:путь).
2. Скрипт-инвентаризация (Python 3, комментарии по-русски): собрать из всех *.md полный список ссылок и якорей — репо, файл, номер строки, тип (1–4), цель. Прогресс-логи и промежуточные выгрузки — в /tmp, НЕ в репо.
3. Проверить все собранные ссылки по правилам типов 1–4. Внешние запросы: не более 8 параллельных; при 429 — пауза 30 с и повтор.
4. Отчёт reports/REPORT-LINKS-AUDIT.md: (а) сводная таблица по репо — сколько .md просканировано, ссылок по типам, битых, неоднозначных; (б) детальная таблица битых — репо, файл:строка, текст ссылки, тип, статус/причина; (в) отдельный список «неоднозначно» с кодами; (г) список пустых якорей; (д) по каждому репо строка-вывод. Находки вне мандата — FINDING-*.txt рядом с отчётом.
5. Чекпоинт-коммиты в ветку audit-links после завершения каждого репо (session-ID в сообщении коммита). Финальный коммит: чистое дерево (git status чист), ветка запушена. В конце конвейерный клон вернуть на main.

## Ограничения и правила

- Ресурсы: не более 6 из 8 ядер и не более 8 параллельных сетевых запросов; перед стартом и во время контролировать память; при доступно < 2 ГБ — стоп, зафиксировать вход/цель в FINDING-*.txt, стоп-вопрос владельцу.
- Коммитить только reports/REPORT-LINKS-AUDIT.md и FINDING-*.txt в ветке audit-links; файлы > 1 МБ не коммитить; файлы аудируемых репо не править.
- Чекпоинты: прогресс-коммит после каждого завершённого пункта/репо; ориентир ~30 минут активной работы проверяется по меткам времени в выводах инструментов, не «по ощущению»; после любого рестарта сессии (краш, --continue, новая сессия) — сверить живое состояние с последним коммитом ветки, отчитаться планом, ничего не повторять без сверки.
- Вопросы: мандат выполняется самостоятельно по задачам и критериям; при блокере, требующем действий только владельца (системные пакеты, доступы, опасные операции), или неоднозначности с риском ошибки/напрасной работы — остановиться и задать в чате один конкретный стоп-вопрос, продолжать после ответа. В конце — только сводка.
