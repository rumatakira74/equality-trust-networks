## Задача

1. **Эпохи и сетевое время (9.2).** Граница эпохи — по сетевому времени от последнего чекпоинта; `epoch_seconds` — вопрос №16, **предложение v1: 24 ч** (обосновать в отчёте; для песочницы — `time_scale`). Календарь UTC: «1-е число месяца» = первая эпоха, начавшаяся после 00:00 UTC 1-го. Допуск timestamp ±30 мин уже в ядре; предел сдвига сетевого времени между чекпоинтами — параметр, предложить дефолт.

2. **Выборочное голосование (9.1).** Snowball-подобное: повторяющийся опрос случайной выборки пиров, **веса — по возрасту и аттестации кошельков**. Параметры (размер выборки k, кворум α, счётчик β) — предложить и обосновать симуляцией; судей и вердиктов нет (7.5): голосование только выбирает ветку при конфликте, метка `flagged` — по-прежнему только через `evidence` любым узлом.

3. **Чекпоинты (spec/07 + 9.1).** Header со `StateRootHash`, `finalized_txid_list`, пороговой подписью N-из-M (`core/threshold`); сбор подписей по сети — тема `checkpoint/<network_id>` из `net/gossip` оживает. Режимы:
   - `decentralized` — подпись выборки валидаторов эпохи; минимальное число M — вопрос №17: рабочая гипотеза **порог ≥ 2/3 M** (spec/07), значение M предложить из симуляции, решение за пользователем по итогам этапа;
   - `members_quorum` — подпись ≥ 2/3 участников (малые сети); **границу размера малых сетей определить симуляцией** (вопрос о малых сетях из QUESTIONS.md, раздел 15 документа) — готовность этапа это требует;
   - переходный режим холодного старта: посевной круг N-из-M по жёсткому расписанию `seed_sunset` (вопрос №15): порог — параметр genesis (число `active`-кошельков **или** число эпох), предложить дефолты в отчёте, локально для тестов: 100 `active` или 24 эпохи.

4. **Симуляция на сотнях виртуальных узлов (9.1).** Headless, детерминированная (seed), поверх тех же core/net. Сценарии: конфликт веток; эквивокация; двойной выпуск; потеря связности и расщепление сети с последующим слиянием; злонамеренное меньшинство в голосовании (доля злонамеренных — варьировать); холодный старт ~10 узлов; `members_quorum` при офлайне части участников; переход `seed_sunset`. Метрики: время до финальности, доля откаченных валидных транзакций, устойчивость по доле злонамеренных. Результаты — в отчёт; по ним — параметры Snowball, M и граница малых сетей.

5. **Интеграция.** `cmd/tnp-node`: голосование и подпись чекпоинта в полном узле; лёгкий узел получает заголовки и Merkle-доказательства из чекпоинтов (использовать готовое из `net/sync`, `core/smt`).

6. **Правка спецификации — авторизована, малым коммитом с пометкой:** `spec/04` INV-9 — конфликтные ветки должны попадать в журнал (альтернативное множество в `finalized_txid_list`), чтобы replay (INV-3) честно воспроизводил выбор финализации; обновить затронутые векторы, если потребует правка. Это единственные изменения spec/proto на этапе (плюс поля №35, `seed_sunset`, `epoch_seconds` в genesis.proto).

7. **Тесты и CI.** Юнит + интеграция + детерминированная симуляция; property-тесты финальности; обновлённые INV-9-тесты; `go test ./...` зелёный, gofmt/vet чистые; CI — расширить `net.yml` или добавить `cons.yml`.

8. **Отчёт `/reports/REPORT-STAGE-5.md`**: принятые параметры (epoch, Snowball k/α/β, пороги M, seed_sunset-дефолты) с обоснованием из симуляции; граница малых сетей; поведение при разделении сети (что видит получатель перевода в каждой из веток до/после слияния); задетые PENDING-вопросы; замеры (время финальности, трафик голосования, размер чекпоинта).

## Правила

1. Источники: разделы 9.1, 9.2, 7.5, 10.1, 13, 15 `docs/KNOWLEDGE.md`; `spec/`; `core/`; `net/`; отчёты этапов 3–4. Ничего не додумывать: механизма нет — в отчёт как PENDING с номером вопроса из `QUESTIONS.md`.
2. `docs/KNOWLEDGE.md` **не редактировать**. Изменения `spec/04` (INV-9) и `proto/genesis.proto` (№35, `seed_sunset`, `epoch_seconds`) — только указанные в п. 3.0 и 6, отдельными коммитами с пометками в сообщении.
3. Вся работа — в новой ветке **`stage5-consensus` от `stage4-network`**; в `main` не вливать; чужие изменения не трогать; пуш — только по решению пользователя.
4. Голосование — единственный механизм разрешения конфликтов; вердикты о «вине» не выносит никто (7.5).
5. Детерминизм обязателен: симуляция воспроизводима по seed; replay из журнала даёт то же состояние (INV-3) с учётом правки INV-9.
6. Отчёты — только в `/reports/REPORT-STAGE-5.md`; имена файлов английские; комментарии в коде русские.
7. Решения №16 (24 ч), №15 (дефолты), №17 (M) — предложения в отчёте; окончательное утверждение за пользователем.

## Критерий готовности (development-plan, этап 5)

Финальность воспроизводится в агрессивных сценариях симуляции; поведение при разделении сети задокументировано; граница размера малых сетей для `members_quorum` определена; чекпоинты подписываются в обоих режимах и в переходном; лёгкий узел проверяет доказательство баланса по чекпоинту.
