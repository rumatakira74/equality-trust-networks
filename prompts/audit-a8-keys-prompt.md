# Тема Blind-аудит ветки a8-keys (тема A8 — боевые ключи подписи APK) — ветка audit-a8-keys (только чтение и reports/)

**Предусловие:** ветка `a8-keys` запушена (tip `2bb50f3`; CI могло докрутиться после пуша — если tip ушёл, работать по текущему tip, сверив предусловия, при сомнении — стоп-вопрос). Запуск — по команде владельца (дана). Ветка `audit-a8-keys` — **от текущего tip ветки `a8-keys`** (не от main: аудит должен видеть код темы). **Режим: только чтение и `reports/` — код, тесты, спека, README, промпты НЕ трогать; находки не править (правки — отдельное решение владельца).** Основание: схема контроля качества темы A8 (исполнитель → blind-аудит → merge по подтверждению владельца после дайджеста). Живых сетей нет. Правило CI-verify: сессия НЕ ждёт статусов CI.

**Слепость:** аудит независимый. Пункты 1–5 выполняются ДО открытия отчёта исполнителя `reports/REPORT-A8-KEYS.md`; его заявления — не истина, а гипотеза для сверки в пункте 6.

**Цель:** механически проверить полноту и качество исполнения мандата `prompts/a8-keys-prompt.md` по факту кода, документов и воспроизводимой сборки; выдать вердикт готовности ветки к merge.

**Пункты:**

1. **Полнота мандата (6 задач).** По каждой задаче мандата — статус по факту: (1) инвентаризация подписи (таблица «точка сборки → подпись → где задаётся»; конфигуратор `cmd/tnp-testnet configure` и путь параметров до сборки); (2) боевые ключи std+rec (генерация локально, `~/.tnp-signing/`, RSA, срок ≥25 лет, отдельные пароли std/rec); (3) точка конфигурации подписи в `configure` (std → `tnp-std`, rec → `tnp-rec`, глобальная — std; явная диагностика при отсутствии ключей; debug-сборки не затронуты); (4) сборка и верификация release-APK std+rec; (5) `docs/RELEASE-KEYS.md` с отпечатками; (6) закрытие находок и отчёт. Каждая — доказательство: файл/строка/коммит.

2. **Секреты и гигиена ключей (критично).** Keystore `tnp-std`/`tnp-rec` в `~/.tnp-signing/` не покидают машину и не попадают в git, CI, логи, отчёт и артефакты. Проверки: `git ls-files '*.jks' '*.keystore'` пуст; `git status` чист; `.gitignore`-паттерны (`*.jks`, `*.keystore`, локальные signing-конфигурации) на месте; signing-конфиг (пути/пароли) читается из локального файла ВНЕ git; в истории ветки нет `.jks`/`.keystore`/конфигов с паролями (`git log --all --diff-filter=A -- '*.jks' '*.keystore'`); CI/workflows не содержат боевых ключей и не правились. Пароли, содержимое credentials-файла и приватные ключи НИКОГДА не печатать — только пути и факты. Утечка секрета — FINDING критической значимости.

3. **Воспроизводимая сборка и верификация.** Собрать release-APK обоих видов (std-сеть и rec-сеть; тестовые genesis из `cmd/tnp-testnet`) с боевыми ключами; `apksigner verify --print-certs` — отпечатки SHA-256; сверить с `docs/RELEASE-KEYS.md`. Вывод apksigner — в артефакты `reports/audit-a8-keys/` (только отпечатки, без секретов). APK в git не коммитить.

4. **Документы ветки.** `docs/RELEASE-KEYS.md`: отпечатки SHA-256 обоих сертификатов, назначение (std/rec), дата генерации, строка-пример проверки — сверить с фактом apksigner (пункт 3). A8 → «Решено» в `reports/AUDIT-equality-trust-networks.md`; «release debug-подпись» → «Решено» в `reports/REPORT-AUDIT-FRONTIER-PASS.md`. README/DISCLAIMER, спека, wire fingerprint-манифест 12.2 — не тронуты (проверить `git diff main...a8-keys`).

5. **Процесс и гигиена ветки.** `git diff main...a8-keys` — только предмет темы (подпись APK: signing-механика, .gitignore, docs/RELEASE-KEYS.md, отчёт, артефакты, закрытие находок). Правки вне мандата (протокол/wire/спека/genesis-семантика/раздел 13/A9/A10/остальные FINDING аудита) — FINDING «вне мандата». Событийные коммиты; форматирование — отдельным коммитом; файлов больше 1 МБ нет; артефакты темы до ~5 МБ; APK в git нет.

6. **Сверка с отчётом исполнителя.** Только теперь открыть `reports/REPORT-A8-KEYS.md`: каждое ключевое заявление (инвентаризация, механика signing-конфига, параметры ключей, результаты apksigner, отпечатки, изменённые файлы, номера прогонов CI) — подтверждено кодом/коммитом/собственной сборкой или расходится (цитата + факт). Расхождения — в таблицу.

7. **FINDING вне мандата.** Крипто-безопасность протокола — отдельный контур: крипто-наблюдения — с пометкой «вне мандата», глубоко не исследовать. Ветки `main` — только база сверки, не аудитировать.

**Ресурсные правила (обязательно):** тяжёлые параллельные прогоны не запускать; Gradle-сборки — по одной за раз; go-тесты при необходимости — `GOMAXPROCS=6`; стоп при <2 ГБ свободной памяти или тормозах машины → FINDING + стоп-вопрос. После прогонов — остановить Gradle-демоны и оставшиеся процессы сборки (`pgrep`), эмулятор погасить.

**Отчёт:** `reports/REPORT-AUDIT-A8-KEYS.md` — таблица «задача мандата → статус → доказательство → замечание», таблица находок (FINDING: файл/строка, значимость, рекомендация — НЕ реализовывать), таблица сверки с отчётом исполнителя, вердикт: **«готова к merge» / «готова с замечаниями» / «не готова»** со списком блокеров. Артефакты — `reports/audit-a8-keys/` при необходимости.

**Правила:** только чтение + `reports/`; событийные коммиты (только reports/); после рестарта сессии — сверка живого состояния с последним коммитом ветки и отчёт планом; не коммитить файлы больше 1 МБ; секреты и пароли никогда не коммитить и не печатать; стоп-вопрос при блокере (нужно действие владельца / риск ошибки, напрасной работы или перерасхода токенов); финал — чистое дерево, пуш ветки `audit-a8-keys`; merge НЕ делать — только после дайджеста Vibe и подтверждения владельца; в конце — сводка (tip ветки, статусы по пунктам 1–7, перечень FINDING, вердикт, путь отчёта), без вопросов.
