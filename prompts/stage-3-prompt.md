## Задача

Go-ядро реестра без сети (development-plan, этап 3): полная логика транзакций ядра, проверяемая каждым узлом, плюс хранилище. Headless: без libp2p, без голосования, без чекпоинтной сети. Источник правды о времени — интерфейс `net_time`/`epoch`, внедряемый тестами; финализация — интерфейс (реализация в этапе 5).

## Подэтап 3.0. Криптофундамент (этап 2, отсутствует в репо)

- Подписи ECDSA P-256: генерация/верификация, DER; `signing_preimage = canonical(Transaction с пустой signature)`, `signing_hash = SHA-256(preimage ‖ pow.nonce)`, `txid = SHA-256(canonical(полная Transaction))` (spec/01 1.2).
- Canonical-кодирование protobuf: поля в порядке номеров, unknown-поля запрещены. Покрыть тестами на стабильность байтов (хеши обязаны совпадать между узлами).
- PoW: лёгкий `SHA-256(preimage ‖ nonce) < target_light`; усиленный Argon2id (`golang.org/x/crypto/argon2`, параметры из `ProfileParams.pow_params`). Значения таргетов «под средний телефон» выбрать минимально консервативно и пометить как предположение — вопрос №9 остаётся открытым.
- Sparse Merkle-дерево состояния: `StateLeaf` из 9 полей (решение D7, spec/07); построение, включение, доказательства.
- Пороговая подпись чекпоинтов: N-из-M набор подписей ECDSA P-256 (закрытое решение этапа 0); только проверка набора, сетевой сбор подписей — этап 5.
- Разбор цепочки аттестации Android (`encoding/asn1`): корни Google, `verifiedBootState`, `deviceLocked`, уровень патча; синтетические тестовые цепочки, реальные — этап 6. Формулу `attestation_challenge` (вопрос №23) сделать параметризуемой, дефолт пометить как предположение.
- Деривация адреса из фингерпринта (вопрос №2 — блокер): адрес = 32 байта. Предложить в отчёте вариант (например, `SHA-256(fingerprint ‖ network_id)` — привязка к сети защищает от переноса адреса между сетями), реализовать как заменяемую функцию с явной пометкой PENDING.

## Подэтап 3.1. Хранилище (раздел 12.5)

SQLite, pure-Go драйвер (`modernc.org/sqlite`, без CGo): цепочки транзакций по кошелькам, индекс `фингерпринт → адрес`, чёрный список фингерпринтов, заголовки чекпоинтов (таблица + интерфейс), состояние (балансы, seq, статусы, метки, слоты, pending-операции). Пересчёт состояния из genesis + журнала — детерминированный (INV-3).

## Подэтап 3.2. Валидация и применение (spec/03)

Все типы ядра: `REGISTER`, `VOUCH`, `MINT`, `TRANSFER` (send / cancel / set_threshold), `MIGRATE` (propose / cancel), `EVIDENCE`, `GUARDIAN_OFFER`.

- Порядок проверок: общие C1–C11 → типовые таблицы (R1–R7, V1–V9, M1–M7, T1–T8, X1–X4, S1–S2, G1–G5, N1–N2, E1–E7, O1–O2) → эффекты. Каждый отказ — точный код `E_*` из spec/00 0.4.
- Модульные типы (pool/redeem/receipt/contribution) — не реализуются (этап 10); структура ядра не должна им мешать.
- Эквивокация — не ошибка валидации: обе ветки проходят C1–C11, конфликт разрешает финализация; `EVIDENCE` — по E1–E7, последствия — мягкая схема (постоянный `flagged`, приостановка выпуска на N мес. — локально N = 3, вопрос №12; доля R поручителям = 0 с эпохи финализации; штрафов и потери слотов нет).

## Подэтап 3.3. Сеттлемент на границе эпох (детерминированный)

- Демередж: транзакций списания нет; `balance_eff = floor + (balance − floor) × (1 − rate)^n`, n — эпохи от последней операции, менявшей баланс (№31 — решение принято в 1.2); списанное сжигается; к pending-резерву не применяется (№18 — за пользователем).
- Окно переводимости свежих выпусков (новый параметр, закрыт данными 1.2, вопрос №11): выпуск периода t переводим с t + 3 мес. Реализация — пер-юнит: когорты выпусков по периодам, списание сначала из старейших переводимых. **Добавить поле в `proto/genesis.proto`** (например, `uint64 fresh_transfer_window_periods`, пометка [M], рядом с `accrual_window_periods`) и обновить `spec/03` T8 и словарь `spec/00` — одним малым коммитом с пометкой «закрывает №11 по REPORT 1.2».
- Исполнение pending-переводов через 48 ч без отмены; отмена возвращает резерв; повышение P через 48 ч, понижение сразу.
- Исполнение миграции через 14 дней: перенос возраста, истории выпусков, `last_claimed_period`, поручительств; старый фингерпринт — навсегда в чёрный список; награда публичным гардианам только подписавшим.
- Истечение `registered` (3 года), освобождение слотов (3 периода выпуска / 90 дней), `seed_sunset`-механика — проверки на границе эпох.

## Подэтап 3.4. Параметры по умолчанию (из REPORT.md 1.2, раздел 5)

Демередж 1 %/мес + floor 3000; комиссия: `fee_min` 1, границы [0,5 %; 2 %], старт 1 %, `fee_mode = BURN`; окно переводимости 3 мес.; мораторий 14 дней; P = 3000, `P_max` = 30000; K = 3, слоты 3/5/10, R = 10 %, посев ≥ 300 — зафиксированы этапом 1.1, **не трогать**. Все значения — по умолчанию в тестовом genesis; в коде — из манифеста, не зашиты.

## Подэтап 3.5. Тесты

1. **Векторы** (обязательный регресс): `valid_register`, `valid_vouch`, `valid_mint`, `valid_transfer`, `valid_evidence`, `valid_migrate`, `valid_guardian_offer`, `bad_equivocation`, `bad_double_mint`, `bad_moratorium`, `bad_accrual_window`, `flow_delayed_cancel` — каждый даёт предсказанный `OK`/`E_*`.
2. **Property/fuzz** по spec/04 4.3: генератор случайных потоков (валидные, невалидные, конфликтные: два seq, дубль-mint, отмена вне окна, vouch без слота); оракул `apply` → `OK`/`E_*`; после каждого шага INV-1..INV-14 (дешёвые — каждый шаг, INV-3/7/8 — на границах эпох); метаморфный тест: мутация валидной транзакции меняет ровно один код.
3. **Сквозной headless-сценарий**: register → vouch ×3 → mint → transfer → отложенный перевод > P → cancel → evidence на эквивокации → migrate с гардианами; INV-8 (сохранение предложения) проверяется на каждом шаге.
4. `go test ./...`, `go vet`, `gofmt` — зелёные; CI GitHub Actions (трек «Инфраструктура разработки» начинается с этапа 3).

## Правила

1. Единственные источники: `spec/` + `proto/` + `vectors/` + `QUESTIONS.md` репозитория equality-trust-networks и `Mistral/REPORT.md` (equality-anti-farm-simulation) для значений. Ничего из документа не додумывать: если механизма нет — отметить в отчёте как PENDING с номером вопроса.
2. Закрытые перечни (типы транзакций, инварианты, последствия evidence) не расширять.
3. `KNOWLEDGE.md` не редактировать. В `spec/`/`proto/` — только добавление `fresh_transfer_window_periods` и сопутствующие правки (см. 3.3); при расхождении кода со спецификацией чинить код, не спецификацию; найденные противоречия — в отчёт, не молча.
4. PENDING-вопросы использовать по предположениям v1 из QUESTIONS.md; каждое использование — в отчёте. Вопросы №2, №9, №23 — блокеры, требующие решения пользователя: в отчёте дать рекомендации, код — с заменяемыми функциями и пометками.
5. Вся работа — в новой ветке `stage3-core` репозитория equality-trust-networks (код в `core/`, каркас от `go.mod` в корне). Чужие незакоммиченные изменения не трогать, в main не вливать, пуш — только по решению пользователя.
6. Отчёт `core/REPORT-stage3.md`: что сделано, задетые PENDING-вопросы с рекомендациями, отклонения от спецификации (если есть), замеры (размер транзакции против ориентира ~250 байт, скорость apply/верификации, размер БД после сквозного сценария).

## Критерий готовности (development-plan, этап 3)

Ядро проходит полный набор тестов спецификации: все типы транзакций ядра работают локально, векторы зелёные, INV-1..14 выполняются в fuzz-потоках, сеттлемент на границах эпох детерминирован. Сеть (этап 4) и консенсус (этап 5) не реализуются — только интерфейсы (`EpochSource`, `Finalizer`, `CheckpointStore`).
